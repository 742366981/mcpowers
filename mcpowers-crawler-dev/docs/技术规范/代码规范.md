# 代码规范

本文档定义高质量代码的编写规范，适用于所有编程语言和项目类型（后端、前端、移动端、嵌入式等）。

> **核心原则**：写出可维护、可扩展、可测试的高质量代码
>
> **语言无关**：规范内容适用于任何编程语言，代码示例仅作参考

---

## 1. 数据建模规范（强制）

### 1.1 实体关联原则

**优先建立实体间关联，避免数据冗余**：

| 关联类型 | 正确做法 | 错误做法 |
|:---------|:---------|:---------|
| 一对多 | 主表存外键，从表关联主表 | 主表冗余从表数据 |
| 多对多 | 使用中间表关联 | 冗余 ID 列表 |
| 一对一 | 从表存主表外键 | 数据完全重复 |

### 1.2 冗余数据控制

**允许冗余的条件（必须同时满足）：

1. 该字段被查询的频率**极高**
2. 关联实体的变更频率**极低**
3. 冗余字段占用空间**可接受**
4. 数据一致性由**业务层保证**

### 1.3 关联查询的正确方式

**预加载关联数据，避免重复查询**：

```
❌ 错误：N+1 查询
   查询 100 条订单 → 再查询 100 次用户 = 101 次数据库调用

✅ 正确：JOIN 预加载
   查询 100 条订单及其用户 → 1 次数据库调用（含 JOIN）
```

## 2. 查询性能规范（强制）

### 2.1 N+1 查询问题（强制）

**N+1 查询**：1 次主查询 + N 次关联查询

| 问题程度 | 查询次数 | 影响 |
|:---------|:--------|:-----|
| 严重 | 1 + N | 100 条记录 = 101 次查询 |
| 轻微 | 1 + 1 | 2 次查询，但可能无索引 |

### 2.2 深度分页性能问题

```sql
-- ❌ 错误：OFFSET 越大越慢
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 1000000;

-- ✅ 正确：游标分页
SELECT * FROM orders
WHERE id > 1000000
ORDER BY id LIMIT 20;
```

### 2.3 批量操作规范

**批量操作优先于循环单条操作**。

## 3. 函数设计规范（强制）

### 3.1 单一职责原则（SRP）

**一个函数只做一件事**。

### 3.2 参数规范

| 要求 | 说明 |
|:-----|:-----|
| 参数数量 ≤ 3 | 超过3个应使用配置对象 |
| 参数类型明确 | 使用类型声明 |
| 避免可变默认参数 | 使用 `None` 而非 `[]` 或 `{}` |

### 3.3 返回值规范

| 要求 | 说明 |
|:-----|:-----|
| 返回类型一致 | 成功/失败返回同类型或使用 Result 封装 |
| 不返回 null 表示成功 | 使用特定值或异常 |
| 集合类型返回空集合 | 返回 `[]` 而非 `null` |

---

## 4. 错误处理规范（强制）

### 4.1 异常使用原则

| 使用异常 | 不使用异常 |
|:---------|:-----------|
| 预期外的错误（网络中断、内存不足） | 业务校验失败（用返回值） |
| 程序无法继续执行 | 表单验证失败 |
| 需要中断调用栈 | 业务流程控制 |

### 4.2 异常捕获规范

**捕获具体异常，不过度捕获**。

### 4.3 异常传播原则

**只传播必要信息，隐藏实现细节**。

---

## 5. 防御性编程规范（强制）

### 5.1 参数校验

**入口函数必须校验输入**。

### 5.2 空值处理

**链式调用前检查空值**。

### 5.3 并发问题

**更新时防止竞态条件**：使用乐观锁或悲观锁。

---

## 6. 代码复用规范（强制）

### 6.1 DRY 原则（Don't Repeat Yourself）

**重复代码必须抽象**。

### 6.2 避免硬编码

使用常量/枚举替代魔法值。

---

## 7. 注释与文档规范（强制）

### 7.1 必要注释的场景

| 场景 | 要求 |
|:-----|:-----|
| 复杂业务逻辑 | 必须注释解释 WHY |
| 非直观写法 | 必须注释解释原因 |
| 性能关键代码 | 必须注释说明性能考虑 |
| 外部依赖 | 必须注释说明来源和用途 |
| 未完成代码 | 使用 `TODO:` 标记 |

### 7.2 注释要求

**解释"为什么"而非"是什么"**。

### 7.3 TODO 注释规范

```python
# ✅ 正确：TODO 格式
# TODO(username): 优化此处查询性能，计划在 v2.1 使用缓存
```

## 8. 日志规范

### 8.1 日志级别使用

| 级别 | 使用场景 |
|:-----|:---------|
| DEBUG | 开发调试，生产环境不开启 |
| INFO | 正常业务流程 |
| WARNING | 异常但可处理（参数校验失败） |
| ERROR | 错误需处理（数据库连接失败） |
| CRITICAL | 严重错误（服务不可用） |

### 8.2 日志内容规范

```python
# ✅ 正确：包含上下文
logger.error(f'Query failed: user_id={user_id}, error={e}')
```

## 9. 安全规范（强制）

### 9.1 SQL 注入防护

**禁止字符串拼接 SQL**，使用参数化查询。

### 9.2 敏感数据处理

日志记录时对敏感数据进行脱敏处理。

## 10. 代码风格规范

### 10.1 命名规范

| 类型 | 规范 | 示例 |
|:-----|:-----|:-----|
| 变量 | 小写下划线 / 小驼峰 | `user_name`, `userName` |
| 函数/方法 | 小写下划线 / 小驼峰 | `get_user`, `getUser` |
| 类 | 大驼峰 | `UserService`, `OrderController` |
| 常量 | 全大写下划线 | `MAX_RETRY`, `API_KEY` |

---

## 11. 变更控制规范（强制）

### 11.1 最小化改动原则

**每次变更只涉及必要的文件**。

### 11.2 根因分析原则

**修复问题前必须分析根因，禁止症状治疗**。

### 11.3 死代码清理

**废弃代码必须删除，不得注释掉**。

---

## 12. 可测试性规范（强制）

### 12.1 可测试代码要求

| 要求 | 说明 |
|:-----|:-----|
| 纯函数优先 | 相同输入必有相同输出，无副作用 |
| 依赖注入 | 将外部依赖通过参数传入，便于 mock |
| 单一职责 | 函数职责单一，测试用例易于编写 |
| 确定性 | 不依赖时间、随机数、网络等不确定因素 |
