# 日志规范

> **栈无关**。Flask/FastAPI/Spring/Express/Gin/爬虫共用。
>
> **本规范的 3 个不可妥协目标**：
>
> 1. **统一**：所有项目必须使用同一套日志类型与字段 schema，跨服务/跨模块可聚合
> 2. **可排查**：通过 `request_id` + `trace_id` + `span_id` 串联任意一次请求的全链路日志
> 3. **不爆**：默认对大内容截断 + 指纹，对敏感字段自动脱敏，单条日志体积可控

---

## 0. 术语表

| 术语 | 含义 |
|:-----|:-----|
| **biz 日志** | 业务关键节点（"订单创建成功"），用于业务追溯 |
| **operation 日志** | 用户操作审计（"用户 X 删除了 Y"），用于事后追责 |
| **audit 日志** | 合规审计（"登录/登出/权限变更"），用于安全合规 |
| **request 日志** | HTTP 请求生命周期（before/after 中间件），用于全链路追踪 |
| **perf 日志** | 性能采样（接口耗时/慢查询），用于性能监控 |
| **schedule 日志** | 定时任务执行（开始/结束/异常），用于任务追溯 |
| **exception 日志** | 异常 + traceback，用于故障定位 |
| **request_id** | 单次 HTTP 请求唯一 ID，由网关/中间件生成（继承 `X-Request-ID`） |
| **trace_id** | 整条调用链 ID（如分布式链路中跨服务的同一笔交易） |
| **span_id** | 链路中某一跳 ID |
| **大内容** | 单条日志序列化后 > 阈值的字段（默认阈值 2KB） |

## 1. 铁律（5 条不可违反）

| # | 铁律 | 违反后果 |
|:-:|:-----|:---------|
| 1 | **所有日志必须 JSON 结构化**（一行一对象） | 文本日志无法聚合/告警 |
| 2 | **所有 `logger.*` 调用必须带上下文**（`request_id` / `trace_id` / `user_id` 三选一） | 事后无法串联日志定位问题 |
| 3 | **大内容（>2KB）默认截断 + 指纹**，禁止原样落盘 | 一条日志炸穿磁盘/带宽 |
| 4 | **敏感字段必须经过 `mask_sensitive` 脱敏**，禁止裸写 password/token | 安全合规事故 |
| 5 | **日志类型必须从 §2 的 7 类中选**，禁止发明新类型 | 跨服务类型对不上，无法聚合 |

> **违反任何一条 = Critical 级别 code-review 问题，合并前必须修复**。

## 2. 日志类型（7 类统一约定）

> **禁止发明新类型**。如确有需求 → 先提需求评审，统一扩展本表。

| 类型 (`type`) | 典型场景 | 必填字段 | 输出通道 |
|:--------------|:---------|:---------|:---------|
| `biz` | 业务关键节点（订单创建/支付成功/审核通过） | `biz_event`, `biz_id` | `biz.log`（按天轮转） |
| `operation` | 用户操作审计（删除/导出/修改权限） | `op_action`, `target_type`, `target_id` | `operation.log` |
| `audit` | 合规审计（登录/登出/权限变更） | `audit_action`, `actor_id`, `result` | `audit.log`（长保留 ≥ 180 天） |
| `request` | HTTP 请求生命周期（before/after 中间件） | `method`, `path`, `status_code`, `cost_ms` | `request.log`（按天轮转） |
| `perf` | 性能采样（接口耗时/慢查询） | `metric`, `value`, `threshold` | `perf.log`（可采样） |
| `schedule` | 定时任务执行（开始/结束/异常） | `job_name`, `job_id`, `status` | `schedule.log` |
| `exception` | 异常 + traceback（任何 `try/except` 内） | `exc_type`, `exc_msg`, `traceback` | `exception.log`（ERROR+ 全量保留） |

### 2.1 类型选择的判定流程

```
是要记录业务事件吗？  ── 是 ──> biz
是要记录谁操作了什么吗？── 是 ──> operation 或 audit（视合规要求）
是 HTTP 请求生命周期？ ── 是 ──> request
是性能指标采样？    ── 是 ──> perf
是定时任务执行？    ── 是 ──> schedule
是异常 catch？      ── 是 ──> exception（强制 traceback 全量）
```

### 2.2 类型与级别的对应

| 类型 | 推荐默认级别 | 备注 |
|:-----|:--------------|:-----|
| `biz` | INFO | 业务关键节点，便于回溯 |
| `operation` | INFO | 正常操作 |
| `audit` | INFO / WARNING（失败时） | 失败登录记 WARNING |
| `request` | INFO（2xx/3xx）/ WARNING（4xx）/ ERROR（5xx） | 状态码自动映射 |
| `perf` | INFO（正常）/ WARNING（超阈值） | 慢查询标 WARNING |
| `schedule` | INFO（开始/结束）/ ERROR（失败） | |
| `exception` | ERROR（业务可恢复）/ CRITICAL（系统级） | 见 §3.4 |

## 3. 字段 schema（统一 JSON 结构）

### 3.1 全局必填字段（任何日志都必须有）

```json
{
  "time": "2026-07-21T10:23:45.123+08:00",   // ISO8601 带时区（强制）
  "level": "INFO",                            // DEBUG/INFO/WARNING/ERROR/CRITICAL
  "type": "biz",                              // §2 的 7 类之一
  "trace_id": "a1b2c3d4e5f6...",              // 链路 ID（无链路则填 "-"）
  "msg": "订单创建成功"                        // 人类可读的一句话
}
```

### 3.2 全局推荐字段（链路追踪必备）

| 字段 | 类型 | 说明 |
|:-----|:-----|:-----|
| `request_id` | string | 单次 HTTP 请求 ID（来自 `X-Request-ID` 头或中间件生成） |
| `span_id` | string | 链路中某一跳 ID |
| `parent_span_id` | string | 父 span（无则 `-`） |
| `user_id` | string/int | 当前操作用户 ID（未登录记 `-`） |
| `module` | string | 模块名（如 `order.service`），用于快速过滤 |
| `service` | string | 服务名（微服务架构必填） |

### 3.3 各类型必填字段（叠加在 §3.1 之上）

| 类型 | 必填字段 |
|:-----|:---------|
| `biz` | `biz_event`（如 `order.created`）, `biz_id`（业务对象 ID） |
| `operation` | `op_action`（如 `delete`）, `target_type`, `target_id` |
| `audit` | `audit_action`（如 `login`）, `actor_id`, `result`（success/fail） |
| `request` | `method`, `path`, `status_code`, `cost_ms` |
| `perf` | `metric`（如 `db.query.duration`）, `value`（数值）, `threshold`（阈值） |
| `schedule` | `job_name`, `job_id`, `status`（start/end/error） |
| `exception` | `exc_type`, `exc_msg`, `traceback` |

### 3.4 exception 类型的额外要求（强制）

| 要求 | 说明 |
|:-----|:-----|
| `traceback` 完整性 | 必须记录**完整堆栈**，禁止截断 |
| 记录方式 | `logger.exception(...)` 或 `logger.error(..., exc_info=True)` |
| 必带上下文 | `user_id` / `request_id` / 关键业务参数（脱敏后） |

```python
# ✅ 正确：exception 类型自动带 traceback
try:
    create_order(data)
except Exception as e:
    logger.exception(
        "订单创建失败",
        extra={
            "type": "exception",
            "biz_event": "order.created",
            "biz_id": data.get("order_id"),
            "user_id": g.user_id,
        }
    )
    raise

# ❌ 错误：只记录 str(e)，丢失堆栈
logger.error(f"订单创建失败: {e}")
```

### 3.5 extra 字段的命名规范

- 自定义字段必须带**业务前缀**（避免 key 冲突），如 `order_id` / `payment_id`
- 多单词用**下划线**（与 JSON 习惯一致）
- 禁止使用魔法缩写（如 `oid`、`pid`）

## 4. 大内容处理（强制）⭐ 防日志炸盘

### 4.1 默认策略：自动截断 + 指纹

| 场景 | 阈值 | 截断方式 | 保留信息 |
|:-----|:-----|:---------|:---------|
| 单条日志 msg + extra 序列化后总大小 | **> 2KB** | 保留首 1.5KB + 末 0.5KB，中间省略 | `original_size`、`sha256`、`truncated=True` |
| 文件/二进制/图片 | **任何大小** | **永不存内容**，只存元信息 | `file_path`、`file_size`、`sha256` |
| SQL 语句 | **> 2KB** | 保留首 1KB + 末 0.5KB | `original_size`、`sha256` |
| traceback / 堆栈 | **> 5KB** | 完整保留（前 N 帧 + 后 N 帧） | `total_frames`、`truncated_frames` |
| HTTP 响应体 | **> 5KB** | 保留首 2KB + 末 1KB | `original_size`、`sha256` |

> **所有截断都必须在日志中记录 `original_size` + `sha256`**，事后可基于指纹追溯原始内容（仅当原始内容被显式持久化到 large.log 时才可能还原）。

### 4.2 截断日志的标准格式

```json
{
  "time": "2026-07-21T10:23:45.123+08:00",
  "level": "INFO",
  "type": "biz",
  "trace_id": "a1b2c3d4e5f6",
  "msg": "导入完成（前 1.5KB + 后 0.5KB，已截断）...[TRUNCATED, original_size=124000, sha256=8f3a2b..., saved_to=large-20260721.log]",
  "extra": {
    "biz_event": "import.completed",
    "truncated": true,
    "original_size": 124000,
    "sha256": "8f3a2b..."
  }
}
```

### 4.3 显式豁免：用户明确说"这个大内容要存"

两种方式任选其一：

```python
# 方式 1：使用 logger.large() 落独立 large.log 文件
logger.large(
    content=full_response_body,
    tag="audit_full",
    extra={"type": "audit", "audit_action": "export"}
)

# 方式 2：extra 标记 _persist_full（仅 DEBUG 模式生效，线上会被剥掉）
logger.info("全量响应", extra={"_persist_full": True, "response": full_body})
```

> **默认线上不会启用 `large` 或 `_persist_full`**。这是有意设计 —— 让"大内容要存"必须显式声明，开发者会想清楚为什么。

### 4.4 反模式黑名单（code-review 必须 Critical）

| # | 反模式 | 后果 |
|:-:|:-------|:-----|
| 1 | ❌ 直接把 `request.body` / `response.body` 拼进日志 | 一行日志几 MB |
| 2 | ❌ 把 ORM 查出来的整张表 `list(query.all())` dump 进日志 | 列表爆炸 |
| 3 | ❌ 截断用 `...` 但**不记录原始大小/指纹** | 事后无法补救 |
| 4 | ❌ 把 Base64 图片 / 二进制文件内容存进日志 | 单条日志爆炸 |
| 5 | ❌ `print()` 当日志用（绕过 logger） | 不走 JSON 模板，无 trace_id 串联 |
| 6 | ❌ 把 SQL 参数列表原样塞日志（含用户输入） | 注入风险 + 体积爆炸 |

## 5. 敏感信息脱敏（强制）

### 5.1 全局敏感字段黑名单

> 任何字段名（不区分大小写）命中以下黑名单 → **自动替换为 `******`**。

| 字段名 | 类别 |
|:-------|:-----|
| `password` / `pwd` / `passwd` | 凭证 |
| `token` / `access_token` / `refresh_token` | 凭证 |
| `secret` / `api_secret` / `client_secret` | 凭证 |
| `api_key` / `apiKey` / `app_key` | 凭证 |
| `authorization` / `cookie` / `set-cookie` | HTTP 头 |
| `id_card` / `身份证` / `身份证号` | PII |
| `phone` / `mobile` / `手机号` | PII |
| `bank_card` / `银行卡` / `银行卡号` | PII |
| `统一社会信用代码` | 企业 PII |

### 5.2 实现约定

> **封装层自动脱敏一次，业务层仍需自查**。两遍保险，不依赖业务自觉。

- **封装层**：日志中间件/封装类在序列化前对 dict/list 递归调用 `mask_sensitive(data)`（实现见 `安全规范.md §5.1`）
- **业务层**：业务代码**禁止**直接 `logger.info(f"password={password}")`，必须显式调用 `mask_sensitive` 或剔除敏感字段

### 5.3 反模式

| # | 反模式 | 后果 |
|:-:|:-------|:-----|
| 1 | ❌ 日志打印明文密码/身份证/手机号 | 信息泄露事故 |
| 2 | ❌ `logger.info(f"Login: {request.json}")` 整坨请求体 | 全字段泄露 |
| 3 | ❌ 依赖"开发环境不开敏感接口"的安全策略 | 生产环境一开就裸奔 |

## 6. 级别判定与采样

### 6.1 级别使用规范

| 级别 | 使用场景 | 线上默认 |
|:-----|:---------|:---------|
| DEBUG | 开发调试细节（SQL 参数、变量值） | **关闭**（线上不输出） |
| INFO | 正常业务流程 | **开启** |
| WARNING | 异常但可处理（参数校验失败、重试成功） | **开启** |
| ERROR | 错误需处理（数据库连接失败、业务异常） | **开启** |
| CRITICAL | 严重错误（服务不可用、数据不一致） | **开启**（触发告警） |

### 6.2 采样策略（性能 vs 成本的平衡）

| 日志类型 | 采样率 | 说明 |
|:---------|:-------|:-----|
| `biz` | 100% | 业务关键节点不能丢 |
| `operation` | 100% | 审计追溯不能丢 |
| `audit` | 100% | 合规要求 |
| `request` | 100%（2xx/3xx）/ 100%（4xx/5xx） | 错误请求不能丢 |
| `perf` | **1%-10%**（推荐 1%） | 高频接口全量会撑爆存储 |
| `schedule` | 100% | 任务数量通常不大 |
| `exception` | 100% | 异常永远全量 |

> 采样开关通过配置中心控制，关闭采样时全量输出（开发/排障场景）。

### 6.3 级别判断的常见误区

| # | 误区 | 正确做法 |
|:-:|:-----|:---------|
| 1 | ❌ 所有日志都用 INFO | 校验失败用 WARNING，异常用 ERROR |
| 2 | ❌ 用 `print()` 输出 | 走 `logger.*` 才能带上下文与级别 |
| 3 | ❌ try/except 后 `pass`（吞异常） | 至少 `logger.exception(...)` |

## 7. 输出与轮转

### 7.1 输出通道

| 通道 | 用途 | 格式 |
|:-----|:-----|:-----|
| **stdout** | 开发环境（Docker/K8s 容器标准输出） | 彩色文本（开发）/ JSON（线上） |
| **文件** | 生产环境（Filebeat/Fluent Bit/Vector 收集） | JSON 行（每行一对象） |
| **large.log** | 大内容豁免落盘（独立文件） | JSON 行 |
| **syslog / 远程** | 合规审计场景（可选） | 按实际协议 |

### 7.2 文件命名与轮转

```
logs/
├── app.log               # 主日志（INFO+，按天轮转）
├── app.log.2026-07-20    # 轮转历史（≤ 7 天免压缩窗口内为 .log；超过后变 .log.2026-07-20.gz）
├── biz.log               # 业务日志
├── operation.log         # 操作日志
├── audit.log             # 审计日志（保留 ≥ 180 天）
├── request.log           # 请求日志
├── perf.log              # 性能日志
├── schedule.log          # 定时任务日志
├── exception.log         # 异常日志（ERROR+）
├── large-2026-07-21.log  # 大内容豁免（按天分割）
└── error.log             # 错误聚合（ERROR+）
```

| 维度 | 规范 |
|:-----|:-----|
| **切分依据** | **按 type 切，禁止按级别切**（见下方说明） |
| 轮转周期 | **按天**（`TimedRotatingFileHandler` 风格） |
| 单文件大小 | **≤ 200MB** 后强制轮转 |
| **免压缩窗口** | `keep_recent_uncompressed_days = 7`（默认 7 天，可配 `0` 表示「轮转后立即压缩」） |
| **压缩时机** | 轮转后 **不立即** gzip；满免压缩窗口（默认 7 天）才压缩（详见 §7.3） |
| 保留 | `app.log` 保留 30 天；`audit.log` 保留 ≥ 180 天；`exception.log` 保留 90 天 |
| 并发写入 | 使用 `ConcurrentRotatingFileHandler` 或同等实现（避免多进程写丢失） |

> **❌ 禁止按级别切文件**（`xxx_info.log` / `xxx_error.log` / `xxx_debug.log`）。
>
> 级别是 §3.1 的 `level` 字段，一次查询即可过滤；切成多文件会把同一条 `request_id` 的 INFO→ERROR 链路**拆散**，直接破坏本规范目标 2「可排查」，且文件与 handler 数量 = 实例数 × 级别数。
>
> **`error.log` 是唯一例外，且它是聚合不是切分**：ERROR+ 在原 `{type}.log` 里保持原位，另复制一份进 `error.log` 供告警脚本 tail —— 两条流都完整。
>
> Flask 实现见 `Flask后端规范.md §6.0`。

### 7.3 轮转 → 清理 → 压缩时序（强制）

> **为什么需要「免压缩窗口」**：排障高发期是「最近 1~7 天」。轮转后立即 gzip 会让 `tail` / `grep` / `zgrep` 都要先解压，严重拖慢排查节奏。**默认 7 天内保留未压缩的 `.log` 文件**，超过 7 天的轮转文件才 gzip。

**时序图**（假设今天 `2026-07-21`，`keep_recent_uncompressed_days = 7`）：

```
时间线           文件状态                                       动作
─────────────────────────────────────────────────────────────────────────────
07-14 00:00      app.log                                         当天写
07-15 00:00      app.log.2026-07-14                             轮转（未压缩）
07-15 ~ 07-21    app.log.2026-07-14                             7 天内：保持 .log，tail/grep 直读
07-22 00:00      凌晨清理任务发现 07-14 的 .log 已满 7 天         → gzip 成 app.log.2026-07-14.gz
                app.log.2026-07-15                              7 天内：保持未压缩
                ……
08-14 00:00      08-14 的 .log 已满 30 天（保留期）               → 删除
```

| 阶段 | 触发时机 | 动作 | 配置项 |
|:-----|:---------|:-----|:-------|
| ① 轮转 | 每 00:00 / 文件满 200MB | 重命名 `app.log` → `app.log.{昨日日期}` | `when='D'` + `maxBytes=200MB` |
| ② 免压缩窗口 | — | 7 天内：保持 `.log` 不压缩 | `keep_recent_uncompressed_days = 7` |
| ③ 过期压缩 | 每天凌晨清理任务 | `gzip` 超过 7 天的 `.log.{date}` → `.log.{date}.gz` | 同上 |
| ④ 过期清理 | 每天凌晨清理任务 | 按保留天数删除（`audit ≥ 180d` / `exception ≥ 90d` / 其他 ≥ 30d） | `BACKUP_DAYS` |

**免压缩窗口默认值约定**：

| 部署场景 | 推荐配置 | 理由 |
|:---------|:---------|:-----|
| 开发/测试 | `0`（轮转即压缩） | 磁盘不在乎，省一次手动清 |
| **生产默认** | **`7`** | 覆盖「最近一周」排障窗口，`tail` 直读免解压 |
| 长期合规项目 | `7` 或更大 | 配合 `audit ≥ 180d`，免压缩文件本身占用不高 |
| 极低存储（小内存机器） | `1` 或 `0` | 仅保留「昨天」，更激进压存储 |

> **手动触发清理**（日常运维）：
> ```bash
> # 立即压缩所有超过 7 天的轮转文件
> python -c "from utils.loggings import compress_old_logs; compress_old_logs(keep_recent_days=7)"
> # 立即清理超过 30 天的 .gz（除 audit/exception）
> python -c "from utils.loggings import purge_old_logs; purge_old_logs()"
> ```
>
> 这两个函数由 `Flask后端规范.md §6.0` 提供实现，禁止业务代码自行写清理脚本。

**反模式**（code-review 必须 Critical）：

| # | 反模式 | 后果 |
|:-:|:-------|:-----|
| 1 | ❌ 业务代码自己写 `gzip` / `rm` 清理脚本 | 与框架清理逻辑双跑，重复压缩或误删 |
| 2 | ❌ 把 `keep_recent_uncompressed_days` 改 `0`（关闭免压缩）但**没测过排障体验** | 排障时手动 `zcat` 一坨，难受 |
| 3 | ❌ 修改免压缩窗口到 `>30`，占用磁盘不告知运维 | OOM 风险 |

### 7.4 控制台 vs 文件的格式差异

| 环境 | 格式 | 颜色 |
|:-----|:-----|:-----|
| 开发（stdout） | `2026-07-21 10:23:45 [INFO] [biz] order.service - 订单创建成功` | 开启（DEBUG=cyan / INFO=green / WARNING=yellow / ERROR=red） |
| 线上（文件） | `{"time":"2026-07-21T10:23:45.123+08:00","level":"INFO",...}` | 无 |

> 格式切换由环境变量控制，**禁止**靠 `if DEBUG` 硬编码在业务代码里。
