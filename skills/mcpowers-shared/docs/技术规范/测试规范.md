# 测试规范

本文档定义 Python 后端项目的测试规范（pytest + Flask 体系）。

> 💡 **适用范围说明**：
> - 通用部分（§1/§4/§7/§9）→ 适用于**所有项目**（测试目的、用例来源、原则、端到端自检）
> - pytest 部分（§2/§3/§5/§6）→ 适用于 **pytest 项目**
> - Flask 部分（§8）→ 适用于 **Flask 后端**
> - 非 Python / 非 pytest 项目请参考对应语言的测试规范

---

## 1. 测试目的

代码完成后，通过测试验证：
1. 代码实现是否符合设计文档
2. 功能是否满足需求文档
3. 边界条件和异常处理是否正确

## 3. 测试文件编写

### 3.1 conftest.py 基础配置

```python
# -*- coding: utf-8 -*-
"""
pytest 配置和公共 fixture

环境切换机制（与 §7.1 mock.ini 配套）：
- 默认加载 config/mock.ini（测试专属配置：mock DB 地址、mock Redis 等）
- 通过 FLASK_ENV 环境变量切换到 config/dev.ini / config/test.ini / config/prod.ini
- mock.ini 中定义的配置项会覆盖 create_app 的默认值，但不会覆盖运行时通过
  app.config['TESTING']=True 等方式设置的运行时开关
"""

import os

import pytest

BASE_DIR = os.path.dirname(os.path.dirname(__file__))


@pytest.fixture(scope='session')
def app():
    """创建测试应用（加载 mock.ini，覆盖测试专属配置）"""
    # 1. 根据 FLASK_ENV 选择配置文件（默认 mock）
    flask_env = os.environ.get('FLASK_ENV', 'mock')
    config_file = os.path.join(BASE_DIR, 'config', f'{flask_env}.ini')

    # 2. 加载配置（文件不存在应报错，让 CI 立即发现配置遗漏）
    from apps import create_app

    app = create_app(protect_swagger=False)
    app.config['TESTING'] = True
    app.config.from_pyfile(config_file, silent=False)  # ← 加载 mock.ini

    return app


@pytest.fixture(scope='function')
def client(app):
    """创建测试客户端（每个测试函数独立，避免状态污染）"""
    return app.test_client()


@pytest.fixture(scope='function', autouse=True)
def db_session(db, app):
    """每个测试函数独立的数据库会话（测试结束自动回滚，避免脏数据）"""
    with app.app_context():
        yield
        # 测试结束显式回滚事务，确保测试数据不留存
        db.session.rollback()
```

### 3.3 测试数据 fixtures

#### 3.3.1 工具选型

| 复杂度 | 推荐方案 | 适用场景 | 示例 |
|:-------|:---------|:---------|:-----|
| 简单 | JSON fixture | 固定数据 / 少量字段 | `tests/fixtures/auth.json` |
| 中等 | Python dict / yaml | 多场景、需动态构造 | `fixtures/user_factory.py` |

### 3.4 测试分层指引（推荐）

> **测试金字塔**：单测 70% / 集成 20% / e2e 10% 的比例原则（出自 Martin Fowler《测试金字塔》）。

| 层级 | 比例 | 验证目标 | 工具 | 执行速度 |
|:-----|:-----|:---------|:-----|:---------|
| 单元测试 | ~70% | 单函数 / 单方法逻辑 | pytest | 🚀 快（< 1s/用例） |
| 集成测试 | ~20% | 多模块协作 / DB / 缓存 / 第三方 mock | pytest + mongomock / fakeredis | ⚡ 中（< 5s/用例） |
| 端到端 | ~10% | 完整业务流 / 集成 | 真实启动服务 + curl | 🐢 慢（< 30s/用例） |

**反模式**：

- ❌ 端到端测试占比 > 30%（慢、脆、维护贵）
- ❌ 集成测试用真实 DB（应该用 mock）
- ❌ 单测写得太厚（实际变集成测试）
- ❌ 跳过集成测试层（直接 e2e 会让失败定位极难）

## 5. 测试执行

```bash

# 生成覆盖率报告
pytest tests/ --cov=. --cov-report=html
```

### 5.1 覆盖率目标（强制）

> **铁律**：覆盖率不是越高越好，而是**核心模块必须达标、新代码必须达标、整体不能下降**。

| 模块类型 | 行覆盖率 | 分支覆盖率 | 说明 |
|:---------|:---------|:-----------|:-----|
| 核心业务（auth / order / pay / 数据写入） | ≥ 80% | ≥ 70% | **改动必须保持不下降**（PR 检查项） |
| 工具层（utils / libs / helpers） | ≥ 70% | ≥ 60% | 新代码必须达标 |
| 新增代码 | ≥ 90% | ≥ 85% | PR 检查项 |
| 整体项目 | ≥ 60% | ≥ 50% | 底线 |

**强制规则**：

- [ ] 覆盖率未达标 → **PR 阻断**（CI 检查 `pytest --cov-fail-under=60`）
- [ ] 核心模块覆盖率**只能上升不能下降**（`pytest --cov=apps.core --cov-fail-under=80`）
- [ ] 新代码必须 ≥ 90%（用 `diff-cover` 工具按 git diff 检查）
- [ ] 例外申请：必须在 PR 描述里写"覆盖率豁免原因 + 后续补齐计划"

**反模式**：

- ❌ 只追求数字（为覆盖率写无意义的断言）
- ❌ 删除难测的代码只为数字好看
- ❌ 不配 diff-cover，只看整体数字（漏掉新代码漏洞）

## 7. 测试原则（强制）

### 7.1 测试环境原则（强制）

| 原则 | 说明 |
|:-----|:-----|
| 独立配置 | Mock 测试使用独立的配置文件（如 `config/mock.ini`），格式与原配置相同，值为 Mock 专属数据；原有三个环境配置（dev/test/prod）不能被修改或覆盖 |
| 环境分离 | Mock 测试环境与生产环境完全隔离，配置相互独立 |
| 数据隔离 | Mock 测试数据仅在测试环境使用，不影响生产数据 |
| 环境配置 | 通过环境变量或配置文件管理不同环境配置 |
| 独立数据库 | Mock 测试使用独立的数据库或数据库实例 |
| 智能配置 | AI 执行测试时，可根据测试需求自动生成合理的 Mock 配置值（如测试数据库、测试账号等） |

**Mock 测试配置文件示例**：
```ini
# config/mock.ini（格式与原配置相同）
[database]
host = 192.168.1.100
name = app_mock

[redis]
host = 192.168.1.101
port = 6379
```

> 💡 conftest.py 如何读取 mock.ini，参见 §3.1 conftest 模板。

#### 7.1.1 测试数据生命周期（v2.0.5 新增，强制）

> **铁律**：测试数据必须**有规划、有标识、有清理**。无标识的测试数据 = 不可清理的脏数据。

测试数据遵循三阶段生命周期：

| 阶段 | 要求 |
|:-----|:-----|
| **测试前** | 规划数据：明确造什么、用什么前缀 / 标签 / 沙箱 |
| **测试中** | 标识数据：使用 `test_` / `tmp_` / `__test__` 前缀，便于批量识别 |
| **测试后** | 清理数据：单测用 conftest rollback，端到端走 §9.6 Step 6 |

**命名约定（强制）**：

| 场景 | 命名规则 | 示例 |
|:-----|:---------|:-----|
| 测试账号 | `test_{module}_{seq}` | `test_user_001`, `test_order_002` |
| 测试数据 | `{prefix}_test_{field}` | `mock_test_email`, `tmp_test_token` |
| 缓存键 | `test:{module}:{key}` / `tmp:{module}:{key}` | `test:user:session:123`, `tmp:order:lock:456` |
| 上传文件 | `temp/test_{uuid}.{ext}` | `temp/test_a1b2.xlsx` |

**禁止**：

- ❌ 用生产账号 / 真实邮箱 / 真实手机号跑测试
- ❌ 测试数据不带前缀（无法批量清理）
- ❌ 测试数据和种子数据混在一起
- ❌ 单测 fixture yield 后不显式 rollback（见 §3.1 模板）

> 💡 **TDD 单测**：用 §3.1 的 `db_session` fixture 即可，yield 后的 rollback 已自动处理。
> 💡 **端到端验证**：跳过此节，看 §9.6 Step 6 的清理要求。

### 7.2 测试执行原则（强制）

| 原则 | 说明 |
|:-----|:-----|
| 独立性 | 每个测试函数独立运行，不依赖其他测试 |
| 可重复 | 测试可以多次运行，结果一致 |
| 自包含 | 测试数据在 fixtures 中管理 |
| 明确断言 | 每个断言都有明确的预期结果 |

### 8.3 测试用例模板

```python
# -*- coding: utf-8 -*-
"""用户 CRUD 接口测试"""

import pytest


class TestUserCreate:
    """POST /user/create"""

    def test_create_success(self, client, auth_headers):
        """正常创建"""
        resp = client.post('/api/user/create',
                           json={'username': 'newuser', 'password': '123456'},
                           headers=auth_headers)
        data = resp.get_json()
        assert resp.status_code == 200
        assert data['code'] == 0
        assert 'id' in data['data']

    def test_create_duplicate_username(self, client, auth_headers):
        """用户名重复应失败"""
        # 第一次创建
        client.post('/api/user/create',
                    json={'username': 'dup', 'password': '123456'},
                    headers=auth_headers)
        # 第二次创建同名
        resp = client.post('/api/user/create',
                           json={'username': 'dup', 'password': '123456'},
                           headers=auth_headers)
        data = resp.get_json()
        assert data['code'] != 0  # 业务错误码


class TestUserList:
    """GET /user/list"""

    def test_list_with_pagination(self, client, auth_headers):
        """分页参数生效"""
        resp = client.get('/api/user/list?page_no=1&page_size=10',
                          headers=auth_headers)
        data = resp.get_json()
        assert data['code'] == 0
        assert 'records' in data['data']
        assert 'total_count' in data['data']

    def test_list_filter_by_status(self, client, auth_headers):
        """按状态筛选"""
        resp = client.get('/api/user/list?status=1', headers=auth_headers)
        data = resp.get_json()
        assert data['code'] == 0
        for record in data['data']['records']:
            assert record['status'] == 1

    def test_list_unauthorized(self, client):
        """无 token 应返回 401"""
        resp = client.get('/api/user/list')
        data = resp.get_json()
        assert data['code'] == 401
```

### 8.4 导入接口测试

```python
# -*- coding: utf-8 -*-
"""导入接口测试"""

import io
from openpyxl import Workbook


def make_test_xlsx(rows: list[list]) -> bytes:
    """构造测试用 .xlsx 文件"""
    wb = Workbook()
    ws = wb.active
    for row in rows:
        ws.append(row)
    output = io.BytesIO()
    wb.save(output)
    output.seek(0)
    return output.getvalue()


def test_import_success(client, auth_headers):
    """正常导入"""
    xlsx_bytes = make_test_xlsx([
        ['用户名', '密码', '状态'],
        ['user1', 'pwd1', '启用'],
        ['user2', 'pwd2', '禁用'],
    ])
    resp = client.post(
        '/api/user/import',
        data={'file': (io.BytesIO(xlsx_bytes), 'test.xlsx')},
        content_type='multipart/form-data',
        headers=auth_headers,
    )
    data = resp.get_json()
    assert data['code'] == 0
    assert data['data']['total'] == 2
    assert data['data']['success'] == 2
    assert data['data']['fail'] == 0
```

#### 8.6.1 覆盖要求

| 要求 | 说明 |

#### 8.6.2 安全要求

#### 8.6.3 隔离要求

## 9. 端到端自检 6 步（强制）

> **适用范围**：所有 bug 修复（`mcpowers-bugfix` Step 5）和新功能交付（`mcpowers-feat` Step 8）。
>
> **铁律**：单测全绿 ≠ 系统正常。集成层（接口契约、配置加载、依赖服务、数据库迁移）的故障单元测试看不见，必须重启服务跑一遍主链路才能发现。

### 9.1 为什么必须有这 6 步

| 误区 | 真实情况 |
|:-----|:---------|
| "单测都过了，应该没问题" | 单测覆盖逻辑，不覆盖集成 |
| "重构完本地跑通就行" | 本地环境 ≠ staging/prod 配置 |
| "怕影响线上，不敢重启验证" | 不验证 = 带病上线，影响更大 |

### 9.2 六步清单（Step 1-6）

#### Step 1：重启服务

| 项 | 要求 |
|:----|:-----|
| 环境 | dev 或 staging（**绝不能在生产直接验证**） |
| 方式 | 实际启动进程 / 容器，不是 `pytest` |
| 目标 | 验证进程能正常起来、无启动期 ERROR |
| 失败信号 | 启动失败、端口冲突、数据库连接超时、迁移报错 |

#### Step 2：主链路 curl

| 项 | 要求 |
|:----|:-----|
| 数量 | 至少 1 个 happy path |
| 方式 | `curl` / `httpie` / Postman / 自动化脚本均可 |
| 验证点 | HTTP 状态码 200 + 业务返回码正确 + 关键字段存在 |
| 失败信号 | 4xx/5xx、业务码异常、关键字段缺失、超时 |

**示例**：

```bash
# 主链路 happy path
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"test","password":"test123"}'

# 期望：HTTP 200 + {"code":0,"data":{"token":"xxx"}}
```

#### Step 3：日志无 ERROR

| 项 | 要求 |
|:----|:-----|
| 时段 | 服务启动后 5 分钟内 |
| 检查项 | 无 ERROR 级别日志；WARN 数量应在合理范围（≤ 5 条） |
| 工具 | `tail -f` / `grep ERROR` / 日志平台检索 |
| 失败信号 | 出现未预期的 ERROR、重复 WARN、堆栈异常 |

#### Step 4：回归点走过

| 项 | 要求 |
|:----|:-----|
| 范围 | 本次改动波及的所有上下游 |
| 方式 | 对每个回归点跑一次 happy path |
| 文档 | 在 PR 描述里列出回归验证清单 |
| 失败信号 | 回归点接口 / 功能异常 |

**回归点定位方法**：

1. `git diff --name-only HEAD~1` → 列出变更文件
2. 对每个变更文件，找到调用方（import / 调用接口）
3. 对每个调用方，挑 1 个 happy path 验证

#### Step 5：环境就绪

| 项 | 要求 |
|:----|:-----|
| 配置 | 新增配置项已写入对应环境的配置文件 |
| 数据库 | 迁移脚本已执行，schema 已更新 |
| 外部依赖 | 第三方接口 / Redis / MQ 已就绪 |
| 缓存 | 必要时清除旧缓存，避免脏数据 |
| 失败信号 | 配置缺失、迁移未执行、依赖不通 |

#### Step 6：清理测试数据（强制）— 不可跳过

> **铁律**：端到端验证通过了 ≠ 任务完成。验证过程中产生的数据库记录、缓存键值、上传文件等都是**脏数据**，必须清理。

**为什么必须有这一步**：

| 误区 | 真实情况 |
|:-----|:---------|
| "测完就完了" | 数据库残留 test_admin 用户，下次验证可能冲突 |
| "反正只有我开发" | 单机本地库也会污染；多人协作更严重 |
| "生产环境不会用到" | dev/staging 数据库残留会让 e2e 误判 |

**清理范围**（4 类）：

| 类型 | 识别方式 | 清理方式 |
|:-----|:---------|:---------|
| 数据库记录 | `test_` / `tmp_` / `__test__` 前缀 | SQL / ORM 批量删除 |
| 缓存键值 | `test:*` / `tmp:*` 前缀 | Redis DEL / 模式删除 |
| 上传文件 | `temp/test_*` / `uploads/test_*` 路径 | OS 删除 + 第三方存储 SDK |
| 第三方副作用 | mock server / 沙箱环境 | 重置 mock 状态 / 沙箱刷新 |

**清理方式**（按项目能力选）：

| 方式 | 适用场景 | 实现示例 |
|:-----|:---------|:---------|
| **手动 SQL** | 小项目 / 临时数据 | `DELETE FROM users WHERE username LIKE 'test_%';` |
| **清理脚本** | 中型项目 | `scripts/cleanup_test_data.sh` 集中处理 |
| **conftest fixture** | pytest 单测 | 已有 yield + rollback 模式（见 §3.1） |
| **CI teardown** | 自动化项目 | CI pipeline 增加 cleanup job |

**强制要求**：

- [ ] Step 1-5 **全部通过**后，**才能**进入 Step 6
- [ ] 清理完成后，**再次验证主链路**确认数据真的清掉
- [ ] 清理动作**记录到 commit message** 或 `docs/细节记录/`
- [ ] 命名遵循 §7.1.1 的 `test_` / `tmp_` 前缀约定

**反模式**：

- ❌ 端到端通过后直接 commit，不清理
- ❌ "反正下次还要用，懒得清"（污染会累积）
- ❌ 在生产数据库上跑端到端测试
- ❌ 手动 SQL 删一半留一半

#### 9.2.1 失败回滚指引（强制）

> **铁律**：Step 1-5 任一步失败 → 立即停止，**不要**进入 Step 6，**不要** commit，**不要** push。端到端通过 ≠ 任务完成；但端到端失败 = 任务未完成。

**失败判定矩阵**：

| 失败步骤 | 严重度 | 是否继续 | 是否 commit | 必须动作 |
|:---------|:-------|:---------|:------------|:---------|
| Step 1（重启） | 🔴 致命 | 否 | 否 | 立即停止 + 回滚代码 |
| Step 2（主链路） | 🔴 致命 | 否 | 否 | 立即停止 + 不 commit |
| Step 3（日志 ERROR） | 🟡 警告 | 排查后可继续 | 标注 `[KNOWN-WARN]` 后可 commit | 必须注释原因 |
| Step 4（回归点） | 🔴 致命 | 否 | 否 | 立即停止 + 不 commit |
| Step 5（环境就绪） | 🔴 致命 | 否 | 否 | 立即停止 + 不 commit |

**回滚 5 步（强制）**：

1. **停止验证**：不再继续后续步骤；不要尝试"再跑一次看看"
2. **回滚代码**：`git stash` 或 `git reset --hard HEAD~1`（已 commit 但未 push 的回滚）
3. **记录失败**：commit message 末尾追加 `[E2E-FAIL: Step X - 原因简述]`
4. **通知用户**：报告失败步骤 + 失败原因 + 已回滚动作
5. **生产规避**：绝不在生产数据库跑端到端；如必须，使用影子流量 / 灰度发布

**反模式**：

- ❌ Step 2 失败后"反正本地能跑，先 commit 吧"（commit 错误代码）
- ❌ "日志有个 ERROR 没事，可能是别的模块"（不排查就继续）
- ❌ 不回滚代码，让失败的代码留在工作区等下次 commit
- ❌ 在生产数据库上跑端到端测试（铁律违反）
- ❌ Step 3 WARN 不注释原因就 commit（污染主分支）

### 9.3 与单元测试的关系

```
单元测试 ──→ 验证逻辑正确性
端到端验证 ──→ 验证集成正确性
两者互补，缺一不可
```

| 阶段 | 验证目标 | 工具 | 通过标准 |
|:-----|:---------|:-----|:---------|
| 单元测试 | 单函数 / 单接口逻辑 | pytest | 全绿 |
| 端到端验证 | 完整业务流 / 集成 | curl + 日志 + 眼 | 6 步全过 |

### 9.4 常见反模式

- ❌ 单测全绿就提交
- ❌ "本地能跑起来就行"（本地 ≠ staging）
- ❌ 只验证主流程，不验证回归点
- ❌ 跳过环境检查（"配置我记得写了"）
- ❌ 在生产环境直接验证（高风险）
- ❌ **端到端验证后不清理测试数据**（数据库残留污染下次验证）

### 9.5 长期演进建议（按需）

| 团队规模 / 业务阶段 | 推荐做法 |
|:--------------------|:---------|
| 1-2 人 / 早期项目 | 手动执行 6 步 |
| 3-10 人 / 多模块 | 写 `scripts/smoke.sh` 自动化 curl |
| 10+ 人 / 高 SLA | 引入契约测试（Pact）+ CI 自动 e2e + 蓝绿部署 |
