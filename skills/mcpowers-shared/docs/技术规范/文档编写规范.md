# 文档编写规范

本文档定义文档编写标准，适用于所有项目。

---

## 1. 章节编号格式（强制）

**所有文档的章节标题必须使用阿拉伯数字编号**，禁止使用中文数字：

| 错误 | 正确 |
|:-----|:-----|
| `## 一、xxx` | `## 1. xxx` |
| `## 十、xxx` | `## 10. xxx` |
| `## 第1章` | `## 1. xxx` |

**格式要求**：
- 一级标题：`## 1.`
- 二级标题：`### 1.1`
- 阿拉伯数字 + 半角点号 + 空格

**示例**：
```markdown
## 1. 项目概述

## 2. 功能需求

### 2.1 用户管理
```

---

## 2. 规范文档标题标注（强制）

**规范文档**（docs/技术规范/ 下的所有文档）的章节标题标注规则：

### 2.1 通用规范文档

| 章节类型 | 示例 | 是否标注强制 |
|:---------|:-----|:-------------|
| 描述性章节 | `## 1. 概述`、`### 1.1 适用范围` | ❌ 不标注 |
| 规范性质章节 | `## 2. 命名规范（强制）`、`### 3.1 禁止行为（强制）` | ✅ 标注 |

> **判断标准**：章节内容是否包含"必须"、"禁止"、"强制要求"等规范性质的要求

适用文档：`docs/技术规范/` 下除技术锁定类规范外的所有文档。

### 2.2 技术锁定类规范

以特定技术命名的规范文档（如 Vue前端规范.md、Flask后端规范.md、爬虫规范.md 等），因其内容本身就是技术要求，**所有章节均可标注强制**，无需逐章判断。

**非规范文档**（需求文档、设计文档等）**不需要标注强制**。

---

## 3. 章节组织原则（强制）

**相同类型的规范必须放在同一章节，禁止分散**：

| 错误做法 | 正确做法 |
|:---------|:---------|
| 路径规范放在第3章，下拉响应格式放在第9章 | 路径规范和下拉响应格式都放在第3章 |
| 同一类接口的规范分散在多个章节 | 同一类接口的规范集中在一个章节 |
| 相关字段说明分散在不同章节 | 相关字段说明集中在同一章节 |

**章节编号必须连续，不得跳跃**：
- ❌ 3.2 → 3.4（缺少3.3）
- ✅ 3.1 → 3.2 → 3.3

---

## 4. 不冗余原则（强制）

**禁止在多个文档中重复定义相同内容**。每个知识点只在一个地方定义，其他地方通过引用链接。

| 错误做法 | 正确做法 |
|:---------|:---------|
| 在多个文档中写相同的概念定义 | 概念只定义一次，其他地方引用 |
| 在 AI操作规范 中写详细的技术细节 | 详细内容写在技术规范中，AI操作规范只引用 |
| 在多个地方复制粘贴相同的说明 | 写一份，其他地方引用 |

---

## 5. 不重复定义原则（强制）

**同一个概念、规则、流程只定义一次**，无论是在单个文档内部还是多个文档之间。

**单个文档内部**：
- 同一概念只在文档的一处定义
- 相似内容合并为一处，避免分散描述
- 避免"在第3章讲过，第5章又讲一遍"

**多个文档之间**：
- 详细内容只在专属文档中定义，其他文档只引用
- 避免在多个文档中复制相同的说明

---

## 6. 内容完整原则（强制）

**每个文档的内容必须是完整的**，避免：

- 文档内容残缺，需要参照其他文档才能理解
- 关键信息缺失，需要猜测或询问
- 示例不完整，无法直接使用

---

## 7. 适用范围标注规范（强制）

**同一文档包含多种技术时，必须在章节标题标注适用范围**。

| 标注方式 | 示例 |
|:---------|:-----|
| 技术无关 | `## 2. ORM框架（MySQL/SQLAlchemy）` |
| 纯通用 | `## 5. 反向代理（通用）` |
| 多技术并列 | `## 3. 缓存（Redis/Memcached）` |

**规则**：
- 章节内容仅涉及单一技术 → 在标题标注该技术
- 章节内容通用 → 在标题标注"（通用）"
- 章节内容涉及多种技术 → 在标题标注所有适用技术

**示例**：
```markdown
## 2. 数据库规范

### 2.1 ORM框架（MySQL/SQLAlchemy）
### 2.2 MongoDB（规划中）

## 3. 缓存规范

### 3.1 Redis（通用）
### 3.2 Memcached（规划中）

## 4. 部署规范

### 4.1 Docker（通用）
### 4.2 Kubernetes（规划中）
### 4.3 Python镜像（Python）
```

**好处**：
- 用户一看标题就知道内容是否适用
- 避免通用规范被误认为适用于所有技术
- 新增技术时只需在标题添加，无需重构文档

---

## 8. 代码示例使用规范（强制）

**通用规范文档**：不应包含代码实现，仅描述规范要求

| 规范类型 | 代码示例要求 | 说明 |
|:---------|:------------|:-----|
| 通用规范 | ✅ 仅作参考 | 代码示例仅辅助理解，不是完整实现 |
| 技术锁定规范 | ✅ 必须 | 可包含该技术的完整代码实现 |

**通用规范示例**（代码规范.md、数据库规范.md 等）：
- ✅ 可以：描述性规范、原则、要求
- ✅ 可以：多语言对比示例（如 Python/JavaScript）
- ❌ 不应：完整的代码实现（会降低通用性）

**技术锁定规范示例**（Flask后端规范.md、Vue前端规范.md 等）：
- ✅ 必须：包含该技术的完整代码实现
- ✅ 必须：包含该技术的配置示例

---

## 9. 终态交付原则（强制）

**文档是当前状态的快照，不是演进过程的日志。**

### 9.1 只写当前状态

文档正文**只描述改完之后的样子**，禁止保留任何"曾经是什么"的痕迹。历史由 git 保存，不需要在正文里复述。

| 错误做法 | 正确做法 |
|:---------|:---------|
| `## 变更历史` 章节列出每次修改 | 删除该章节，历史查 `git log` |
| `订单状态用 code（原来用 id）` | `订单状态用 code` |
| `~~方案 A：轮询~~ 方案 B：WebSocket` | `方案：WebSocket` |
| `已废弃：旧的登录接口 /api/login` | 直接删除该段 |
| `v1 时是同步调用，v2 改成异步` | `调用方式：异步` |
| 保留旧配置示例并注明"不再使用" | 只保留当前配置示例 |

**修订已有文档时**：直接改写原文，**不得**用"新增说明"的方式在旧内容旁边追加，导致新旧并存。

### 9.2 参考资料不进正文

阅读参考文档、参考项目、示例代码，目的是**学习后用自己的话重新组织**，产出物必须是独立成立的原创表达。

| 错误做法 | 正确做法 |
|:---------|:---------|
| `参考《xxx 规范》第 3 章，字段命名用小写下划线` | `字段命名用小写下划线` |
| `根据提供的资料，部署分三步` | `部署分三步` |
| `如上述参考文档所述` | 直接陈述结论 |
| `本文档基于 xxx 项目的实现整理` | 删除该句 |
| 照搬参考文档的章节结构和措辞 | 按当前项目实际重新组织 |

**确需溯源时**：只在文末「附录 · 参考来源」列一次链接，**正文任何位置不得出现来源指代**。

### 9.3 痕迹词黑名单

产出文档后自查，正文命中以下词即需清理：

| 类型 | 痕迹词 |
|:-----|:-------|
| 历史演进 | 原来是、原为、曾经、已废弃、不再使用、旧版本、历史遗留、变更历史、更新记录、改动说明 |
| 版本对照 | v1 时、旧方案、迁移前、由 xxx 改为、现已改成 |
| 参考来源 | 参考 xxx 文档/规范、根据提供的资料、基于 xxx 项目、如上述参考、来源于 xxx、借鉴自 |
| **画蛇添足字眼（v4.0.2+ 通则化）** | **参考 / 参见 / 详见 / 引用 / 参照 / 引自 / 根据规范 / 按照规范 / 按规范要求 / 遵守规范 / 按规范**（独立出现也算画蛇添足，不限于"在某文档后"）+ 英文 **according to / refer to / referring to / as described in / as specified in / see also / conform to / conforms to / based on / defined in / outlined in**（22 个单字眼粒度，详见 §9.5 场景化规则）|

> 判断标准：**删掉这句话，读者对"当前该怎么做"的理解是否受损**。不受损即为痕迹，必须删。
>
> 注意区分：描述**时序**的"之前/以后"（如"调用之前必须初始化"）是正常表达，不是痕迹；只有描述**版本变迁**的才是。

### 9.4 例外白名单

以下位置**允许**出现历史信息，不属于痕迹：

| 位置 | 允许内容 |
|:-----|:---------|
| `CHANGELOG.md` | 完整变更日志（这是它的职责） |
| README「最近变更」 | 最近 3-5 条，超出删最旧 |
| 复盘类文档（如 `docs/历史教训.md`） | 历史决策与教训（这是它的主题） |
| API 契约中的 `Deprecation` 标记 | 接口的产品语义，不是编写痕迹 |
| 迁移指南类文档 | 新旧对照是文档目的本身 |

> 除以上五类，**任何文档不得记录变更历史**。

---

### 9.5 画蛇添足字眼场景化决策模型（v4.0.2+ 用户决策 C·新增）

**核心原则**：AI 写任何文档时，禁用字眼（22 个）出现必须跑 3 问决策——**不靠记忆、不一刀切**。

#### 9.5.1 3 类文档场景判定

| 类型 | 典型文档 | 字眼规则 | 决策依据 |
|:-----|:--------|:--------|:--------|
| **输出型** | README / 用户手册 / 技术规范正文 / API 接口 description / 任何内容型文档 | **完全禁止** | 删掉字眼不影响读者理解——读者无需"再去查其他文档" |
| **参考型** | mcpowers-spec-index / API 契约字典 / 技术规范目录 / 迁移指南 / 技能索引 | **允许且必要** | 不指向其他文档 = 文档无法用——索引本职就是引用 |
| **历史型** | CHANGELOG / 历史教训 / Deprecation 标记 / README「最近变更」段 | **允许**（§9.4 已白名单）| 文档主题本身要求 |

#### 9.5.2 22 个禁用字眼清单（中文 11 + 英文 11）

**中文 11 个**：参考 / 参见 / 详见 / 引用 / 参照 / 引自 / 根据规范 / 按照规范 / 按规范要求 / 遵守规范 / 按规范

**英文 11 个**：according to / refer to / referring to / as described in / as specified in / see also / conform to / conforms to / based on / defined in / outlined in

> 单一权威源：`skills/mcpowers-shared/docs/_assets/_forbidden_ref_words.txt`（v4.0.1+ 接口零引用与 v4.0.2+ 文档零引用三处脚本共用）

#### 9.5.3 3 问决策流程图（AI 写文档时必跑）

```
Q1: 这段文字是给谁看的？
    ├─ 对接方/终端用户 → 输出型
    ├─ 自己查的索引  → 参考型
    └─ 追溯历史      → 历史型

Q2: 删掉字眼后意思会变吗？
    ├─ 不变 → 画蛇添足 → 删
    └─ 变   → 必要引用 → 保留

Q3: 类型 + Q2 联合判定
    ├─ 输出型 + 不变 → 完全禁止 → 删
    ├─ 输出型 + 变   → 改写（不引用其他文档，直接说明）
    ├─ 参考型 + 不变 → 完全禁止 → 删
    ├─ 参考型 + 变   → 允许且必要 → 保留
    └─ 历史型       → 允许（§9.4 已白名单）
```

#### 9.5.4 反向合规改写示范 4 条

| 错误做法 | 合规改写 |
|:---------|:---------|
| ❌「详见 §3.1 token 管理规范」| ✅「token 用 Redis 反向键 Set 管理，允许多端登录」|
| ❌「本接口参考 RBAC 模型实现」| ✅「本接口基于角色鉴权，权限粒度到接口级」|
| ❌「如上所述」/「如上述参考文档所述」| ✅ 直接陈述结论 |
| ❌「see also OpenAPI 3.0 spec」| ✅ 直接展开说明字段 |

#### 9.5.5 跨场景落地表

| 文档类型 | 字眼规则 | 软门禁 hook | 审查 R16 |
|:---------|:--------|:----------|:--------|
| **输出型** .md（README/规范/用户手册）| ❌ 完全禁止 | ✅ 命中提示 | ✅ R16 阻塞 |
| **参考型** .md（mcpowers-spec-index/API 契约/迁移指南）| ✅ 允许且必要 | ⏭ 路径白名单跳过 | ⏭ 路径白名单跳过 |
| **历史型** .md（CHANGELOG/历史教训/Deprecation）| ✅ 允许 | ⏭ 路径白名单跳过 | ⏭ 路径白名单跳过 |
| **接口描述** docstring | ❌ 完全禁止（v4.0.1 接口零引用）| ✅ v4.0.1 写时硬门禁 | ✅ R15 |

#### 9.5.6 与 v4.0.1 接口零引用的关系

- **v4.0.1 接口零引用** = §9.5 输出型在 API 接口描述这一子集的最严格实施（写时硬门禁 + 导出时硬门禁）
- **v4.0.2 文档零引用** = §9.5 通用化推广（覆盖所有输出型文档，软门禁为主）
- **两者共用 22 字眼清单**（共享常量 `_forbidden_ref_words.txt`），避免漂移

## 10. 编写检查清单（强制）

编写新文档或更新文档时，对照检查：

- [ ] 是否有内容在其他文档中重复定义？
- [ ] 是否有内容应该引用而非复制？
- [ ] 文档内容是否完整，可以独立使用？
- [ ] 示例是否完整可运行？
- [ ] 引用路径是否正确？
- [ ] 同一文档内多技术是否已标注适用范围？
- [ ] 通用规范是否只包含代码示例而非完整实现？
- [ ] 正文是否残留历史演进痕迹？（§9.3 黑名单逐词自查）
- [ ] 正文是否残留参考来源指代？（读参考 = 学习，不是转述）
- [ ] **§9.5 决策 3 问**（v4.0.2+ 新增）：① 这段文字是给谁看的？② 删掉「参考 / 参见 / 详见 / 引用 / 参照 / 引自」等 22 个字眼后意思会变吗？③ 类型 + Q2 联合判定——输出型禁止 / 参考型允许且必要 / 历史型允许
