# 代码规范

本文档定义高质量代码的编写规范。**当前以 Flask 后端（Python）+ Vue 前端为参考栈**；其他技术栈（Node/Go/Django/Spring 等）可参考本规范的通用原则，或生成对应技术栈的专属规范。

> **核心原则**：写出可维护、可扩展、可测试的高质量代码
>
> **栈无关原则**：SOLID/KISS/DRY/YAGNI 等原则适用于任何编程语言；具体代码示例以 Flask 后端 / Vue 前端为主
>
> **本技能禁止使用环境变量（v2.25.0+ 最高铁律）**：见下方「## 最高铁律」段，**所有栈 / 仓库所有 .py .sh .js .ts 源文件统一适用**。

## 最高铁律 · 本技能禁止使用环境变量（强制 · 全栈适用 · v2.25.0+）

> **本规则是 mcpowers 仓库的全局最高规则之一**，适用于仓库所有 .py / .sh / .js / .ts 源文件，以及应用本规范的所有项目代码。

### 禁行写法（强制）

| 语言 | 禁行写法 | 替代方案 |
|:-----|:--------|:--------|
| **Python** | `import os` 后调用 `os.environ.*` / `os.getenv(...)`；`from os import environ` / `from os import getenv`；`os.environb` 任何属性 | 配置文件 + 单例加载器（Flask `Config.get()` / Node `config.json` / 爬虫 `config.yaml`） |
| **Shell / Bash** | `echo "$XXX"` / `${XXX}` 从外部环境读取（依赖外部 `export XXX` / 容器环境） | bash 内部变量 `XXX=value`、`$1` 位置参数、`${XXX:-default}` 默认值写法（这些都不是从进程环境读取） |
| **JavaScript / TypeScript** | `process.env.XXX` / `dotenv.config()` / `import.meta.env.*`（运行时） | 配置文件 + 构建时注入（`vite`/`webpack` 的 `define` / `import.meta.env` 仅构建时）+ `process.argv` |

### 正例（任何栈通用）

- **配置文件 + 加载器**（栈规范各自定义加载方式）
- **命令行参数**（`sys.argv` / `argparse` / `clap` / `commander` / `$1` 位置参数）
- **框架 / 语言硬编码默认值**（如 OS 路径探测用 `pathlib.Path.home()` + 已知路径列表，不用 `os.environ.get("PROGRAMFILES")`）

### 唯一允许的两处例外

1. **Claude Code 钩子配置（`hooks.json`）中的 `${CLAUDE_PLUGIN_ROOT}` 占位符** —— 这是 Claude Code 框架在调用 hook 命令前注入的占位符，**不是钩子脚本运行时读 `os.environ`**
2. **Docker Compose YAML 的 `environment:` 字段** —— 这是容器编排层注入到容器进程环境，**不进入 mcpowers 代码运行时**

### 栈级落地（各栈规范承担）

- **Flask 后端**：见 `Flask后端规范.md §4.1`（`Config` 单例统一入口，禁 `os.environ.*`）
- **Vue 前端**：见 `Vue前端规范.md`（`process.env` 仅构建时通过 `import.meta.env` 注入，**运行时禁止 `process.env`**）
- **爬虫**：见 `爬虫工具与抓包规范.md`（`config.yaml` + 启动器传参）
- **CI / 脚本**：仓库自身的 `.py` / `.sh` 文件统一约束；OS 探测（Windows 浏览器路径、Linux PATH）走硬编码 + `shutil.which()` 组合

### 反例（Python）

```python
# ❌ 禁止（fallback 掩盖配置缺失 + 跳过 ini 审计 + 类型解析不稳）
DB_HOST  = os.environ.get('DB_HOST', '127.0.0.1')
PORT     = int(os.getenv('PORT', '8000'))
SECRET   = os.environ['SECRET_KEY']
PROGRAMFILES = os.environ.get('PROGRAMFILES', 'C:/Program Files')  # OS 探测也不允许

# ✅ 正确（缺失即启动失败 + 单例 + 类型校验）
DB_HOST  = config.get('admin_mysql', 'host')      # 缺失抛 NoSectionError
PORT     = config.getint('app', 'port')            # 类型由 Config 校验
SECRET   = config.get('app', 'secret_key')        # 敏感字段同样走 ini
PROGRAMFILES = str(pathlib.Path('C:/Program Files'))  # 硬编码 + pathlib
```

## 最高铁律 · mcpowers 注入路径稳定性（强制 · 全栈适用 · v2.27.1+）

### `${CLAUDE_PLUGIN_ROOT}` 是什么（必读 · AI 自查）

`${CLAUDE_PLUGIN_ROOT}` 是 **Claude Code 框架在调用工具前自动展开的字符串占位符**，**不是 shell / Python 进程环境变量**：

- AI 在 **Bash / Read / Edit / Glob 工具的输入字符串里**写 `${CLAUDE_PLUGIN_ROOT}/...`，框架在调用前替换成当前激活的插件根目录
- AI 在 **.py / .sh / .js / .ts 源文件运行时读不到**这个值（运行时不会有 `os.environ['CLAUDE_PLUGIN_ROOT']`），所以源文件**禁止**用 `${CLAUDE_PLUGIN_ROOT}` 做运行时逻辑——它只是 hook 命令前的字符串替换层
- 实测自检：`bash -c 'echo "[$CLAUDE_PLUGIN_ROOT]"'` 在普通 shell session 返回 `[]`（空字符串）——印证它**不**进 shell 进程环境

### 标准 Claude Code 插件机制安装（主路径）

绝大多数用户场景：通过 `/plugin marketplace add <GitHub URL 或本地路径>` + `/plugin install mcpowers@mcpowers` 安装，后续通过 `/plugin` → `Update now` 更新。

| 目录 | 物理路径 | 角色 |
|:-----|:---------|:-----|
| **运行时根目录**（`${CLAUDE_PLUGIN_ROOT}` 解析为这里） | `~/.claude/plugins/cache/mcpowers/mcpowers/{version}/`（**带版本号**，如 `2.27.0/`)） | 激活版本的**独立物理副本**——AI 实际 Read / Edit / Bash / hook 执行的位置；当前激活版本以该目录下的 `.in_use/<pid>` 标记为准 |
| marketplace **源**目录 | `~/.claude/plugins/marketplaces/mcpowers/`（**不带版本号**） | `marketplace add` 时的源；与 cache 副本**inode 不同**，是两份独立的文件树 |
| cache 历史版本 | `~/.claude/plugins/cache/mcpowers/mcpowers/<多个旧 version>/` | 升级前的旧版本残留，回滚或比对时用 |

**关键事实**：
- `marketplaces/mcpowers/`（不带版本号）**只是 marketplace add 源**——AI 实际读到的不是这里
- `${CLAUDE_PLUGIN_ROOT}` **始终**解析为 `cache/mcpowers/mcpowers/{version}/`（**带版本号**）——upgrade / install / reload 插件机制统一走 cache 路径
- "${version}" 升级时变化，`{version}/` 整个目录会被新版本替换，旧版本保留在历史版本目录

> **AI 自查当前激活版本**：`ls ~/.claude/plugins/cache/mcpowers/mcpowers/` 看哪个 `{version}/.in_use/<pid>` 最新创建——这就是当前 `${CLAUDE_PLUGIN_ROOT}` 的物理路径。**禁止**硬猜 `2.26.2` 或 `2.27.0`，**永远**通过 `${CLAUDE_PLUGIN_ROOT}/...` 让框架替换。

### 本地开发模式（开发者偏好 · 非默认）

开发者用 `/plugin marketplace add <本地仓库路径>`（如 `/d/document/my/workspace/mcpowers`）+ `/plugin install` + `/reload-plugins` 时，**实际激活运行时仍是 cache path**，**不**会让 `${CLAUDE_PLUGIN_ROOT}` 变成不带版本号的 `marketplaces/mcpowers/`。这是 Claude Code 插件机制的统一行为——`install` 始终先把内容复制到 `cache/.../{version}/` 再激活。

> 本地路径只是 marketplace add 源——一旦 `install` 完成或 reload 完成，runtime 解析的就是 cache 路径。

### 禁行字面值（强制）

| 禁行字面值 | 原因 | 替代写法 |
|:-----------|:-----|:---------|
| `~/.claude/plugins/cache/mcpowers/mcpowers/{version}/...`（直接硬编码） | 升级时版本号变化，旧路径失效 | 抽象规范路径 `mcpowers-shared/docs/技术规范/Flask后端规范.md`（AI 按需 Read，不复制不软链） |
| `~/.claude/plugins/marketplaces/mcpowers/...`（直接硬编码当作运行时） | 只是 marketplace add 源，不是 AI runtime 解析位置 | 同上 |
| `~/.claude/skills/mcpowers-shared/...` | v2.0 之前旧安装机制，v2.0+ 已废弃 | 同上 |
| 自定义占位符如 `<mcpowers>`、`{plugin_root}` | 无清晰定义，AI 无法解析 | `${CLAUDE_PLUGIN_ROOT}`（框架自动展开） |

### 配套铁律

- **不**提议"软链 `mcpowers-shared/docs/` 到项目 `docs/`"——软链指向带版本号 cache 路径，升级即失效
- **不**让用户"装到 `~/.claude/skills/`"——v2.0+ 唯一安装机制是 Claude Code 插件市场（`/plugin marketplace add ...`）
- AI **写代码 / 写文档 / 写注释**时**只写抽象路径**（如 `mcpowers-shared/docs/技术规范/Flask后端规范.md §6.3`）——**不**写 `~/.claude/...`
- AI **在 Bash / Read / Edit / Glob 工具输入字符串里**用 `${CLAUDE_PLUGIN_ROOT}/skills/mcpowers-shared/...` 让框架替换——**不**直接 `~/.claude/...`
- **不**在 .py / .sh / .js / .ts 源文件运行时读 `CLAUDE_PLUGIN_ROOT`（**不是环境变量**，运行时不存在）——这与本规范「本技能禁止使用环境变量」铁律同源

### 注入物版本号写死禁令（v2.27.3+ · 全栈适用）

1. **禁止硬编码 mcpowers 版本号**——任何位置都不能写 `v{major}.{minor}.{patch}` / `{version}/` / `cache/mcpowers/mcpowers/{version}/` 这类带具体版本号的字面值（`{version}` 占位符用于规则说明本身则允许）。版本号是 mcpowers 仓库内部演进元数据，**不**属于被注入的内容。
2. **必须描述为「对应 mcpowers 最新版本的纪律」**——后续访问由 Claude Code 框架通过 `${CLAUDE_PLUGIN_ROOT}/...` 自动展开为最新版本对应的物理路径；读者**永远**读到最新版本，无须关心版本号。
3. **禁止以"注入时刻的版本"或"当前版本"作为说明基准**——`/plugin` Update now 之后，旧版本号就是错的；唯有"最新版本"在跨升级周期里始终正确。
4. **版本演进历史只**允许出现在 mcpowers 仓库自己的 `.claude-plugin/*.json`、`CHANGELOG.md`、`docs/历史教训.md`——这三处是 mcpowers 仓库持有，**不**外流到用户项目。
5. **物理兜底**：mcpowers 仓库内任何向用户项目注入内容的脚本（cp / Write）都必须以本规范为唯一来源；模板内若发现硬编码版本号视为 bug，按本铁律修复。

### 运行时版本访问白名单（v2.27.4+ · 全栈适用）

上节禁的是**注入物**（cp / Write 进用户项目的内容）。本节允许的是**AI 运行时访问**——AI 在 Claude Code 工具调用层发现并读取历史版本目录，是 forensic 调试、跨项目兼容、升级迁移的合法场景，**不**与上节冲突。

AI 在会话里**允许**通过以下 3 种方式访问 mcpowers 历史版本规范（运行时侦查，**不**是预先硬编码）：

1. **AI 主动侦查历史**：用户问"我代码当时合规吗？"或"v2.27.3 那版的规范是什么样？" → AI `ls ~/.claude/plugins/cache/mcpowers/mcpowers/` 发现用户已装的旧版本 → `Read ~/.claude/plugins/cache/mcpowers/mcpowers/<version>/skills/mcpowers-shared/docs/...` 读该版本规范（version 是**运行时发现**的，**不**是预先硬编码在文档里的）
2. **项目级冻结标记**：项目根存在 `.mcpowers-version: v{major}.{minor}.{patch}` 文件时，AI 默认读该版本目录而非 `${CLAUDE_PLUGIN_ROOT}`（最新）；典型场景：用户想保持代码与某版规范的契约冻结、不被升级自动波及
3. **用户显式指定**：用户说"按 v{major}.{minor}.{patch} 规范写" → AI 按显式指令读历史版本目录

**边界判定**（关键）：

| 场景 | 是否允许 | 理由 |
|:----|:--------|:-----|
| 注入物（CLAUDE.md 段 / 模板 / 脚本）写死版本号 | ❌ 禁止 | 跨升级会失效 |
| 注入物写"对应 mcpowers 最新版本" | ✅ 允许 | 由 `${CLAUDE_PLUGIN_ROOT}` 动态解析 |
| 注入物写 `${CLAUDE_PLUGIN_ROOT}/skills/mcpowers-shared/...` | ✅ 允许 | 框架字符串替换 |
| AI 运行时 `ls cache/...` 发现旧版本 + `Read` 读 | ✅ 允许 | 运行时侦查 |
| 项目根 `.mcpowers-version: v2.27.3` 标记 | ✅ 允许 | 项目级冻结 |
| AI 把 `last_breaking_change` 等元数据写回用户 CLAUDE.md | ❌ 禁止 | 元数据是 mcpowers 内部决策辅助，**不**外流 |

### CHANGELOG 强制破坏声明段（v2.27.4+ · 全栈适用）

mcpowers 每次发布的 `CHANGELOG.md` **必须**在版本条目内含 `### Breaking Changes` 段（哪怕内容是 `无`）。这是 AI / 用户升级前判断兼容性的**唯一权威索引**——没标"无"等于发布者声明"我没审过是否有破坏性变更"，CI 应阻断。

格式约束：

```markdown
## v{major}.{minor}.{patch} - YYYY-MM-DD

### Breaking Changes
- `path/to/file.md §X.Y` 重写：<一句话说明新旧差异>
- 函数签名变更：`old_func(a, b)` → `new_func(a, b, c=None)`
- 删除的公共 API：`<list of removed exports>`

（**若确认无破坏性变更**，必须显式写 `### Breaking Changes\n\n- 无`，**禁止**省略该段）
```

**配套铁律**：
- mcpowers 仓库自身**禁止**"minor bump + 破坏性变更"——破坏性变更必须 bump `major` 版本号
- AI 在 `mcpowers-code-review` 阶段必须确认本次变更若属破坏性，已在 PR 描述里**预先**列出 Breaking Changes 条目
- 用户升级 mcpowers 前应优先 Read 最新 CHANGELOG 的 Breaking Changes 段，确认本项目是否需要迁移

> **正反对照**：

```yaml
# ✅ 正确：抽象 + 永远指向最新
# 本纪律对应 mcpowers 最新版本
# 物理路径用 ${CLAUDE_PLUGIN_ROOT}/scripts/templates/... 让框架展开

# ❌ 禁止：硬编码版本号
# 例如 ~/.claude/plugins/cache/mcpowers/mcpowers/{version}/
```

## Python import 位置规范（强制）

### 模块级导入区

Python 文件的 `import` / `from ... import ...` 必须位于模块级导入区，并按以下顺序分组：标准库、第三方依赖、本项目模块。函数、方法、类体和装饰器内部禁止写 import。

```python
# ✅ 正确：模块级导入区
import json
from pathlib import Path

from flask import request

from common.settings import config

def load_config(path: Path) -> dict:
    """加载配置文件。"""
    return json.loads(path.read_text(encoding='utf-8'))

# ❌ 禁止：函数内局部导入
# def load_config(path: Path) -> dict:
#     import json
#     return json.loads(path.read_text(encoding='utf-8'))
```

### 局部 import 例外

循环依赖或确实可选的第三方依赖可能需要局部 import，但不能以“按需使用”“延迟加载”或“性能优化”作为默认理由。必须同时满足：

1. 已确认模块级导入会造成可复现的循环依赖或可选依赖缺失。
2. import 旁写明具体原因和影响范围。
3. 用户明确确认继续使用局部 import。

没有满足以上条件时，改为模块级导入、依赖注入或调整模块依赖方向。写入 Hook 命中局部 import 时会阻断并要求确认。

### 自检

```bash
# 查看 Python 文件中的 import 行，确认没有缩进
rg --type py -n '^\s+(import|from\s+[^ ]+\s+import)' .
```

## 1. 数据建模规范（强制）

### 1.1 实体关联原则

**优先建立实体间关联，避免数据冗余**：

| 关联类型 | 正确做法 | 错误做法 |
|:---------|:---------|:---------|
| 一对多 | 主表存外键，从表关联主表 | 主表冗余从表数据 |
| 多对多 | 使用中间表关联 | 冗余 ID 列表 |
| 一对一 | 从表存主表外键 | 数据完全重复 |

```
# 错误示例：数据冗余
用户表 users
├── id
├── username
├── role_id        # 外键
├── role_name      # ❌ 冗余！从 roles 表关联即可
└── role_desc      # ❌ 冗余！

# 正确示例：外键关联
用户表 users
├── id
├── username
└── role_id        # 外键 → roles.id

角色表 roles
├── id
├── name
└── description
```

### 1.2 冗余数据控制

**允许冗余的条件（必须同时满足）**：

1. 该字段被查询的频率**极高**
2. 关联实体的变更频率**极低**
3. 冗余字段占用空间**可接受**
4. 数据一致性由**业务层保证**

| 场景 | 冗余是否合理 | 原因 |
|:-----|:-------------|:-----|
| 订单冗余用户昵称 | ✅ 合理 | 订单必然展示，昵称变更少 |
| 订单冗余用户电话 | ⚠️ 可选 | 电话可能变更，需权衡 |
| 订单冗余用户地址 | ❌ 不合理 | 地址频繁变更，关联查询不贵 |

### 1.3 关联查询的正确方式

**预加载关联数据，避免重复查询**：

```
❌ 错误：N+1 查询
   查询 100 条订单 → 再查询 100 次用户 = 101 次数据库调用

✅ 正确：预加载
   查询 100 条订单及其用户 → 1 次数据库调用（含 JOIN）
```

## 2. 查询性能规范（强制）

### 2.1 N+1 查询问题（强制）

**N+1 查询**：1 次主查询 + N 次关联查询

| 问题程度 | 查询次数 | 影响 |
|:---------|:---------|:-----|
| 严重 | 1 + N | 100 条记录 = 101 次查询 |
| 轻微 | 1 + 1 | 2 次查询，但可能无索引 |

**典型错误模式**：

```python
# ❌ 错误：循环内查询（N+1）
for order in orders:
    user = db.query("SELECT * FROM users WHERE id = ?", order.user_id)
    print(order.no, user.name)

# ✅ 正确：JOIN 预加载
orders = db.query("""
    SELECT o.*, u.name as user_name
    FROM orders o
    LEFT JOIN users u ON u.id = o.user_id
    LIMIT 100
""")

# ✅ 正确：批量查询后映射
user_ids = [o.user_id for o in orders]
users = db.query("SELECT * FROM users WHERE id IN (?)", user_ids)
user_map = {u.id: u for u in users}
for order in orders:
    print(order.no, user_map[order.user_id].name)
```


## 3. 函数设计规范（强制）

### 3.1 单一职责原则（SRP）

**一个函数只做一件事**：

```python
# ❌ 错误：职责过多
def create_order(data):
    validate(data)        # 验证
    calculate(data)       # 计算
    save(data)            # 保存
    notify(data)          # 通知
    log(data)             # 日志
    return data

# ✅ 正确：职责分离
def validate_order_data(data):
    """验证订单数据"""
    pass

def calculate_order(data):
    """计算订单"""
    pass

def create_order(data):
    """创建订单（核心逻辑）"""
    validate_order_data(data)
    data = calculate_order(data)
    save(data)
    return data

def create_order_with_notification(data):
    """创建订单并发送通知"""
    order = create_order(data)
    notify_async(order.id)
    return order
```

### 3.2 参数规范

| 要求 | 说明 |
|:-----|:-----|
| 参数数量 ≤ 3 | 超过3个应使用配置对象 |
| 参数类型明确 | 使用类型声明 |
| 避免可变默认参数 | 使用 `None` 而非 `[]` 或 `{}` |

```python
# ❌ 错误：参数过多
def create_user(name, age, email, phone, address, role_id, status, source, tags, remark):
    pass

# ✅ 正确：使用配置对象
class CreateUserInput:
    name: str
    email: str
    phone: str
    address: str
    role_id: int
    status: int = 1
    source: str = 'web'
    remark: str | None = None

def create_user(input: CreateUserInput):
    pass
```

```javascript
// JavaScript 使用对象解构
// ❌ 错误

// ✅ 正确
function createUser({ name, age, email, phone, address, roleId, status = 1, source = 'web' }) {}
```

### 3.3 返回值规范

| 要求 | 说明 |
|:-----|:-----|
| 返回类型一致 | 成功/失败返回同类型或使用 Result 封装 |
| 不返回 null 表示成功 | 使用特定值或异常 |
| 集合类型返回空集合 | 返回 `[]` 而非 `null` |

```typescript
// ❌ 错误：返回类型不一致
function getUser(id: number): User | null | boolean {
    if (!id) return null;
    const user = db.find(id);
    if (!user) return false;  // 类型不一致
    return user;
}

// ✅ 正确：使用 Result 封装
interface Result<T> {
    success: boolean;
    data?: T;
    error?: string;
}

function getUser(id: number): Result<User> {
    if (!id) return { success: false, error: 'Invalid ID' };
    const user = db.find(id);
    if (!user) return { success: false, error: 'User not found' };
    return { success: true, data: user };
}
```

## 4. 错误处理规范（强制）

### 4.1 异常使用原则

| 使用异常 | 不使用异常 |
|:---------|:-----------|
| 预期外的错误（网络中断、内存不足） | 业务校验失败（用返回值） |
| 程序无法继续执行 | 表单验证失败 |
| 需要中断调用栈 | 业务流程控制 |

```python
# ❌ 错误：用异常处理业务逻辑
def withdraw(amount):
    if amount > balance:
        raise ValueError('余额不足')  # 业务校验不应抛异常
    balance -= amount

# ✅ 正确：业务校验用返回值
def withdraw(amount):
    if amount > balance:
        return False, '余额不足'
    balance -= amount
    return True, None
```

### 4.2 异常捕获规范

**捕获具体异常，不过度捕获**：

```python
# ❌ 错误：过度捕获所有异常
try:
    result = do_something()
except Exception as e:
    log.error(e)  # 丢失了具体类型信息

# ✅ 正确：捕获具体异常
try:
    result = db.execute(stmt)
except ConnectionError as e:
    log.error(f'数据库连接失败: {e}')
    raise ServiceUnavailable('服务暂时不可用')
except IntegrityError as e:
    log.warning(f'数据完整性错误: {e}')
    raise DuplicateKeyError('数据已存在')
```

### 4.3 异常传播原则

**只传播必要信息，隐藏实现细节**：

```python
# ❌ 错误：暴露内部实现
try:
    db.query("SELECT ...")
except OperationalError as e:
    # ❌ 暴露了数据库类型 MySQL
    raise Exception(f'MySQL错误: {e.code}, {e.msg}')

# ✅ 正确：转换为通用异常
try:
    db.query("SELECT ...")
except Exception as e:
    log.error(f'查询失败: {e}')
    raise QueryError('查询数据失败')
```

## 5. 防御性编程规范（强制）

### 5.1 参数校验

**入口函数必须校验输入**：

```python
# ❌ 错误：信任外部输入
def delete_user(user_id):
    db.delete('users', {'id': user_id})

# ✅ 正确：校验参数
def delete_user(user_id: int) -> Result:
    if not user_id or not isinstance(user_id, int):
        return Result(success=False, message='Invalid ID')

    if not db.exists('users', user_id):
        return Result(success=False, message='User not found')

    if db.exists('orders', {'user_id': user_id}):
        return Result(success=False, message='Cannot delete user with orders')

    db.delete('users', {'id': user_id})
    return Result(success=True)
```

```javascript
// JavaScript 同样需要校验
// ❌ 错误
function deleteUser(userId) {
    db.delete('users', { id: userId });
}

// ✅ 正确
function deleteUser(userId) {
    if (!userId || typeof userId !== 'number') {
        return { success: false, message: 'Invalid ID' };
    }
    if (!db.exists('users', userId)) {
        return { success: false, message: 'User not found' };
    }
    db.delete('users', { id: userId });
    return { success: true };
}
```

### 5.2 空值处理

**链式调用前检查空值**：

```python
# ❌ 错误：链式调用不检查空值
city = get_user(user_id).profile.address.city

# ✅ 正确：安全获取
user = get_user(user_id)
if not user or not user.profile:
    return None
return user.profile.address.city

# ✅ 更安全：使用 Optional/Maybe 模式
def get_city(user_id):
    user = get_user(user_id)
    return user?.profile?.address?.city  # 类似 Swift/ Kotlin 的 optional chaining
```

### 5.3 并发问题

**更新时防止竞态条件**：

```python
# ❌ 错误：并发更新丢失
def update_stock(product_id, quantity):
    product = db.get('products', product_id)
    product.stock -= quantity  # 读取后修改，无锁
    db.update('products', product)

# ✅ 正确：乐观锁
def update_stock(product_id, quantity):
    product = db.get('products', product_id)
    result = db.execute("""
        UPDATE products
        SET stock = stock - ?, version = version + 1
        WHERE id = ? AND version = ?
    """, [quantity, product_id, product.version])
    if result.rows_affected == 0:
        raise ConflictError('Data has been modified, please retry')

# ✅ 正确：悲观锁
def update_stock(product_id, quantity):
    db.begin_lock()  # 开启事务锁
    try:
        product = db.get('SELECT * FROM products WHERE id = ? FOR UPDATE', product_id)
        if product.stock < quantity:
            raise ValueError('Insufficient stock')
        product.stock -= quantity
        db.update('products', product)
        db.commit()
    except:
        db.rollback()
        raise
```

## 6. 代码复用规范（强制）

### 6.1 DRY 原则（Don't Repeat Yourself）

**重复代码必须抽象**：

```python
# ❌ 错误：重复代码
def create_user_order(user_id, items):
    if not user_id: raise ValueError('User ID required')
    if not items: raise ValueError('Items required')
    for item in items:
        if not item['product_id']: raise ValueError('Product ID required')
        if item['quantity'] <= 0: raise ValueError('Quantity must be positive')
    # 创建订单...

def create_guest_order(guest_name, items):
    if not guest_name: raise ValueError('Guest name required')
    if not items: raise ValueError('Items required')
    for item in items:
        if not item['product_id']: raise ValueError('Product ID required')
        if item['quantity'] <= 0: raise ValueError('Quantity must be positive')
    # 创建订单...

# ✅ 正确：抽象公共验证
def validate_order_items(items):
    if not items:
        raise ValueError('Items required')
    for item in items:
        if not item.get('product_id'):
            raise ValueError('Product ID required')
        if not item.get('quantity') or item['quantity'] <= 0:
            raise ValueError('Quantity must be positive')

def create_user_order(user_id, items):
    if not user_id:
        raise ValueError('User ID required')
    validate_order_items(items)
    # 创建订单...

def create_guest_order(guest_name, items):
    if not guest_name:
        raise ValueError('Guest name required')
    validate_order_items(items)
    # 创建订单...
```

### 6.1.1 复用优先于二次抽象（强制 · v2.26.0+ 防过度设计）

> **DRY 的「反面」是无差别二次抽象**：
> - 每个新功能都新建 `wrapper` / `helper` / `manager` 类
> - 明明 SDK / 通用模块已有同名函数，又写一个同名 `xxx_v2`
> - 「我觉得这个更好用」**不构成**抽象的理由
>
> 本节强制规定**复用 → 二次抽象**的两段式判断，避免「先抽象再核对库」。

**两段式判断**（写函数前必走）：

```
Q1: 这个逻辑，仓库内是否已有等价实现？
   ├─ 是 → 直接调用，禁止包同名 wrapper（见下方反模式）
   └─ 否 ↓
Q2: SDK / 第三方库是否提供等价接口？
   ├─ 是 → 直接调用，禁止再抽象一层
   └─ 否 ↓
Q3: 是否需要调用本仓库的至少 3 个同类调用方才存在共性？
   ├─ 是 → 抽公共函数
   └─ 否 → 先在当前文件用私有函数，等出现第 3 个调用方再抽象（避免 YAGNI）
```

**反模式黑名单**（code-review 必须 Critical）：

| # | 反模式 | 反例 | 正确做法 |
|:-:|:-------|:-----|:---------|
| 1 | ❌ **未先扫仓库已有 API 就写 wrapper** | `class MyHttpClient: def get(...): return requests.get(...)` | 直接 `import requests; requests.get(...)` |
| 2 | ❌ **二次抽象仅一行转发，无真实逻辑** | `def send_email(to, body): EmailService.get().send(to, body)` | 直接 `email_service.send(to, body)` |
| 3 | ❌ **函数名与 SDK/公共模块冲突且非有意扩充** | SDK 有 `parse_url`，本仓库写 `parse_url_v2` | 提 PR 改 SDK 或公共模块，不要并存 |
| 4 | ❌ **跨项目搬运同名函数但不复用** | A 项目 `validate_phone` → B 项目再写 `validate_phone` | 提到 `common/validators.py` 跨项目复用 |
| 5 | ❌ **抽象类（ABC / Protocol）只有一个具体实现** | `class AbstractParser(Protocol): ...` + `class JsonParser: ...` | 直接用具体类，等出现第 2 个实现再抽 |
| 6 | ❌ **写 helper 函数但无调用方（写完等用）** | `def format_phone(raw): ...` 全仓无 `import` | 删掉，需要时再写（YAGNI） |

**自检清单**（写函数前必跑）：

```bash
# 1. 仓库内同名函数扫描（必须无重复定义）
rg --type py "def\s+${候选函数名}\b" .
# 2. SDK/通用模块是否有等价接口（按命名空间扫）
rg --type py "def\s+${候选关键词}\b" common/ sdk/ utils/
# 3. 调用方数量（>= 3 才值得抽公共函数）
rg --type py "${候选函数名}\(" . | wc -l
```

> 三个命令跑完、都符合预期 → 写函数；任一项命中已有 → 直接复用。

**v2.28.2 补充：hook 行为简化（核心原则：只有真 bug 才拦）**

仓库 `hooks/pre-write-check-duplicate.sh` 在 Write/Edit/MultiEdit 触发时自动扫描新函数与已有定义的同名冲突。**上面 R1-R6 反模式黑名单 + 3 条 `rg` 自检清单是写新函数前的必走手动判断；本段是 hook 自动化兜底（CI/编辑器层）**：

| 命中条件 | 决策 | 理由 |
|:---------|:----|:-----|
| **同文件内重名**（同一文件对同一函数名定义 ≥ 2 次） | ❌ [阻断]，exit 2 | Python 后者覆盖前者，是真 bug |
| **跨文件同名 + 单行透传 wrapper**（函数体仅一行 `return <call>(...)` 或 `<call>(...)`） | ❌ [阻断]，exit 2 | gold standard 二次包装信号（R2 反模式） |
| **跨文件同名（非单行透传）** | ✅ [放行]，exit 0 | Python import 是模块级作用域，跨文件同名不冲突；属业务模块各自实现 |

**豁免（与命中条件无关）**：

- **入口命名**：`def main()` / `def hook_main()` 等模块入口惯例被 `CONVENTION_NAMES` 直接跳过，不计入重名
- **Python dunder 协议方法**：`__init__` / `__new__` / `__repr__` 等 Python 语言级协议方法被 `DUNDER_NAMES` 豁免（任何自定义类 / dataclass / Exception 都会重新实现这些）
- **单下划线私有名**：`def _helper(...)` 等内部封装名跳过（避免模块内部命名冲突的误报）

**为什么跨文件同名默认放行**：v2.27.6 之前 hook 对所有同名函数默认 block，靠「命名空间 / 签名 / 绑定方法」3 类启发式降级——但**降级本身就是设计缺陷**：跨文件同名是合法常态（业务模块各自的 `parse(data)`），不该用启发式打补丁。v2.28.2 砍掉 3 类启发式降级，回归「只有真 bug 才拦」的极简原则。

**wrapper 类真正必要的 3 种场景**（除此以外直接调底层）：

1. **参数映射**：把外层 6 个参数聚合到底层 1 个 dict（如 `UserCreateDTO` → `dict`）
2. **批量调用**：单接口需要底层循环多个调用（且失败语义不同）
3. **统一异常处理**：把底层 5 种 `Exception` 归一为本项目的 2 种业务异常

> 反例（"觉得这样更优雅"的常见借口）：
> - ❌ "我想给函数加重试逻辑" → 直接 `@retry(stop=stop_after_attempt(3))`，不要写 wrapper
> - ❌ "我想加日志" → 用 `logger.exception` / 装饰器，不要写 wrapper
> - ❌ "我想加缓存" → 用 `functools.lru_cache` / 显式 cache key，不要写 wrapper

### 7.4 工具脚本 docstring 5 段骨架（v4.0.0+ 推荐基线）

#### 7.4.1 背景

mcpowers 仓内 `tools/export_docs.py` 等工具脚本曾存在 docstring 详细度失守——7 个函数仅 4 个完整 docstring，3 个缺 Returns 段。本节定义**工具脚本**（含仓内 `tools/` `hooks/` `scripts/` 下的脚本 + 用户项目 CLI 入口 + SDK 公开 API）的 docstring 5 段骨架基线。

详细度参考锚：`docs/API文档/swagger_template.md`（19 类接口 Flasgger YAML 模板——tool 脚本的 docstring 详细度对齐此参考）。

#### 7.4.2 5 段骨架定义

工具脚本函数 docstring 应至少包含以下 5 段（顺序固定）：

1. **Args / Arguments**：参数说明，每个参数一行，含类型 + 含义 + 边界条件
2. **Returns / Return Value**：返回值说明，含类型 + 含义；无返回值的函数写 `Returns: None`
3. **Raises**：可能抛出的异常，每个异常一行，含触发条件
4. **Side Effects / Notes**：副作用或备注（写文件 / 改全局状态 / 触发回调等）；无副作用时写 `无`
5. **Example**：可运行的最小调用示例

#### 7.4.3 Python 当前实现（Google 风格）

```python
def calculate_total(items: list[dict], tax_rate: float = 0.0) -> float:
    """计算订单总额（含税）

    Args:
        items: 商品列表，每项含 `price` 和 `quantity` 字段
        tax_rate: 税率，0.0 ~ 1.0，默认 0.0（不含税）

    Returns:
        订单总额（保留两位小数）

    Raises:
        ValueError: items 为空或 tax_rate 越界
        KeyError: 商品项缺 price 或 quantity 字段

    Side Effects:
        无

    Example:
        >>> calculate_total([{'price': 100, 'quantity': 2}], tax_rate=0.1)
        220.0
    """
```

| 段位 | Python（Google）| Go（Godoc）| JS/TS（JSDoc）| Rust（rustdoc）| Java（Javadoc）|
|:-----|:---------------|:-----------|:--------------|:---------------|:---------------|
| **1. 参数** | `Args:` | `// Parameters:` 或 `Args:` | `@param {type} name` | `# Arguments` | `@param name desc` |
| **2. 返回** | `Returns:` | `// Returns:` | `@returns {type}` | `# Returns` | `@return desc` |
| **3. 异常 / 错误** | `Raises:` | `// Returns error:` | `@throws {type}` | `# Errors` + `# Panics` | `@throws class desc` |
| **4. 副作用 / 备注** | `Side Effects:` | `// Notes:` | `@remarks` | `# Side Effects` | `@apiNote` |
| **5. 示例** | `Example:` | `// Example:` | `@example` | `# Examples` | `{@code ...}` |

> **当前 mcpowers 实现（v4.0.0）**：仅 Python 栈完整落地；其他 4 语言仅给出对照表作为参考，不强制。
> 扩展路径（不在本次 scope）：给 `swagger-lint-helper.py` 加 JS/TS / Go / Rust / Java 解析器，按各自 docstring 风格做 5 字段检查。

#### 7.4.5 适用场景

| 场景 | 必须使用 | 推荐 | 不适用（YAGNI）|
|:-----|:---------|:----|:--------------|
| 仓内工具脚本（`tools/` `hooks/` `scripts/` 下的 .py） | ✅ | - | - |
| 用户项目 CLI 入口（`cli.py` / `cmd.py`） | ✅ | - | - |
| SDK 公开 API 函数 | - | ✅ | - |
| Flask 视图函数 | - | ✅ | - |
| 业务逻辑函数 | - | - | ❌ |
| 测试函数 / fixture | - | - | ❌ |
| 内部 `_helper()` | - | - | ❌ |

#### 7.4.6 反模式（禁止）

- ❌ 只写一行说明（如 `"""计算总额"""`）——缺 4 段，违反骨架
- ❌ Args 只写参数名不写类型与含义
- ❌ Returns 段省略（"返回值显而易见" 不构成省略理由——无返回值的函数也必须写 `Returns: None`）
- ❌ Example 写伪代码（必须可运行的最小调用）
- ❌ 长函数 docstring 套用 5 段但字段顺序错乱
- ❌ 在 Args 段混入 Returns 内容（破坏分段纯度）

#### 7.4.7 与 swagger_template.md 的关系

swagger_template.md 是 **docstring 详细度的参考锚**——tool 脚本的 docstring 在**详细度**上对齐 swagger_template（即：每个字段都不空泛、参数有类型 / 含义 / 边界、异常有触发条件、Example 可运行）。

但 swagger_template.md 是 **Flasgger YAML 块**格式（接口注解），不是 Python `def` docstring 格式——两者**格式不同**，仅**详细度对齐**。Go / JS/TS / Rust / Java 等其他栈不需要对齐 swagger_template 的 YAML 格式，按各自栈的 docstring 风格落地 §7.4.4 对照表即可。

## 8. 日志规范

> **本节为基线原则**。完整的日志类型分类、字段 schema、大内容处理、脱敏规则、各栈实现 → 见 `日志规范.md`（v2.6.0 起顶层规范）。
>
> **本节只保留 2 件事**：
> 1. 日志级别的判定速查
> 2. 异常日志必须 `exception()` 或 `exc_info=True`（强制，禁止裸 `str(e)`）

### 8.1 日志级别使用（基线速查）

| 级别 | 使用场景 |
|:-----|:---------|
| DEBUG | 开发调试，生产环境不开启 |
| INFO | 正常业务流程 |
| WARNING | 异常但可处理（参数校验失败） |
| ERROR | 错误需处理（数据库连接失败） |
| CRITICAL | 严重错误（服务不可用） |

> **详细规则 + 采样策略 + 级别与日志类型映射** → `日志规范.md §2.2` / §6。

### 8.2 异常日志（强制）

**铁律**：触发代码报错时，必须记录完整 traceback，禁止截断；记录方式 `logger.exception()` 或 `logger.error(..., exc_info=True)`。

```python
# ❌ 错误：只记录错误信息，不记录堆栈
logger.error(f'Query failed: {e}')

# ✅ 正确：记录完整 traceback
logger.exception(f'Query failed: user_id={user_id}')
# 或
logger.error(f'Query failed: user_id={user_id}', exc_info=True)
```

**禁止**：
- ❌ 只记录 `str(e)` 而不记录 traceback
- ❌ 截断堆栈信息
- ❌ 用省略号替代完整堆栈

> **完整日志字段约束 + exception 类型的额外必填项（exc_type / exc_msg / traceback / user_id / request_id）** → `日志规范.md §3.4`。

## 9. 安全规范（强制）

### 9.1 SQL 注入防护

**禁止字符串拼接 SQL**：

```python
# ❌ 错误：SQL 注入风险
query = f"SELECT * FROM users WHERE name = '{name}'"
db.execute(query)

# ✅ 正确：参数化查询
db.execute("SELECT * FROM users WHERE name = ?", [name])

# ✅ ORM 方式（推荐）
User.objects.filter(name=name).first()
```

```javascript
// JavaScript 同样需要防止注入
// ❌ 错误
const query = `SELECT * FROM users WHERE name = '${name}'`;

// ✅ 正确：参数化查询
const result = await db.query('SELECT * FROM users WHERE name = ?', [name]);
```

### 9.2 敏感数据处理

```python
# ❌ 错误：日志记录敏感信息
logger.info(f'Login: username={username}, password={password}')

# ✅ 正确：脱敏处理
logger.info(f'Login: username={username}')

# ✅ 正确：只记录非敏感字段
logger.info(f'Login: username={username}, attempt={attempt}')
```

## 10. 代码风格规范

### 10.1 命名规范

#### 10.1.1 基础类型命名

| 类型 | 规范 | 示例 |
|:-----|:-----|:-----|
| 变量 | 小写下划线 / 小驼峰 | `user_name`, `userName` |
| 函数/方法 | 小写下划线 / 小驼峰 | `get_user`, `getUser` |
| 类 | 大驼峰 | `UserService`, `OrderController` |
| 常量 | 全大写下划线 | `MAX_RETRY`, `API_KEY` |
| 私有成员 | 下划线前缀 | `_internal_method` |

#### 10.1.2 通用命名原则

命名应自解释，禁止无意义简写，项目内缩写需保持一致。

```python
# ✅ 正确示例
user_name, is_active, get_user_by_id

# ❌ 错误示例
func1        # 不可自解释
usr_nm       # 无意义简写
pd           # 歧义（product? paid? password?）
```

#### 10.1.3 布尔变量命名

| 前缀 | 含义 | 示例 |
|:-----|:-----|:-----|
| `is_` | 是否为某状态/条件 | `is_active`、`is_deleted`、`is_empty` |
| `has_` | 是否拥有某属性/关系 | `has_permission`、`has_child`、`has_error` |
| `can_` | 能否执行某操作 | `can_edit`、`can_delete`、`can_export` |
| `should_` | 是否应该做某事 | `should_retry`、`should_validate` |
| `need_` | 是否需要做某事 | `need_refresh`、`need_migration` |

### 10.2 代码格式化

| 要求 | 说明 |
|:-----|:-----|
| 缩进一致 | 4 空格或 2 空格，禁止混合 |
| 行长度 | ≤ 120 字符 |
| 空格使用 | 运算符前后、逗号后加空格 |
| 空行使用 | 函数间空一行，逻辑块间空一行 |

## 11. 变更控制规范（强制）

### 11.1 最小化改动原则

**每次变更只涉及必要的文件**：

| 场景 | 正确做法 | 错误做法 |
|:-----|:---------|:---------|
| 修改超时时间 | 只改超时配置 | 重构整个登录模块 |
| 新增接口 | 只新建接口文件 | 改动三个旧接口 |
| 修复空指针 | 定位根因修复 | 改调用方、被调用方、加日志 |

### 11.2 根因分析原则

**修复问题前必须分析根因，禁止症状治疗**：

```python
# ❌ 错误：治标不治本
def get_user(user_id):
    try:
        return db.query(user_id)
    except NullPointerError:
        return {}  # 掩盖了问题

# ✅ 正确：找到根因并修复
def get_user(user_id):
    if not user_id:
        return None  # 根因：没有校验空值
    return db.query(user_id)
```

```python
# ❌ 错误：加了日志但没解决问题
def process_data(data):
    try:
        return do_something(data)
    except Exception as e:
        logger.error(f"Error: {e}")  # 只是记录了问题
        return None  # 仍然返回 None，问题依然存在

# ✅ 正确：分析根因并修复
def process_data(data):
    if data is None:
        return default_value()  # 根因：没有处理 None
    return do_something(data)
```

### 11.3 死代码与痕迹清理

**废弃代码必须删除，不得注释掉**：

```python
# ❌ 错误：注释掉废弃代码
# def old_function():
#     pass
#
# def another_old():
#     pass

# ✅ 正确：直接删除，git 历史会保留
```

**注释只解释当前代码，不记录演进和出处**：

```python
# ❌ 错误：注释里写历史演进
# 原来用 requests，因为性能问题现在改成 httpx
client = httpx.Client()

# ❌ 错误：注释里写参考来源
# 参考 xxx 项目的实现方式
def sign(payload): ...

# ✅ 正确：只说明当前代码在做什么、为什么这样做
client = httpx.Client()  # 需要 HTTP/2 与连接池复用

def sign(payload):
    """按服务端约定生成请求签名：sha256(body + salt)。"""
```

> 完整的痕迹词黑名单与例外白名单见《文档编写规范》§9（权威源），代码注释同样适用。

### 11.4 不确定性处理

**需求不明确时的处理原则**：

| 原则 | 说明 |
|:-----|:-----|
| 先确认再实现 | 禁止猜需求，模糊地带必须找用户确认 |
| 宁可少实现 | 功能蔓延是万恶之源，先满足核心需求 |
| 涉及多模块先设计 | 影响范围超过 2 个模块时，先输出设计文档 |
| 记录决策 | 做的假设要记录，后续可追溯 |

```python
# ❌ 错误：需求不明确时按猜测实现
def send_notification(user_id, message, channel="email"):
    # 产品没说要不要支持短信，但我觉得将来可能用...
    if channel == "sms":
        # 实现了但需求没要求
        pass

# ✅ 正确：需求不明确时先问清楚
def send_notification(user_id, message, channel):
    """
    发送通知

    Args:
        channel: 通知渠道（email/sms/push）
        注意：目前仅支持 email，其他渠道需确认需求
    """
    if channel != "email":
        raise NotImplementedError(f"channel={channel} 暂不支持，请联系产品确认")
    # 只实现明确需要的功能
```

## 12. 可测试性规范（强制）

### 12.1 可测试代码要求

| 要求 | 说明 |
|:-----|:-----|
| 纯函数优先 | 相同输入必有相同输出，无副作用 |
| 依赖注入 | 将外部依赖通过参数传入，便于 mock |
| 单一职责 | 函数职责单一，测试用例易于编写 |
| 确定性 | 不依赖时间、随机数、网络等不确定因素 |

### 12.2 依赖注入示例

```python
# ❌ 错误：硬编码依赖，难以测试
class UserService:
    def __init__(self):
        self.db = MySQLConnection()  # 硬编码

    def get_user(self, user_id):
        return self.db.query(user_id)

# ✅ 正确：依赖注入，便于测试
class UserService:
    def __init__(self, db):
        self.db = db  # 通过参数注入

    def get_user(self, user_id):
        return self.db.query(user_id)

# 测试时可以传入 mock
def test_get_user():
    mock_db = MockDB()
    service = UserService(mock_db)
    # ...
```

### 12.3 测试替身使用场景

| 替身类型 | 使用场景 |
|:---------|:---------|
| Mock | 模拟对象行为，验证交互 |
| Stub | 提供固定返回值 |
| Fake | 简化实现（如内存数据库） |
| Spy | 记录调用信息 |

### 12.4 单元测试编写原则

| 原则 | 说明 |
|:-----|:-----|
| Arrange-Act-Assert | 明确三个阶段 |
| 一个测试一个断言 | 便于定位问题 |
| 测试名称描述行为 | `test_user_not_found_returns_none` |
| 覆盖边界条件 | nil/0/空字符串/最大值等 |

#### B.1 KISS & YAGNI 详细条款

**KISS — 保持简单**：

| 要求 | 说明 |
|:-----|:-----|
| 优先标准库 | 能用标准库就不用第三方库 |
| 优先简单方案 | 能用简单数据结构就不用复杂设计 |
| 优先同步 | 能用同步就不用异步（除非有必要） |
| 拒绝硬套设计模式 | 简单逻辑不用模式，复杂逻辑让模式使代码更清晰 |

**YAGNI — 不提前实现**：

| 要求 | 说明 |
|:-----|:-----|
| 不做需求未要求的扩展 | 没有明确需求就不预留接口 |
| 不预留"将来可能用"的代码 | 将来需要时再实现 |
| 不提前优化 | 先 profiling 再优化，避免过早优化 |
| **只改需要改的** | 不重构无关代码 |
| 宁可少实现 | 不要多实现，功能蔓延是万恶之源 |

**最小化改动示例**：

| 场景 | 正确做法 | 错误做法 |
|:-----|:---------|:---------|
| 修改超时时间 | 只改超时配置项 | 重构整个登录模块 |
| 新增接口 | 只新建接口文件 | 改动三个旧接口 |
| 修复空指针 | 定位根因修复 | 改调用方+被调用方+加日志 |
| 修复 bug | 只改有问题的逻辑 | 顺手重构无关代码 |
