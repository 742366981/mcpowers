# mcpowers-optimize（性能优化）

> **核心**：先测量，再优化。没测过就优化 = 盲猜。
> **借鉴**：无直接对标，是 mcpowers 自有技能。

---

## 编排

本技能按顺序调用以下方法层技能 + 规范：

| 步骤 | 调用对象 | 类型 | 触发条件 | 失败时 |
|:-----|:---------|:-----|:---------|:-------|
| 1 | 规范组（`mcpowers-spec-index`） | 规范 | 必读（数据库/缓存/导入导出） | 提示加载 |
| 2 | 性能基线测量 | 内联 | 必走 | 没数据不进入下一步 |
| 3 | `mcpowers-code-review` | 方法 | 优化实施后 | 验证不破坏可读性 |
| 4 | `mcpowers-git-commit` | 场景 | 性能数据确认提升 | 阻断提交 |

**保护路径**：`mcpowers-shared/`、`mcpowers/`、`hooks/` 三个目录的写操作触发前确认。

**铁律**：禁止"优化"后性能无变化；禁止优化时改行为（这是 bugfix 不是 optimize）。

---

## 触发即执行

### 1. 加载规范
- Read `mcpowers-shared/mcpowers-spec-index/SKILL.md`
- 加载：
  - `mcpowers-shared/docs/技术规范/代码规范.md`（**必读**）
  - `mcpowers-shared/docs/技术规范/数据库规范.md`（涉及 DB）
  - `mcpowers-shared/docs/技术规范/缓存规范.md`（涉及缓存）
  - 对应栈规范

### 2. 建立基线（HARD-GATE）
**禁止**没测过就动手优化。

测量：
- 响应时间（p50 / p95 / p99）
- QPS / TPS
- CPU / 内存 / 磁盘 IO
- 数据库慢查询日志
- 接口耗时分布

**记录基线**：
```
优化前基线：
- 接口 X 平均响应：500ms（p95: 1200ms）
- QPS：100
- 慢查询：3 条（> 1s）
```

### 3. 定位瓶颈
按优先级排查：

| 瓶颈 | 排查方式 |
|:-----|:---------|
| 数据库 | 慢查询日志、`EXPLAIN`、索引使用 |
| 缓存 | 命中率、缓存穿透 / 雪崩 |
| 网络 | 接口依赖、外部服务 |
| 计算 | 循环复杂度、CPU 密集操作 |
| IO | 文件读写、序列化反序列化 |
| 架构 | 同步改异步、串行改并行 |

**禁止**：
- ❌ 不查就改（"我觉得是 N+1"）
- ❌ 同时改 3 个地方（不知道哪个有效）

### 4. 单点优化
对**一个**瓶颈点优化：
- 写改动
- 跑测试（保证不破坏功能）
- **重新测量**（对比基线）

**如果性能没变化 → 回滚 + 重新定位瓶颈**。

### 5. 反复迭代
- 优化一个点 → 测量 → 看变化
- 找到下一个瓶颈 → 优化 → 测量
- 性能达标 → 停止（YAGNI：别过度优化）

### 6. 输出优化报告
```markdown
# 性能优化报告

## 基线
- 接口 X 平均响应：500ms（p95: 1200ms）

## 优化项
### OP-1: 加索引
- 改动：给 `user.email` 加唯一索引
- 原因：慢查询日志显示这条 SQL 全表扫描
- 效果：响应从 500ms → 50ms（10x 提升）

### OP-2: 加缓存
- 改动：用户信息加 Redis 缓存（TTL 5min）
- 原因：相同用户连续请求重复查 DB
- 效果：缓存命中后响应 5ms

## 优化后
- 接口 X 平均响应：50ms（p95: 80ms）
- 整体提升：10x
```

---

## 反模式（禁止）

- ❌ 没测过就优化
- ❌ 一次改多个点（不知道哪个有效）
- ❌ 优化后不复测
- ❌ 过度优化（YAGNI：达标就停）
- ❌ 优化时改行为（这是 bugfix 不是 optimize）

- 性能数据记录到 `docs/细节记录/`
