# mcpowers:workflow

AI辅助开发的标准化工作流程技能。

## 触发词

当用户说以下内容时，**必须**加载本技能并执行：

| 触发词 | 场景 |
|:-------|:-----|
| 新项目 / 新建项目 | 创建一个全新的项目 |
| 开始开发 / 启动开发 | 已有项目，开始开发任务 |
| 初始化项目 | 项目初始化配置 |
| 按流程开发 | 用户要求按标准流程执行 |

## 核心原则（红线）

> ⚠️ **以下行为是红线，违反将被视为不合格**

| 红线行为 | 说明 |
|:---------|:-----|
| **未经确认直接修改** | 用户未确认前不得执行任何修改 |
| **先写代码后补文档** | 接口必须先写 docstring 再写实现 |
| **多个操作后才 commit** | 每个独立任务完成后必须立即 commit |
| **只 commit 代码不 commit 文档** | 代码和文档变更必须同时提交 |
| **发现重复定义未处理** | 冗余内容必须删除，保留一处 |
| **代码注释不完整** | 所有代码必须有完整注释 |

## 代码质量标准

**所有代码必须遵循以下原则**：

| 原则 | 说明 |
|:-----|:-----|
| **SOLID** | 单一职责、开闭原则、里氏替换、接口隔离、依赖倒置 |
| **KISS** | 保持代码简洁易懂，避免不必要的复杂性 |
| **DRY** | 拒绝重复代码，相同逻辑只写一次 |
| **YAGNI** | 只实现当前明确所需的功能，拒绝过度设计 |

## 开发流程（7步法）

### Step 0: 环境检查

检查项目是否初始化：

```
检查项：
- .gitignore 是否存在？
- 语言特定文件是否存在？（requirements.txt / package.json）
- 虚拟环境脚本是否存在？
```

若缺失 → 询问用户是否初始化。

---

### Step 1: 识别核心规范

**强制执行**，每次任务开始都必须执行。

**1.1 扫描规范目录**

```bash
ls docs/技术规范/*.md
```

**1.2 确定项目类型**

根据 `docs/设计文档/` 下的设计文档，确认：

| 项目类型 | 技术栈 |
|:---------|:------|
| 后端 | Flask / FastAPI / Django |
| 前端 | Vue / React |
| 全栈 | 后端 + 前端 |
| 爬虫 | Python 爬虫相关 |

**1.3 识别技术锁规范**

| 项目特征 | 技术锁规范 |
|:---------|:----------|
| 后端 + Flask | Flask后端规范.md |
| 前端 + Vue | Vue前端规范.md |
| 爬虫功能 | 爬虫规范.md |

**1.4 读取适用规范**

必须读取以下规范文件：

| 优先级 | 规范文件 |
|:-------|:---------|
| 必须 | `docs/技术规范/Git规范.md` |
| 必须 | `docs/技术规范/代码同步修改规范.md` |
| 必须 | `docs/技术规范/开发环境规范.md` |
| 必须 | `docs/技术规范/设计规范.md` |
| 必须 | `docs/技术规范/代码规范.md` |
| 按需 | `docs/技术规范/Flask后端规范.md`（Flask项目） |
| 按需 | `docs/技术规范/Vue前端规范.md`（Vue项目） |
| 按需 | `docs/技术规范/爬虫规范.md`（爬虫项目） |

**1.5 汇报项目情况**

向用户汇报：
- 项目类型和技术栈
- 所有识别到的规范
- 本次需要遵守的规范清单
- 核心要点总结

---

### Step 2: 查找需求

**强制执行**。

检查以下目录：

| 目录 | 含义 | 状态 |
|:-----|:-----|:-----|
| `docs/原始需求/` | 用户提供的原始需求 | 空→产品设计，有→继续 |
| `docs/需求文档/` | 标准化需求 | 无→需求转换，有→继续 |

**状态判断**：

| 状态 | 条件 | 处理 |
|:-----|:-----|:-----|
| 无原始需求 | 目录为空 | **阶段0：产品设计** |
| 有原始需求，无需求文档 | 原始需求存在，需求文档为空 | **阶段1：需求转换** |
| 两者都有 | 原始需求和需求文档都存在 | 直接进入阶段2 |

---

### Step 3: 确认设计文档

**强制执行**。

检查 `docs/设计文档/` 目录：

| 状态 | 处理 |
|:-----|:-----|
| 无设计文档 | 生成设计文档 → 询问用户确认技术选型 |
| 有设计文档但未确认 | 询问用户确认技术选型 |
| 有设计文档且已确认 | 直接进入阶段4 |

⚠️ **注意**：设计文档存在 ≠ 用户已确认

---

### Step 4: 按流程执行

根据 Step 2-3 的结果，按以下阶段执行：

#### 阶段0：产品设计

触发：用户只有想法/创意，没有原始需求

```
1. 引导用户描述需求（按产品设计规范交互）
2. 生成原始需求文档
3. 保存到 docs/原始需求/
```

#### 阶段1：需求转换

输入：`docs/原始需求/`
输出：`docs/需求文档/`

```
1. 读取原始需求
2. 转换为标准化需求文档
3. 识别下拉框/可配置字段
4. 输出基础数据表清单
5. 保存到 docs/需求文档/
```

**需求文档必须包含**：
- 项目概述（名称、背景、目标）
- 系统定位（边界、核心功能、用户角色）
- 功能需求（模块划分、功能点列表）
- 非功能需求（性能、安全等）
- 数据字典（核心数据实体）
- 基础数据表清单

#### 阶段2：设计生成

输入：`docs/需求文档/`
输出：`docs/设计文档/`

```
1. 确定技术选型（后端/前端/数据库/缓存等）
2. 检查 docs/技术规范/ 是否有对应技术规范
3. 询问用户是否遵守该规范
4. 编写系统概述
5. 设计技术架构和模块划分
6. 设计基础数据模块（独立模块）
```

**设计文档必须包含**：
- 系统概述（项目定位、主要功能）
- 技术选型（后端/前端/数据库/缓存等）
- 技术规范（遵循的规范）
- 系统架构（模块划分、目录结构）
- 基础数据模块设计

⚠️ 必须询问用户确认技术选型

#### 阶段3：代码生成

输入：`docs/需求文档/` + `docs/设计文档/` + `docs/技术规范/`

```
1. 严格遵守对应的技术规范，搭建项目结构
2. 每个模块/组件先编写接口文档，再写实现
   - 后端：视图docstring + 视图实现
   - 前端：组件文档 + 组件实现
   - 数据库：表结构设计 + 初始化脚本
3. 同步编写配置文件（开发/测试/生产环境）
4. 每完成一个独立功能点，立即 git commit
```

**强制要求**：
- 严格遵守对应的技术规范
- 严格遵守代码规范
- **禁止先写代码后补文档**
- **禁止多个功能点完成后才commit**
- **禁止只commit代码不commit相关文档**

---

### Step 5: 细节记录

触发：用户主动告知关键信息时

**记录格式**：
```markdown
## 用户告知的关键信息

| 日期 | 内容 | 适用范围 |
|-----|------|----------|
| 2026-05-09 | 用户告知的XXX | 用于XXX功能开发 |
```

**要求**：
- 适用范围必须明确到具体模块或接口
- AI 修改相关功能前必须检查并遵守
- 禁止堆砌，应分类整理

---

### Step 6: 保持更新

触发：用户告知新的关键信息时

**README 维护**：
- 更新"项目结构"（新增模块/目录时）
- 更新"快速开始"（新增启动命令时）
- 记录"最近变更"（最近 3-5 条）

---

### Step 7: 三阶段同步

需求、设计、代码三者必须保持同步。

**同步方向**：

| 同步方向 | 触发条件 | 同步内容 |
|:---------|:---------|:---------|
| **正向同步** | 需求变更 | 原始需求 → 标准需求 → 设计文档 → 代码 |
| **逆向修正** | 代码实现与设计文档不符 | 代码实现 → 更新设计文档 |

**禁止行为**：
- ❌ 代码与设计文档不一致
- ❌ 设计文档与需求不一致
- ❌ 变更只改一处
- ❌ 跳过设计文档直接改代码

## 强制检查清单

### 每次任务前
- [ ] Step 1: 是否已识别核心规范？
- [ ] Step 2: 是否已检查需求？
- [ ] Step 3: 是否已确认设计文档？

### 每次修改前
- [ ] 是否分析了影响范围？
- [ ] 是否检查了需要同步的文件？
- [ ] 是否询问了用户确认？

### 每次 commit 前
- [ ] 是否每个独立任务单独 commit？
- [ ] 是否代码和文档同时 commit？
- [ ] commit message 是否符合规范？

### 接口开发
- [ ] 是否先写了 docstring？
- [ ] 是否符合 API 规范？
- [ ] 是否包含了完整示例？
