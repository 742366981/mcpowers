# 前端对接流程（基于 OpenAPI Spec 自动生成 TS 客户端）

> **核心理念**：后端改了 spec → 前端自动重新生成 TS 类型，**零文档维护、零沟通成本**。

---

## 0. 与现有工具的关系（重要！避免重复造轮子）

| 工具 | 用途 | 何时用 |
|:-----|:-----|:-------|
| **`tools/export_docs.py`** | 一键导出 `swagger_spec.json` + `API文档.md` | **Step 6 必跑**（Markdown 给产品/测试，JSON 给前端/测试工具） |
| **`openapi-typescript-codegen`** | 生成前端 TS 客户端 | **Step 7 必跑**（TS 类型 + fetch 客户端） |
| **`schemathesis` / `dredd`** | 基于 spec 自动生成 API 测试 | **Step 7 必跑**（fuzz + 契约测试） |
| **`API文档/swagger_template.md`** | Swagger 2.0 YAML 模板（写进 docstring） | **Step 4 必读**（写 docstring 用） |
| **`API文档/API文档模板.md`** | 人类阅读 Markdown 模板（导出后样式参考） | **Step 4 必读**（验证导出 Markdown 符合预期） |

> ⚠️ **禁止**：本文件不得重新定义导出 Markdown 文档的逻辑（已有 `export_docs.py`）。
> ⚠️ **禁止**：本文件不得重新定义 docstring 模板格式（已有 `API文档/` 两份模板）。

## 1. 整体流程

```
后端 Flask（docstring 完整）
        ↓ Flasgger 自动生成
/apispec_1.json（OpenAPI 2.0 规范）
        ↓ openapi-typescript-codegen
前端 TS 类型 + API 客户端
        ↓ CI 校验
spec 变更自动检测 → 强制重新生成 + 通知前端
```

## 2. 工具选型

| 工具 | 用途 | 备注 |
|:-----|:-----|:-----|
| **openapi-typescript-codegen** | 生成 TS 类型 + fetch 客户端 | 主流、支持 OpenAPI 2.0/3.0 |
| openapi-generator | 生成多语言客户端 | 体积大、配置复杂 |
| orval | 生成 React Query / SWR 客户端 | 适合 React 生态 |

> 推荐 **openapi-typescript-codegen**（Vue/React 通用、配置简单）。

## 3. 安装与配置（Vue 项目示例）

### 3.1 安装

```bash
npm install --save-dev openapi-typescript-codegen
```

### 3.2 生成脚本（`scripts/gen-api.sh`）

```bash
#!/bin/bash
set -e

# 后端 Swagger 地址
SPEC_URL="${SPEC_URL:-http://localhost:5000/apispec_1.json}"
# 生成位置（约定：src/api/generated/）
OUTPUT_DIR="${OUTPUT_DIR:-src/api/generated}"

# 拉取 spec（开发环境无需鉴权；生产环境按加密方案加 header/auth）
curl -fsSL "$SPEC_URL" -o /tmp/openapi.json

# 生成 TS 类型 + fetch 客户端
npx openapi-typescript-codegen \
  --input /tmp/openapi.json \
  --output "$OUTPUT_DIR" \
  --client fetch \
  --useUnionTypes
```

### 3.3 package.json scripts

```json
{
  "scripts": {
    "api:gen": "bash scripts/gen-api.sh",
    "api:check": "bash scripts/gen-api.sh && git diff --exit-code src/api/generated/"
  }
}
```

## 4. 生成产物结构

```
src/api/generated/
├── index.ts              # 总入口
├── models/               # 所有 TS 类型
│   ├── LoginRequest.ts
│   ├── LoginResponse.ts
│   └── ...
├── services/             # 所有 API 客户端方法
│   ├── LoginService.ts
│   └── ...
└── core/                 # fetch 封装 + 错误处理
    ├── request.ts
    └── ApiError.ts
```

**使用示例**：
```typescript
import { LoginService, LoginRequest } from '@/api/generated';

const request: LoginRequest = {
  username: 'admin',
  password: '0192023a7bbd73250516f069df18b500',
};
const response = await LoginService.login(request);
// response.data 自动有 TS 类型提示
```

## 5. CI 校验（关键！）

**目的**：检测后端 spec 变更 → 强制重新生成 → 防止前端代码与后端不同步。

### 5.1 GitHub Actions 示例（`.github/workflows/api-sync.yml`）

```yaml
name: API Spec Sync Check

on:
  pull_request:
    paths:
      - 'apps/**/*.py'  # 后端代码变更触发

jobs:
  check-api-sync:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - name: 启动后端
        run: |
          cd backend && pip install -r requirements.txt
          python app.py &
          sleep 10
      - name: 拉取 spec 并重新生成
        run: |
          curl -fsSL http://localhost:5000/apispec_1.json -o /tmp/openapi.json
          npm run api:gen
      - name: 检测是否有未提交的生成产物
        run: |
          git diff --exit-code src/api/generated/ || (echo "❌ 后端 spec 已变更，请运行 npm run api:gen 并提交" && exit 1)
```

**效果**：
- 后端改了接口但前端没重新生成 → CI 失败，PR 不能合并
- 强制前端开发者及时同步

## 6. 错误码统一处理

后端响应统一 `{code, msg, data}`，前端可封装全局拦截器：

```typescript
// src/api/interceptor.ts
import { ApiError } from '@/api/generated';

api.interceptors.response.use(
  (response) => {
    const { code, msg, data } = response.data;
    if (code !== 0) {
      // 业务错误统一处理
      ElMessage.error(msg || '操作失败');
      return Promise.reject(new ApiError(code, msg));
    }
    return data;
  },
  (error) => {
    // HTTP 错误（如 401、500）
    ElMessage.error('网络异常');
    return Promise.reject(error);
  }
);
```

## 7. 与 mcpowers-feat 的协作

| 步骤 | 触发 |
|:-----|:-----|
| 后端开发 | `mcpowers-feat` → 写 docstring → 改实现 → TDD |
| 提交 | `mcpowers-git-commit` |
| 前端同步 | 本技能 Step 7 → `npm run api:gen` → 提交生成产物 |
| CI 校验 | GitHub Actions 检测 spec 变更 |

---

## 8. 反模式（禁止）

- ❌ 前端手写接口类型（与后端脱节）
- ❌ 后端改完接口不通知前端（必须走 CI 强制）
- ❌ 生成产物不提交到 git（团队成员拿不到一致类型）
- ❌ 跳过 CI 校验步骤直接合并 PR
- ❌ 用业务请求工具（如 axios）绕过生成的客户端（破坏类型一致性）
