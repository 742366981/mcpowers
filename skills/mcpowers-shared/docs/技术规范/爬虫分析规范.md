## 1. 分析流程总览

> **v2.13.0 + v2.14.0 设计**：完整的 7 阶段编排流程图见
> `mcpowers-crawler-reverse/SKILL.md` 阶段 1-7（目标画像 → 接口分析 → 决策点 →
> 逆向攻坚 → 模块化封装 → 沉淀案例 → 落地决策）。本规范只承载公共方法论，不
> 重复流程编排；专项方法论按命中平台的 reverse 技能分流。

### 1.1 最终交付形态与逆向实现方式分离（**v2.12.0 新增**）

逆向前必须先确认最终交付形态，避免分析完成后才发现产物方向不对：

| 最终交付形态 | 运行边界 | 验收目标 |
|:-------------|:---------|:---------|
| **纯协议** | 最终脱离浏览器/App/RPC，协议客户端独立生成参数并请求 | 停止依赖运行时后仍能完成核心业务；外部浏览器保持运行 |
| **半自动化** | 自动化或 RPC 处理登录、验证码、challenge、sign/token 等难点，协议层完成核心请求 | 运行态状态可刷新、隔离、过期恢复 |
| **纯自动化** | 浏览器/App 自动完成完整业务动作与数据提取 | 页面/App 业务链路端到端成功 |

**RPC 是逆向实现方式，不是第四种交付形态**。阶段 4 可按难度选择：Python 纯复现 →
Node/JS 补环境 → RPC 调用目标运行时。若使用 RPC：

- Web 可在目标页面注入 WebSocket 客户端，由本地服务按 `group` / `name` 隔离运行时，
  注册受控 action 或执行受限 JS，返回 sign/token/响应；
- APP 可使用 Frida `rpc.exports` 调用 Java/native 运行时函数；
- 必须记录调用端、运行时标识、action、参数/返回 schema、健康检查、超时、断线重连
  和并发隔离；
- RPC endpoint 仅绑定本机或受控内网，禁止公网暴露、任意代码默认执行、跨账号/
  session 串用或静默复用旧参数；
- 纯协议目标最终不得依赖 RPC；无法剥离时必须重新确认改为半自动化。

**JsRpc 参考**：[`jxhczhl/JsRpc`](https://github.com/jxhczhl/JsRpc) 展示了本地服务 +
浏览器注入 WebSocket、`group/name` 连接隔离、注册 action、`/go` 调用和 `/execjs`
执行模式。这里只借鉴驻留运行时与显式 action 的方法，不把该项目、默认端口或接口
变成本规范硬依赖。

运行态 token/Cookie/challenge 必须与抓包样本、稳定常量分离，记录生成时间、TTL、
账号/session/设备绑定并原子刷新；日志只保留脱敏标识。

### 1.2 目标载体与运行时分层（**v2.13.0 新增**）

逆向技能先按载体判断，再按运行时细分；语言、平台和框架不得平铺混用：

| 证据 | 主专项 | 说明 |
|:-----|:-------|:-----|
| URL、浏览器页面、H5、JS/WASM | `mcpowers-reverse-web` | 浏览器网络与 Web 运行时为主（详见《爬虫Web逆向规范》） |
| App 但平台/框架未知 | `mcpowers-reverse-app` | 先识别包格式、OS 和核心逻辑层（详见 §10.9 指纹交接） |
| APK/AAB、DEX、Java/Kotlin/JNI | `mcpowers-reverse-android` | Kotlin 是 Android 语言分支，不单独成类（详见《爬虫Android逆向规范》） |
| IPA、Mach-O、Swift/Objective-C | `mcpowers-reverse-ios` | iOS 签名、运行时和设备模型独立（详见《爬虫IOS逆向规范》） |
| Dart snapshot、`libapp.so`、`App.framework` | `mcpowers-reverse-flutter` | Android/iOS 只处理外壳与原生桥接（详见《爬虫Flutter逆向规范》） |
| uni-app、React Native、Cordova、Capacitor、WebView/JSBridge | `mcpowers-reverse-hybrid` | 先定位 JS、Bridge、Native 哪层生成关键值（详见《爬虫Hybrid逆向规范》） |
| 微信/支付宝/抖音/百度小程序或小游戏 | `mcpowers-reverse-miniprogram` | 宿主、分包、平台 API 和登录态独立（详见《爬虫小程序逆向规范》） |

多种指纹同时出现时，选择一个"核心逻辑所在层"作为主专项，其他专项只补外壳、
Bridge 或平台环境证据。证据不足时保持 `unknown`，禁止按用户口述技术栈强行选工具。

### 1.3 外部资源所有权铁律（**v2.14.0 强化**）

> **外部接管资源不可关闭**：通过 CDP、WebView 调试端口或外部 daemon（如
> bb-browser / frida / LSPosed / 调试 IDE）接管的资源不属于当前任务。无论正常
> 收尾、异常还是回退，都只能停止使用/断开客户端，**不能关闭用户本身的浏览器、
> App、daemon 或 `browser.contexts[0]`/`page`**。纯协议任务验收通过停止依赖并
> 独立调用完成，用户的 Chrome 必须保持运行。
>
> - 实操步骤与禁止模式见《爬虫工具与抓包规范》§3.5.1（资源所有权清单）
> - 与本铁律兼容的连接方式见《爬虫工具与抓包规范》§6（bb-browser MCP）
> - CDP 接管 WebView 的具体模式见《爬虫Hybrid逆向规范》§2 与
>   《爬虫小程序逆向规范》§4
> - frida / frida iOS / LSPosed / 调试 IDE 的资源所有权清单分别见各平台专项
>   规范的"调试资源所有权"小节
>
> 资源清单（按 owner 分类）：

| resource | origin / owner | 允许操作 | 收尾 |
|:---------|:---------------|:---------|:-----|
| 用户 Chrome browser | `external/user` | attach、读取 tabs、经确认操作页面 | 断开客户端；禁止 `browser.close()` / kill |
| 用户 context | `external/user` | 复用 Cookie/登录态 | 禁止 `context.close()` / clear cookies |
| 既有 page/tab | `external/user` | 经确认读取或操作 | 禁止 `page.close()` |
| 用户 context 内任务新建 tab | `task-in-user-context` | 执行目标动作 | 默认保留；用户明确确认后才可关闭 |
| 外部 bb-browser daemon | `external` | status、adapter 调用 | 异常即回退；禁止 stop/restart |
| frida-server（root 设备） | `external/user` 或 `task` | attach + Hook | 按资源清单 owner 处置；禁止 kill |
| LSPosed 注入 / 调试 IDE / 微信开发者工具 | `external/user` | attach / 查看 Network | 断开客户端；禁止 taskkill |

**反模式**：
- ❌ 接管收尾调用 `browser.close()` / `context.close()` / `page.close()` 或
  kill 用户 Chrome / frida-server / 调试 IDE
- ❌ Playwright `browser.new_context()` 新建独立 context
- ❌ 任何 daemon 处理都不得关闭 / 重启 / kill 用户 Chrome
- ❌ 不记录 owner 就 stop/restart daemon

## 3. 接口定位与筛选

### 3.1 过滤冗余请求（**必做第一步**）

**冗余请求类型清单**（**先排除这些**）：
- 静态资源：`.png` / `.jpg` / `.css` / `.js` / `.woff` / `.ttf` / `.svg`
- 上报埋点：`/log`、`/beacon`、`/track`、`/analytics`、`/collect`、`/monitor`
- 健康检查：`/health`、`/ping`、`/actuator`、`/favicon.ico`
- CDN 域名：常见 CDN 厂商域名段
- 心跳保活：`/heartbeat`、`/keepalive`（长连接场景）

### 3.2 核心业务接口特征（**重点关注**）

- URL 含 `/api/`、`/gateway/`、`/graphql`、`/v1/`、`/v2/`
- Content-Type 是 `application/json` 或 `application/x-www-form-urlencoded`
- 有非空 Request Body
- 响应含 `data` / `list` / `result` / `records` 字段
- 通常每次操作只发 1-3 次（不是高频上报）

### 3.3 静态页 vs 动态接口

| 特征 | 静态页（HTML 渲染） | 动态接口（API 渲染） |
|:-----|:-------------------|:-------------------|
| 抓包主体 | Network → Doc | Network → XHR/Fetch |
| 数据位置 | HTML DOM 节点 | JSON 响应体 |
| 适用工具 | BeautifulSoup / lxml | requests / aiohttp |
| 抓取难度 | 低（无反爬） | 中-高（常含加密） |

### §3.0 接口分析协作模式（**v2.9.5 新增**）

> **核心原则**：AI 抓不到时**主动切换模式**，**不把"找不到"等同于"不存在"**。
> v2.9.4 缺失这一步，导致复杂场景（登录态接口、懒加载接口）漏抓关键接口。

#### §3.0.1 4 种协作模式

| 模式 | 适用场景 | 操作流程 | AI 行为 |
|:-----|:---------|:---------|:--------|
| **A. AI 全自动**（默认） | 抓包 + 自动化分析无障碍 | 自动化抓包 + 过滤 + 置信度标记 | 跑 Playwright 模拟 + DevTools 抓包 |
| **B. 用户操作 + AI 抓包** | 关键操作只能在登录态触发 / Chrome 150+ 强校验表单 / 真实 page target 上下文（v2.16.0 扩展） | "请你在浏览器里操作 X → A → B，我监控网络请求" | 跑 `popup-handler.cleanup_all()` 后 `user_action_recorder.start_recording()`；**AI 必须 attach 真实 page target（不 `Target.createTarget`），强校验表单场景不驱动表单**，用户操作完 `stop_recording()` 落 `user-actions.json` + `user-session.har.jsonl`（工具见《爬虫工具与抓包规范》§8；实战案例见 §3.0.6） |
| **C. 用户告知接口** | 用户已知目标接口（曾用过接口/查过文档/有现成 HAR） | "请直接告诉我 URL / 参数 / 业务含义" | 直接录入用户给的接口 |
| **D. AI 引导用户到指定页面** | 用户不清楚目标页位置（"我要爬 X 但不知道从哪里开始"） | "请告诉我要爬的具体页 URL → 我接管你的标签页" | 用户到指定页后切换 A 模式接管 |

#### §3.0.2 模式选择 AskUserQuestion（v2.9.5 必走）

> **核心原则**：阶段 2 开头**必问**，让用户一开始就有掌控感。

```
> 请问使用哪种协作模式分析接口？
> - A. AI 全自动抓包（默认，AI 跑 Playwright 模拟触发）
> - B. 用户操作 + AI 抓包（适合登录态场景：你操作我看）
> - C. 用户告知接口（如果你已知目标 URL / 参数）
> - D. AI 引导用户到指定页面（适合不清楚目标位置的场景）
```

#### §3.0.3 模式切换触发条件（v2.9.5 新增）

| 触发条件 | 切换动作 |
|:---------|:---------|
| A 模式下，连续 3 次自动化抓包未识别出核心接口 | **暂停**，主动切换到 B / C / D |
| A 模式下，抓包未识别但**未走漏抓 7 层 6 问自检**（v2.16.0 强门禁） | **暂停**，必须先按《爬虫工具与抓包规范》§3.9.2 6 问自检，**禁止**直接把"抓不到"等同于"接口不存在" |
| 用户主动说"我直接告诉你" | 切到 C |
| 用户主动说"我帮你打开" | 切到 D |
| 用户主动说"我自己操作" | 切到 B |
| 用户贴 cURL 命令（v2.16.0 新增） | 切到 C 并按 §3.0.7 12 项快速帮助清单 + §3.0.8 cURL → 代码 SOP 处理 |
| 阶段 2 自检发现 [❓] 过多（>3 条） | 暂停，切到 B 让用户操作触发遗漏接口 |

#### §3.0.4 模式协同工作流

```
[问 1] 协作模式 4 选 1（§3.0.2）
  │
  ├─ A 模式 ─── 自动化抓包 → 漏抓 → [问 3] 切换到 B/C/D
  │
  ├─ B 模式 ─── 用户操作时 AI 监控 → AI attach 真实 page target（不 createTarget）
  │              → 每个操作触发的接口都收下
  │              → 用户操作完 → 转 A 模式做置信度收敛
  │              → v2.16.0 实战：Chrome 150+ + 强校验表单 + 真实登录态必走 B
  │
  ├─ C 模式 ─── 用户告知接口 → AI 直接录入 + 实测验证（转 A 的实测阶段）
  │              → v2.16.0：用户提供 cURL 时按 §3.0.7 + §3.0.8 SOP 转换为 Python 代码实测
  │
  └─ D 模式 ─── 用户到指定页面 → AI 接管 → 自动转 A 模式
```

#### §3.0.6 Chrome 150+ 协作模式 B 实战案例（**v2.16.0 新增**）

> **核心原则**：Chrome 150+ 时代，**协作模式 B 已成为强校验表单场景的默认入口**，
> 不再只是"AI 自动失败后的回退"。

**真实用户复盘（2026-07）**：

| 阶段 | 内容 |
|:-----|:-----|
| **背景** | Chrome 150 起强制 `--remote-allow-origins=*`；强校验表单场景，AI 自动化点击会被识别为机器人 |
| **L1 坑** | Playwright / DrissionPage 默认只 attach 到顶层 page Target；SPA 内部 fetch 走了 worker/iframe 副 target，`Network.requestWillBeSent` 根本不发到主 session |
| **L2 坑** | Chrome 150 起新增了 `--remote-allow-origins` Origin 校验；任何非浏览器/扩展来源的 WebSocket 直连 9222 都会被 403 Forbidden |
| **L3 坑** | AI 自己 `Target.createTarget` 拉起了新 tab，但最终在 attach 时挑中了自己创建的那个 tab（EAF22CC9AD995855B401），而不是用户 Chrome 自己的结果页 tab（4252F91C4CC929918E03），所以一直收不到 POST |
| **突破** | attach 到用户真实的 page target（4252F91C4CC929918E03）+ **不驱动表单** + **让用户手动点一次触发 POST**，1 秒内抓到 200 响应 |

**SOP 提炼**：

1. **接管前必检**：`curl http://localhost:9222/json | jq '.[] | {type, url}'`
   列出所有 target，按 type 分流 attach；worker/iframe/SW target 必须单独
   `Network.enable`
2. **启动命令必传 `--remote-allow-origins=*`**：Chrome 150+ 强校验，否则
   `403 Forbidden`
3. **禁止 `Target.createTarget`**：必须从 `user.contexts[i].pages` 中按 URL /
   title 匹配真实 page target
4. **强校验表单不驱动**：让用户手动点一次，AI 只监控抓包
5. **抓不到先查漏抓 7 层**（《爬虫工具与抓包规范》§3.9），**禁止**直接把"抓不到"
   等同于"接口不存在"

#### §3.0.7 cURL 12 项快速帮助清单（**v2.16.0 新增，模式 C 扩展**）

> **核心原则**：用户提供 cURL 是已知接口的**最高价值告知形式**——比"用户告知
> URL/参数"信息密度高 10 倍。AI 必须按 12 项清单最大化利用。

**12 项直接获得**（无需任何逆向）：

| # | 字段 | 来源 | 用途 |
|:--|:-----|:-----|:-----|
| 1 | 完整 URL（含 query） | cURL | 直接喂 `curl_cffi` / `requests` 实测 |
| 2 | HTTP Method | `-X` / `--request` | 排除 GET/POST 歧义 |
| 3 | 完整 Headers | `-H` | 直接拿到 `Cookie` / `Authorization` / `x-sign` / `x-csrf` / `x-token` / `referer` / `origin` |
| 4 | 完整 Body | `-d` / `--data` / `--data-raw` | 直接拿到 payload 结构（含加密字段 `sign=xxx` / `timestamp=xxx`） |
| 5 | HTTP version | 默认推断 | 推断是 H1 还是 H2 |
| 6 | 压缩 / 编码 | `--compressed` / `Accept-Encoding` | 推断响应是否 gzip/br |

**4 项快速验证**（替代抓包阶段）：

| # | 验证 | 含义 |
|:--|:-----|:-----|
| 7 | 重放验证 | 把 cURL 改 cookie/token/sign → 立刻知道哪些参数必传、哪些可空、哪些强校验 |
| 8 | 加密字段识别 | Headers 含 `x-sign: xxx` + Body 含 `sign=xxx&timestamp=xxx&nonce=xxx` → **3 秒定位加密链路** |
| 9 | 替代抓包 | 如果用户给的 cURL 已能稳定返回业务数据 → **直接跳过抓包阶段**，进入算法还原 |
| 10 | 跨协议复用 | cURL URL 直接喂给 `curl_cffi` 协议层，作为首次实测验证 |

**2 项工具化增益**（AI 分析时按需转换，**不引入独立工具脚本**）：

| # | 增益 | 说明 |
|:--|:-----|:-----|
| 11 | cURL → Python 代码生成 | AI 在分析时按需用 `python -c` + `curlconverter` 库一行生成 `requests` / `httpx` / `curl_cffi` 调用；**不**新建独立 `curl_parser.py` 工具 |
| 12 | cURL → Playwright route() mock | AI 在分析时按需用 Python 把 cURL 转成 `page.route(url, lambda route: route.fulfill(...))` 模板 |

**4 项 cURL 不包含**（**必须告知用户**）：

- ❌ **响应体**（响应头除外）—— 用户需单独贴响应
- ❌ **端口**（非标准端口场景）
- ❌ **真实浏览器指纹**（TLS JA3 / TLS fingerprint / Canvas / WebGL）
- ❌ **客户端中间产物**（动态 token 的生成过程只能从 cURL 推断起点）

#### §3.0.8 cURL → 代码转换 SOP 提示（**v2.16.0 新增**）

> **核心原则**：cURL → Python 代码转换是**分析能力**而非**独立工具**——
> AI 在分析阶段按需用 `python -c` 在线转换即可，不引入独立脚本文件。

**AI 分析 cURL 的标准 SOP 流程**：

```
1. 用户贴 cURL → AI 不立即录入接口，先按 §3.0.7 12 项清单提取字段
2. AI 用 python -c + curlconverter 在线生成 Python 调用：
   python -c "
   import curlconverter
   code = curlconverter.to_python('''<用户的 cURL 命令>''')
   print(code)
   "
   生成 requests / curl_cffi / httpx 三选一的 Python 代码
3. AI 立刻用生成的代码实测一次（替代抓包阶段）
4. 实测成功后录入接口清单，标 [🎯]（已实测 + 来源=cURL）
5. 告知用户 cURL 不包含的内容（响应体 / 端口 / TLS 指纹 / 中间产物）
```

**为什么不引入独立 `curl_parser.py` 工具脚本**：

- ✅ `curlconverter` 是稳定成熟的 Python 库，无需自造轮子
- ✅ cURL 解析是**一次性分析动作**，不是模块化复用场景
- ✅ AI 用 `python -c` 在线转换**比启动一个独立脚本更轻量**
- ✅ 避免新增工具脚本带来的 `DEFAULT_CURL_PARSER` 常量、模块 docstring、
  check-readme-sync 校验项等同步开销
- ✅ YAGNI 守边界——除非出现 ≥ 3 个不同项目都需要稳定 cURL 解析，否则不引入

### 3.4 接口功能实测验证原则（**v2.9.3 铁律** + **v2.9.5 置信度增强**）

> **核心原则**：在 `接口清单.md` 写「这个 URL 是干嘛的 / 这个参数是加密的 /
> 这个响应字段是用户数据」等结论前，**必须实测一次**。**禁止凭接口名/参数名/
> 字段名凭空判断**。

**实测流程**（**必走**）：

1. **标定核心接口**：在抓包结果中识别出"看起来像核心业务接口"的 URL（命中 §3.2 特征）
2. **发起实测请求**：用《爬虫工具与抓包规范》§5 的 `curl_cffi` 或工具册 §3 的
   `playwright` 发起一次**带真实 header/cookie/参数**的请求
3. **保存响应样本**：把响应原文（**脱敏后**）落到 `02-接口分析/响应样本/{slug}.json`
4. **在 `接口清单.md` 写结论**：基于实测响应**确认**接口功能（不是猜）

**示例（反例 → 正例）**：

```markdown

# ✅ 正例（基于实测）

  - 响应字段：`{code: 0, data: {uid, nickname, avatar, ...}}`
  - 结论：返回登录态用户的基础资料
```

## 4. 请求结构分析

### 4.1 URL 与 Query 参数

- 路径参数 vs Query 参数 vs Body 参数的区别
- 必填 vs 选填（看哪些参数每次都发、哪些偶尔发）
- 命名规律（`id`、`pid`、`uid`、`biz_id`、`trace_id` 等）

### 4.2 Header / Cookie / Token

- **必看 Header**：`User-Agent`、`Referer`、`Origin`、`Cookie`、`Authorization`、
  `X-*` 自定义头
- **Token 来源**：
  - 登录接口返回 → 缓存复用
  - 每次请求动态生成 → 看是否参与签名（多数情况是）
  - 第三方 OAuth → 看是否有 refresh 机制

### 4.3 Body 形式

- `application/x-www-form-urlencoded`：表单提交（key=value&...）
- `application/json`：JSON 体（最常见）
- `multipart/form-data`：文件上传
- 二进制：protobuf / MessagePack（**高难度**，需逆向 IDL）

### 4.4 分页机制

| 形式 | 参数 | 特点 |
|:-----|:-----|:-----|
| 偏移分页 | `page`、`page_size` | 简单 |
| 游标分页 | `cursor`、`last_id` | 性能好、爬取全量需记录 cursor |
| 时间分页 | `since`、`until` | 增量同步 |
| 加密游标 | `cursor=xxx`（密文） | **需逆向** |

### 4.5 鉴权方式

| 方式 | 特征 | 应对 |
|:-----|:-----|:-----|
| **Cookie** | `Cookie: session=xxx` | 复用浏览器 Cookie |
| **Bearer Token** | `Authorization: Bearer xxx` | 看 token 有效期 |
| **签名头** | `X-Sign: xxx` | **需逆向**（见《爬虫Web逆向规范》§1） |
| **双因素** | Cookie + 签名头 | 两个都要解决 |

### 4.6 加密参数的初步识别（**核心**）

**风控参数常见 5 类**（**必查**）：

| 参数名（模糊匹配） | 含义 | 应对难度 |
|:-----------------|:-----|:---------|
| `sign` / `signature` / `sig` | 请求签名（核心反爬） | **高** |
| `token` / `access_token` / `auth` | 鉴权令牌（可绕过/可复用） | 中 |
| `_ts` / `timestamp` / `t` | 时间戳（防重放） | 低（跟随即可） |
| `nonce` / `uuid` / `rid` | 一次性随机串（防重放） | 低（跟随即可） |
| `device_id` / `fp` / `fingerprint` / `umid` | **设备指纹** | **高** |
| `x-ticket` / `x-token` / `x-sign` | 自定义头签名 | **高** |

**判定原则**：参数值是 32/64 位十六进制、Base64 字符串、时间戳+nonce 组合
→ 大概率是加密/签名 → 进入《爬虫Web逆向规范》§1 加密参数定位。

## 5. 响应结构分析

### 5.1 数据字段提取路径

- 响应通常是 JSON：`{ "code": 0, "msg": "ok", "data": { ... } }`
- 重点看 `code` 字段（业务状态码 ≠ HTTP 状态码）
- 列表接口：`data.list` 或 `data.records` 或 `data.items`

### 5.2 响应加密/压缩识别

| 现象 | 识别 | 应对 |
|:-----|:-----|:-----|
| 响应是乱码字符串 | Base64 / 加密 | 看响应头 `Content-Encoding` |
| 响应体很短（< 50B）但页面有数据 | 加密 + 客户端解密 | 需逆向客户端解密逻辑 |
| 响应是二进制 | protobuf / MessagePack | 需逆向 IDL |

### 5.3 空响应与风控响应

- HTTP 200 + 空 body → 可能是被风控拦截
- HTTP 403 / 429 / 503 → 限频或被封
- 业务 `code: 401` / `code: 403` → Token 过期或权限不足
- 业务 `code: -1` + `msg: "风控拦截"` → 需绕风控

**应对**：记录典型风控响应特征，作为自动检测脚本的判定依据。

## 6. 反爬强度评估

### 6.1 L1-L5 难度分级（**v2.7.0 新增**）

| 难度 | 特征 | 首选方案 |
|:-----|:-----|:---------|
| **L1 明文** | GET/POST 无加密 | 直接采 |
| **L2 简单编码** | Base64 / URL 编码 / 固定密钥 AES | 一次性还原 |
| **L3 动态签名** | HMAC、时间戳参与 | Web JS 逆向（见《爬虫Web逆向规范》§1-§2） |
| **L4 设备指纹 + 行为** | Canvas / WebGL / 鼠标轨迹 | 逆向 + 浏览器环境模拟（**Playwright stealth**） |
| **L5 风控引擎** | 服务端实时风控决策 | **降级**（降频/人工/官方 API） |

### 6.2 反爬维度清单（评估项）

| 维度 | 评估内容 | 应对 |
|:-----|:---------|:-----|
| **限频规则** | 多少请求/秒触发限制？429 状态码？ | 加 `time.sleep` / 代理池 |
| **UA / 指纹校验** | 校验 User-Agent？校验 TLS 指纹（JA3）？ | 随机 UA / `curl_cffi` 模拟 TLS |
| **Cookie 时效** | Cookie 多久过期？是否含登录态？ | 自动登录 / Cookie 池 |
| **验证码触发条件** | 多少次请求后触发？哪种类型？ | 人工打码 / OCR / 打码平台 |
| **风控信号** | 服务端实时风控？是否有 device_id 校验？ | 逆向算法 + 模拟设备指纹 |

### 6.3 评估输出

写到 `02-接口分析/反爬评估.md`，结论包括：
- 综合难度等级（L1-L5）
- 主要反爬维度（限频 / UA / Cookie / 验证码 / 风控）
- 应对策略：是直接采（用《爬虫规范》骨架）还是进入第二部分逆向

### 9.4 模块真实可用性验收（**v2.12.0 新增**）

> **目标**：把"算法正确"推进到"用户要求的业务功能真的可用"。本节是
> `mcpowers-crawler-reverse` 阶段 5.5 的方法论依据；只有验收 `PASS` 才能沉淀
> 案例或创建完整骨架。

#### 9.4.1 四层证据不可混用

| 证据层 | 证明内容 | 不能外推为 |
|:-------|:---------|:-----------|
| **算法正确性** | ≥ 3 组还原值与真实值一致 | 服务端会接受请求 |
| **协议有效性** | 一次真实请求被接受 | 业务功能完整、可重复使用 |
| **业务完整性** | 用户要求的字段/副作用正确 | 跨会话、TTL、并发稳定 |
| **运行稳定性** | 重复、生命周期和目标并发实测通过 | 未测试环境下永久有效 |

验收前必须写清输入、模块公开入口、核心业务动作、业务成功断言、运行前提和目标
并发。业务成功必须校验响应业务码、关键字段、数据数量或实际副作用，禁止只检查 HTTP 200。

#### 9.4.2 串行重复与冷启动

从模块公开入口执行，而不是复用分析临时代码：

1. 至少 2 组业务输入，合计连续调用 ≥ 5 次，小样本门禁要求全部满足业务断言
2. 至少覆盖 2 个独立 session 或冷启动环境，排除 DevTools 上下文、进程全局变量和
   残留 token 依赖
3. 记录时间、脱敏输入摘要、HTTP/业务状态、关键字段、耗时和失败原因
4. 任一核心业务动作未完成，回到接口分析、算法还原或模块实现，不能留给项目骨架补救

#### 9.4.3 报文生命周期矩阵

§4.2 的 Cookie/Token、§4.6 的 timestamp/nonce 和《爬虫Web逆向规范》§3.3 的动态参数
必须通过以下最小矩阵确认：

| 测试 | 操作 | 识别目标 |
|:-----|:-----|:---------|
| **原报文重放** | 完全相同报文额外发送 1 次 | 是否单次消费或防重放 |
| **动态参数重生成** | 业务输入不变，重新生成动态参数 | 是否能持续构造有效新报文 |
| **跨 session 重放** | 新 session 先用旧状态，再用新状态对照 | 是否绑定 Cookie、账号、设备或会话 |
| **延时 / TTL** | 根据过期字段、已知 TTL 或合理短间隔复测 | 是否受时间窗口约束 |

关键状态统一分类：

- `reusable`：仅在已验证范围内可重复使用，不得表述为永久有效
- `per-request`：每次请求重新生成
- `single-use-token`：服务端消费一次即失效，每次调用前重新获取
- `session-bound`：按 Cookie / 账号 / 设备 / session 隔离
- `time-bound`：记录 TTL 并在过期前刷新
- `challenge-bound`：封装完整"获取 challenge → 生成参数 → 请求"链路
- `unknown`：证据不足；禁止写成可复用，影响验收契约时不能 PASS

原报文重放失败不等于逆向失败。只要模块能按已确认生命周期持续生成有效新报文，
并满足业务契约，即可继续验收。

#### 9.4.4 有界并发稳定性

并发验证只用于发现共享状态污染，**不是压力测试**：

1. 按并发 2 → 5 递增，每级使用最小批量
2. 分别使用相同输入和不同输入，检查 nonce/token 重用、session 线程安全、参数
   串值和结果交叉污染
3. 记录总数、业务成功数、401/403/429/5xx、验证码次数、P50/P95、session 策略和
   失败原因
4. 出现 429、验证码增加、账号安全提示、目标异常、robots/服务条款/授权不允许
   时立即停止
5. 用户要求的目标并发未通过或未能证明时，不能 PASS

完整项目的线程池、Session 池、代理池、Redis 锁等工程设施仍按《爬虫规范》实施；
轻量模块只保留完成真实调用所需的最小状态生命周期，优先使用实例/调用级状态，
禁止模块级可变全局状态。

#### 9.4.5 判定与报告

| 状态 | 条件 | 行为 |
|:-----|:-----|:-----|
| **PASS** | 当前验收契约的业务、重复、生命周期、跨会话/时效和目标并发均有实测证据 | 可进入案例沉淀和落地决策 |
| **CONDITIONAL** | 存在未被契约接受的限制，或关键生命周期仍为 `unknown` | 不得落地；调整契约后补测，满足后才能改为 PASS |
| **FAIL** | 核心业务失败、无法持续生成有效报文、状态污染或目标并发失败 | 返回对应分析/还原/封装步骤 |

统一报告到 `04-模块封装/{module}/验收报告.md`：测试环境、验收契约、
串行结果、生命周期矩阵、并发结果、停止原因、已知限制、最终状态和证据路径。
`verify.py` 未实际执行、报告缺证据或只检查 HTTP 200，均视为 FAIL。

#### 9.4.6 模块产物封装形式约束（**v2.17.0 新增**）

> **核心原则**：阶段 5 模块化封装必须满足 4 类约束——类式封装、请求与解析
> 分离、零前置参数调用、`quick_test.py` 手动验证入口。除非类无法满足，
> 否则一律用类；分析阶段的临时参数（token / cookie / sign / nonce /
> challenge）禁止固化进模块产物。

##### 9.4.6.1 类式封装约定（v2.17.0 起强制）

模块产物**默认以类（class）形式封装**。理由：状态封装 + SOLID 单一职责 +
后续扩展友好 + 与《爬虫规范》项目骨架的 `Spider`/`Pipeline` 类风格一致。

**目录结构**（v2.17.0 起强制）：

```text
04-模块封装/{module}/
├── __init__.py          # 暴露主入口类（from .client import ModuleClient）
├── client.py            # 模块入口类（v2.17.0 起替代 functions.py）
├── constants.py         # 稳定常量（不含抓包临时值）
├── README.md            # 模块公开 API + 业务用例
├── quick_test.py        # 手动快速验证（v2.17.0 新增，必备）
├── test_*.py            # pytest 单元测试（可选）
├── verify.py            # 阶段 5.5 真实可用性验收脚本
└── 验收报告.md
```

**入口类设计**（`client.py`）：

```python
class ModuleClient:
    """模块入口类：所有业务调用都通过此类。

    业务调用方法只接收业务参数（item_id、query 等），
    token / cookie / sign / nonce / timestamp 由本类内部自动生成。
    """

    def __init__(self, base_url: str = "...", proxy: str = None):
        # 只接收配置参数（一次性配置），不接收业务参数
        ...

    def build_request(self, business_input: dict) -> "Request":
        """仅构造请求报文（不发送），返回可调试的 Request 对象。"""
        ...

    def do_request(self, business_input: dict) -> "Response":
        """构造并发送请求，返回原始响应。"""
        ...

    def parse_response(self, response, business_input: dict) -> "ParsedData":
        """解析响应为业务数据。"""
        ...

    # 便捷方法：业务需要数据时按顺序调用
    def request_and_parse(self, business_input: dict) -> "ParsedData":
        """do_request + parse_response 串行（业务需要数据时用这个）。"""
        response = self.do_request(business_input)
        return self.parse_response(response, business_input)
```

**保留函数式的例外**（满足任一即可）：

- 纯算法函数（如：`def md5_with_salt(s: str) -> str`）
- 字典映射常量（如：`POPUP_TYPE_RULES: dict`）
- 配置读取器（如：`def load_config(path: str) -> Config`）
- 单条业务逻辑（如：`def normalize_phone(phone: str) -> str`）

##### 9.4.6.2 请求与解析分离（SRP）

类内部**请求构造/发送**和**响应解析**是两个独立方法（`do_request` /
`parse_response`），**不**合并为单个大方法。理由：

- ✅ 业务只需要报文（和别的系统对账、断点重传、自定义重试）→ `build_request()`
- ✅ 业务需要原始响应（自定义解析、debug）→ `do_request()`
- ✅ 业务需要数据（默认场景）→ `request_and_parse()` 便捷方法
- ✅ 单元测试可分别 mock 请求和响应

**禁止**：

- ❌ 单个 `fetch_data(business_input)` 同时做请求+解析，无法单独使用
- ❌ 把解析逻辑藏在 `__init__` 或模块级全局函数里
- ❌ `do_request` 内部直接返回解析后的数据（应返回原始 Response）

##### 9.4.6.3 零前置参数调用（业务调用方法）

**业务调用方法**（`request_and_parse` / `do_request` / `parse_response` /
`build_request`）**只接收业务参数**（如 `item_id`、`query`、`page_num`）。
**禁止**要求调用方传入：

- ❌ `token` / `cookie` / `session_id` / `authorization`
- ❌ `sign` / `signature` / `nonce` / `timestamp` / `challenge`
- ❌ `device_id` / `fingerprint` / `ua`
- ❌ 任何抓包临时参数（即使作为"默认参数"也不允许）

**模块内部自动生成**——按 §9.4.3 生命周期分类（`reusable` / `per-request` /
`single-use-token` / `session-bound` / `time-bound` / `challenge-bound` /
`unknown`）实现自洽。`unknown` 必须升级到具体类型才能 PASS。

**允许**接收的配置参数（一次性，写进 `__init__`）：

- ✅ `base_url` / `endpoint` / `host`
- ✅ `proxy` / `timeout` / `verify_ssl`
- ✅ `debug` / `dry_run` / `screenshot_dir`

**反模式**：

- ❌ `client.request_and_parse(item_id, token=xxx, cookie=xxx, sign=xxx)`
- ❌ 把抓包临时 token 写进 `constants.py` 作为 `DEFAULT_TOKEN`
- ❌ 业务用例写死 `token = "eyJ..."`（违反"项目可直接复用"原则）

##### 9.4.6.4 `quick_test.py` 手动验证入口（v2.17.0 新增，必备）

每个模块**必须**有 `quick_test.py`，提供 `if __name__ == "__main__":` 模式的
手动快速验证入口。**与 verify.py 验收脚本严格区分**：

| 文件 | 用途 | 调用方式 | 何时用 |
|:-----|:-----|:---------|:------|
| **`quick_test.py`** | **手动快速验证**（直接 `python quick_test.py`） | `if __name__ == "__main__":` 内硬编码测试输入 | 改完模块立刻验证逻辑 |
| `test_*.py` | **pytest 单元测试**（CI 跑） | `pytest test_*.py` | 持续集成 |
| `verify.py` | **真实可用性验收**（§9.4.5 跑生命周期矩阵） | argparse + 真实业务流 | 阶段 5.5 验收 |

**模板**（`quick_test.py`）：

```python
"""quick_test.py — 模块快速验证（可直接 python quick_test.py 运行）

演示 3 类典型用法：
1. 业务需要数据：按顺序调用 request_and_parse
2. 业务只要报文：单独调 build_request
3. 业务需要原始响应：单独调 do_request

零前置参数：调用方不需要传入 token / cookie / sign 等抓包临时参数，
模块内部自动生成。
"""
from client import ModuleClient


if __name__ == "__main__":
    client = ModuleClient()

    # 1. 业务需要数据：按顺序调用
    data = client.request_and_parse({"item_id": "12345"})
    print(f"[业务数据] {data}")

    # 2. 业务只要报文：单独调 build_request
    req = client.build_request({"item_id": "12345"})
    print(f"[请求报文] {req.method} {req.url}")
    print(f"[请求头] {req.headers}")
    print(f"[请求体] {req.body}")

    # 3. 业务需要原始响应：单独调 do_request
    resp = client.do_request({"item_id": "12345"})
    print(f"[响应] HTTP {resp.status_code}")
    print(f"[响应体] {resp.text[:200]}")
```

**禁止**：

- ❌ `if __name__ == "__main__": sys.argv` 解析参数（违反 KISS，应改用测试文件）
- ❌ 把 quick_test 写在 `__init__.py`（污染包入口，破坏零前置参数语义）
- ❌ 把 `verify.py` 当手动测试用（启动成本高，违反单一职责）
- ❌ `quick_test.py` 不写示例输入就直接 `exit()`（失去手动验证意义）
- ❌ `quick_test.py` 在 `__main__` 内 `import` 抓包样本（如 `tokens.py`），违反"零前置参数"边界

## 11. 验证码与风控应对

### 11.1 验证码类型与应对

> **v2.9.3 铁律**：遇到任何类型验证码，**AI 必须主动解决**，**不得以"难以绕过"
> 为由建议人工**。行为验证码的"通常降级"已改为"先穷尽自研手段再降级"。

| 类型 | 特征 | 应对方案（**v2.9.3 主动解决**） |
|:-----|:-----|:---------|
| **图形验证码**（简单） | 4-6 位数字字母 | **主动解决**：Tesseract / PaddleOCR / 打码平台（主动调用，**不推人工**） |
| **滑动验证码** | 拼图 + 滑动轨迹 | **主动解决**：轨迹模拟（贝塞尔曲线 + 随机扰动）+ OpenCV 缺口识别 + 行为轨迹拟合（**不推人工**） |
| **点选验证码** | 按顺序点击文字 | **主动解决**：OCR（点选文字识别）+ 行为轨迹拟合 + 必要时打码平台（**不推人工**） |
| **行为验证码**（极验/腾讯） | 拖动 + 行为评分 | **先穷尽自研**：1) 行为轨迹深度拟合（贝塞尔 + 加速度曲线 + 鼠标抖动）2) JS 逆向获取 gt/challenge 3) 真实浏览器 CDP 接管（详见《爬虫工具与抓包规范》§3）。**仅当以上全部失败才降级** |
| **短信验证码** | 短信下行 | 接码平台（合规敏感，需用户明确授权） |

### 11.2 风控参数生成还原

**设备指纹**（常见 5 类）：

| 维度 | 生成方式 | 模拟难度 |
|:-----|:---------|:---------|
| **浏览器指纹**（Web） | UA + Canvas + WebGL + 字体列表 | 中（Playwright stealth） |
| **设备指纹**（APP） | `IMEI` + `MAC` + `Android ID` + `OAID` | 高（需 root 改值） |
| **行为轨迹** | 鼠标轨迹 + 滑动速度 + 点击间隔 | 高（行为评分模型） |
| **IP 风险** | IP 信誉库 + ASN + 地理位置 | 中（高质量代理池） |
| **账号风险** | 登录设备数 + 登录频率 + 异地登录 | 高（养号） |

**应对决策树**（**v2.9.3 强化：先防御再主动解决再降级**）：

1. **第 1 步：指纹防御（默认已开）** —— `playwright-stealth` + UA/视口/时区合理随机 +
   行为模式伪装 + Cookie 持久化
2. **第 2 步：仅 L4 设备指纹** —— 逆向生成算法 + Playwright/真实设备模拟
3. **第 3 步：含 L5 风控引擎** —— 优先**主动解决**（行为轨迹深度拟合 + JS 逆向 +
   真实浏览器 CDP 接管，详见《爬虫工具与抓包规范》§3），仅当全部失败才**降级**
   （降频 / 购买数据 / 走官方 API / 人工打码）
4. **风控决策误判可申诉**：少数场景支持人工申诉

### 11.3 风控对抗速查

| 难度 | 特征 | 首选方案 |
|:-----|:-----|:---------|
| L1 明文 | GET/POST 无加密 | 直接采 |
| L2 简单编码 | Base64/URL编码/固定密钥 | 一次性还原 |
| L3 动态签名 | HMAC、时间戳参与 | Web JS 逆向（《爬虫Web逆向规范》§1-§2） |
| L4 设备指纹 + 行为 | Canvas/WebGL/鼠标轨迹 | 逆向 + 浏览器环境模拟 |
| L5 风控引擎 | 服务端实时决策 | **先主动解决**（行为轨迹深度拟合 + JS 逆向 + 真实浏览器 CDP 接管，工具册 §3），**仅当全部失败才降级**（降频/购买数据/官方 API/人工打码） |
