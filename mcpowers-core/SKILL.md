# mcpowers-core

轻量级通用工作流，独立于任何技术栈。

## 核心原则

### 红线行为
| 红线 | 说明 |
|:-----|:-----|
| 未经确认直接修改 | 用户未确认前不得执行任何修改 |
| 先代码后文档 | 接口必须先写文档再写实现 |
| 多个操作后才 commit | 每个任务完成后立即 commit |

### 基本要求
- **修改前**：必须分析影响、询问确认
- **修改时**：必须同步更新所有相关文件
- **完成时**：必须立即 commit
- **代码注释**：函数/类/复杂逻辑必须有完整注释

---

## 流程步骤

### Step 0：确认需求

**执行内容**：
1. 询问用户项目类型（Web/桌面/移动/其他）
2. 询问是否有设计文档或原型
3. 询问是否有技术偏好

**输出**：
```
## 需求确认

- 项目类型：{类型}
- 设计文档：{有/无}
- 技术偏好：{用户选择}
- 下一步：进入 Step 1
```

---

### Step 1：制定方案

**执行内容**：
1. 根据需求制定技术方案
2. 确定项目结构
3. 确认用户是否同意

**输出**：
```
## 技术方案

- 技术选型：{方案}
- 项目结构：{目录}
- 确认后进入 Step 2
```

---

### Step 2：执行开发

**执行内容**：
1. 按方案执行开发
2. 每个功能完成后 commit
3. 保持与用户沟通进度

**自检**：
- [ ] 代码是否符合方案？
- [ ] 注释是否完整？
- [ ] commit 是否及时？

---

### Step 3：交付

**执行内容**：
1. 最终检查
2. 整理文档（如需要）
3. 提交代码

---

## Git 规范（简化版）

### commit 格式
```
<类型>: <简短描述>

<可选详细说明>
```

**类型**：
| 类型 | 说明 |
|:-----|:-----|
| feat | 新功能 |
| fix | 修复 |
| docs | 文档 |
| refactor | 重构 |
| test | 测试 |
| chore | 杂项 |

### 分支管理
| 分支 | 说明 |
|:-----|:-----|
| master | 主分支 |
| dev | 开发分支 |
| feature/xxx | 功能分支 |

---

## 变更处理

当需求变更时：
1. **评估影响**：确定涉及范围
2. **确认变更**：告知用户影响
3. **执行变更**：按新需求执行
4. **同步更新**：更新相关文档和代码

---

## 临时文件

- 临时文件放在 `temp/` 目录
- 用完即删，不堆积
- 不提交到 git

---

## 自检清单

每次 commit 前检查：
- [ ] 用户已确认修改内容
- [ ] 代码注释完整
- [ ] 无临时文件遗留
- [ ] commit 信息规范
