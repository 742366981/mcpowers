AI辅助开发的标准化工作流程技能。

## 0. 速查表（强制）

> ⚠️ **AI 每次任务开始前，必须先确认以下事项**

### 强制执行项
- [ ] **修改前**：必须先分析影响、询问确认
- [ ] **修改时**：必须遵守 `docs/技术规范/代码同步修改规范.md`
- [ ] **完成时**：必须立即 commit（禁止多个操作后才 commit）
- [ ] **接口开发**：必须先写 docstring，再写实现
- [ ] **代码注释**：函数/类/复杂逻辑必须有完整注释
- [ ] **临时文件**：必须放在 `temp/` 目录，用完即删

### 禁止项
- ❌ 未经用户确认直接修改任何代码/文档
- ❌ 先写代码后补文档
- ❌ 只 commit 代码不 commit 文档
- ❌ 多个文档重复定义相同内容
- ❌ 在项目目录创建临时文件

## 1. 核心原则（强制）

> ⚠️ **强制（红线）**
>
> 以下行为是 AI 操作的**红线**，违反将被视为不合格：

| 红线行为 | 说明 | 违规后果 |
|:---------|:-----|:---------|
| **未经确认直接修改代码/文档** | 用户未确认前不得执行任何修改 | 用户有权要求回滚 |
| **先写代码后补文档** | 接口必须先写 docstring 再写实现 | 视为不合格 |
| **多个操作后才 commit** | 每个独立任务完成后必须立即 commit | 视为不规范 |
| **只 commit 代码不 commit 文档** | 代码和文档变更必须同时提交 | 视为不规范 |
| **发现重复定义未处理** | 冗余内容必须删除，保留一处 | 视为不合格 |
| **代码注释不完整** | 所有代码必须有完整注释（见本章第1.5节） | 视为不合格 |
| **临时文件不清理** | 调试文件用完即删，不堆积 | 视为不规范 |
| **代码质量不合格** | 违反 SOLID/KISS/DRY/YAGNI 原则 | 视为不合格 |

### 1.1 修改前必须询问

**禁止直接修改任何代码/文档**。当用户要求修改时，AI 必须：

1. **先分析** - 理解需求和影响范围
2. **先检查** - 查阅 `docs/技术规范/代码同步修改规范.md`，确认需要同步哪些文件
3. **先询问** - 确认方案是否符合预期
4. **再执行** - 用户确认后才修改

### 1.2 变更必须同步

任何代码变更，**必须同步更新所有受影响的文件**。详见 `docs/技术规范/代码同步修改规范.md`。

### 1.3 每次操作后必须 commit（强制）

**禁止一次性做多个操作后再 commit**，也**禁止只 commit 代码不 commit 文档**。

每个独立任务完成后**必须立即 commit**：
- 完成一个接口 → 立即 commit
- 完成一个文档 → 立即 commit
- 完成一个配置修改 → 立即 commit

详见 `docs/技术规范/Git规范.md`。

### 1.4 接口必须先写文档（强制）

**禁止先写代码后补文档**，也**禁止不写接口文档**。

每个接口开发时，必须：
1. **检查模板文件** - 详见 `docs/技术规范/Flask后端规范.md` 第13章
2. **编写**视图函数docstring - 详见 `docs/技术规范/Flask后端规范.md` 第13章
3. **编写**视图函数实现
4. **完成后**运行导出脚本生成可读文档

### 1.5 代码注释必须完整（强制）

**所有代码必须有完整注释**，包括但不限于：

| 代码类型 | 注释要求 | 示例 |
|:---------|:---------|:-----|
| **函数/方法** | 必须有 docstring，说明功能、参数、返回值 | `"""获取用户信息\n\nArgs:\n    user_id: 用户ID\n\nReturns:\n    User: 用户对象\n"""` |
| **类定义** | 必须有类注释，说明用途 | `"""用户模型类\n\n用于管理用户数据的增删改查操作\n"""` |
| **复杂逻辑** | 关键判断、分支必须有注释 | `# 超过阈值才入库，避免噪音数据` |
| **常量定义** | 必须有注释说明用途 | `# 每页返回的最大记录数` |
| **配置文件** | 必须有注释说明配置项含义 | `# 数据库连接池大小` |

**注释语言**：必须与现有代码库保持一致（自动检测）。

**禁止**：
- ❌ 空函数无注释
- ❌ 复杂逻辑无注释说明
- ❌ 配置项无注释
- ❌ 用注释替代完整文档

### 1.6 代码质量标准（强制）

**所有代码必须遵循以下质量原则**：

| 原则 | 说明 | 违反后果 |
|:-----|:-----|:---------|
| **SOLID原则** | 单一职责、开闭原则、里氏替换、接口隔离、依赖倒置 | 视为不合格 |
| **KISS原则** | 保持代码简洁易懂，避免不必要的复杂性 | 视为不合格 |
| **DRY原则** | 拒绝重复代码，相同逻辑只写一次 | 视为不合格 |
| **YAGNI原则** | 只实现当前明确所需的功能，拒绝过度设计 | 视为不合格 |

**代码质量检查清单**：

```
□ 函数是否单一职责（不超过50行）？
□ 是否有重复代码需要抽取？
□ 变量/函数命名是否清晰表达意图？
□ 是否有不必要的嵌套层级（不超过3层）？
□ 是否有硬编码需要提取为常量？
□ 是否有无用的导入或注释需要清理？
□ 是否符合当前项目的代码风格？
```

**违反示例**：

| 违反类型 | 错误示例 | 正确做法 |
|:---------|:---------|:---------|
| 违反单一职责 | 一个函数同时处理数据校验、业务逻辑、数据库操作 | 拆分为三个独立函数 |
| 违反DRY | 多处复制粘贴相同的校验逻辑 | 抽取为公共函数 |
| 违反KISS | 使用复杂的设计模式解决简单问题 | 使用最简单直接的方案 |
| 违反YAGNI | 提前实现"将来可能用到"的接口 | 只实现当前明确需要的功能 |

## 2. 修改前强制检查（强制）

### 2.1 修改技术规范文档时

修改 `docs/技术规范/` 下的任何文档时，**必须同步检查以下文件**：

| 修改内容 | 必须检查并更新的文件 |
|:---------|:-------------------|
| 新增技术规范文档 | 开发环境规范.md 中的模板、README.md |
| 删除技术规范文档 | 开发环境规范.md 中的模板、README.md |
| 修改技术规范文档 | 开发环境规范.md 中的模板、README.md |
| 新增产品设计文档 | 开发环境规范.md 中的模板、README.md |
| 新增入口文档（如入门指南） | README.md |

### 2.2 修改配置文件时

| 修改内容 | 必须检查并更新的文件 |
|:---------|:-------------------|
| 修改项目中的 CLAUDE.md | 必须同步检查 AGENTS.md |
| 修改项目中的 AGENTS.md | 必须同步检查 CLAUDE.md |
| 修改 AI操作规范.md | 检查是否需要同步到开发环境规范中的模板 |

### 2.3 检查原则

> ⚠️ **强制执行**
>
> 修改任何文件前，先问自己：
> 1. 这个文件是否有对应的同步文件（如 CLAUDE.md ↔ AGENTS.md、项目配置 ↔ 模板）？
> 2. 是否有其他文档引用了被修改的内容？
>
> 如有，必须**同时修改**，不得只改一处。

## 3. 边界场景处理（强制）

| 场景 | 处理方式 |
|:-----|:---------|
| 用户说"快点改一下" | 仍需询问确认，但可以简化确认方式（如"确认修改X？Y/N"） |
| 紧急修复bug | 仍需先询问，可以加快确认速度 |
| 规范之间冲突 | 优先顺序：核心约束（红线）> 禁止行为 > 建议做法 |
| 不确定是否需要修改 | 先询问用户，不要自行判断 |

## 6. 技术选型确定（强制）

### 6.1 技术选型询问

当进入**设计阶段**时，AI 必须询问用户确定技术选型：

```markdown
## 技术选型确认

请确认项目使用的技术栈：

### 后端技术（可选）
- [ ] Flask (Python)
- [ ] Node.js (Express/Koa/NestJS)
- [ ] Go (Gin/Fiber)
- [ ] Java (Spring Boot)
- [ ] 其他：

### 前端技术（可选）
- [ ] Vue 3
- [ ] React
- [ ] 小程序
- [ ] 其他：

### 其他技术
- [ ] 数据库：MySQL / PostgreSQL / MongoDB
- [ ] 缓存：Redis / Memcached
- [ ] 消息队列：（根据需要）

请确认后将在设计文档中明确技术选型。
```

### 6.2 技术规范识别

确定技术选型后，AI 自动识别对应的技术规范：

1. **检查 `docs/技术规范/` 目录**
   - 若有对应的技术规范 → 询问用户"是否遵守该技术规范？"
     - 若**遵守** → 在设计文档中注明，后续严格遵循
     - 若**不遵守** → 说明需要遵守的规范内容，由用户确认
   - 若**没有**对应的技术规范 → 询问用户"是否需要自动创建该技术规范？"
     - 若**需要** → 基于通用最佳实践创建技术规范文档

2. **技术规范范围**
   - 后端技术（Flask/Node.js/Go/Java等）→ 对应后端规范
   - 前端技术（Vue/React/小程序等）→ 对应前端规范
   - 数据库/缓存/消息队列 → 可选，需根据项目实际情况

## 7. 完整项目执行流程（强制）

### 7.1 阶段0：产品设计

```
┌─────────────────────────────────────────────────────────────┐
│                    阶段0：产品设计                      │
├─────────────────────────────────────────────────────────────┤
│  触发：用户只有想法/创意，没有原始需求时                 │
│  输入：用户想法/创意                                    │
│  输出：docs/原始需求/                                  │
│  动作：                                               │
│    1. 引导用户描述需求（按产品设计规范交互）           │
│    2. 生成原始需求文档                                 │
│    3. 保存到 docs/原始需求/                            │
│  依据：docs/产品设计/产品设计规范.md                   │
│  注意：若用户已有原始需求，跳过此阶段                  │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 阶段1：需求转换

```
┌─────────────────────────────────────────────────────────────┐
│                    阶段1：需求转换                      │
├─────────────────────────────────────────────────────────────┤
│  输入：docs/原始需求/                                    │
│  输出：docs/需求文档/                                   │
│  目的：                                               │
│    1. 精确完整提取原始需求信息                         │
│    2. 明确系统定位和边界                              │
│    3. 结构化组织，便于后续引用和开发                   │
│  动作：读取原始需求，转换为标准化需求文档               │
│  动作：识别下拉框/可配置字段，标注处理方式             │
│  输出文档应包含：                                     │
```

## 7.6 三阶段同步机制（强制）

需求、设计、代码三者必须保持同步，任何变更都必须向上下游传递。

### 7.6.1 同步关系图

```
┌──────────────────────────────────────────────────────────────┐
│                     三阶段同步机制                            │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│   ┌──────────┐      转换      ┌──────────┐     转化     ┌──────────┐     生成     ┌──────────┐     │
│   │ 原始需求  │ ───────────→ │ 标准需求  │ ──────────→ │ 设计文档  │ ──────────→ │   代码   │     │
│   └──────────┘              └──────────┘              └──────────┘              └──────────┘     │
│                                                              │
│         ↑                                    │                                    │                │
│         │              变更同步              ↓                                    │                │
│         │ ───────────────────────────────── ────────────────────────────────── →                │
│                                                              │
│         ↑                                                         │                │
│         │                    代码逆向修正（当代码实现方式与设计文档 │                │
│         │                    不一致时，以实际代码实现更新设计文档） │                │
│                                                              │
│   任意环节变更，都必须同步更新下游所有环节                        │
└──────────────────────────────────────────────────────────────┘
```

### 7.6.2 同步方向（强制）

| 同步方向 | 触发条件 | 同步内容 |
|:---------|:---------|:---------|
| **正向同步** | 需求变更 | 原始需求 → 标准需求 → 设计文档 → 代码 |
| **逆向修正** | 代码实现与设计文档不符 | 代码实现 → 更新设计文档 |

### 7.6.3 正向同步规则（强制）

| 变更环节 | 必须同步的下游 | 同步内容 |
|:---------|:---------------|:---------|
| 原始需求变更 | 标准需求 | 更新需求文档对应内容，标注变更点 |
| 标准需求变更 | 设计文档 | 更新设计文档对应内容，说明变更原因 |
| 设计文档变更 | 代码 | 更新代码实现，保持与设计文档一致 |

**正向同步必须按顺序执行，禁止跳级**：
```
需求变更 → 不允许直接改代码，必须先更新设计文档
```

### 7.6.4 逆向修正规则（强制）

| 触发情形 | 修正内容 | 说明 |
|:---------|:---------|:-----|
| 代码实现方式与设计文档描述不符 | 更新设计文档 | 以实际代码实现为准，修正设计文档 |
| 代码发现更优方案 | 先更新设计文档，再改代码 | 不得擅自改变设计，必须先走变更流程 |

### 7.6.5 禁止行为（强制）

| 禁止行为 | 说明 | 违规后果 |
|:---------|:-----|:---------|
| ❌ 代码与设计文档不一致 | 代码实现必须符合设计文档 | 视为不合格 |
| ❌ 设计文档与需求不一致 | 设计文档必须实现需求文档的内容 | 视为不合格 |
| ❌ 需求文档与原始需求不一致 | 需求文档必须准确反映原始需求 | 视为不合格 |
| ❌ 变更只改一处 | 变更必须同步所有下游文档和代码 | 视为不规范 |
| ❌ 跳过设计文档直接改代码 | 需求变更必须先更新设计文档 | 视为不合格 |
| ❌ 代码完成后不验证设计文档 | 每次代码变更后必须检查设计文档 | 视为不规范 |

### 7.6.6 变更处理流程（强制）

当任何环节发生变更时，必须按以下流程处理：

```
┌─────────────────────────────────────────────────────────────┐
│                    变更处理流程                              │
├─────────────────────────────────────────────────────────────┤
│  1. 评估影响                                                │
│     - 确定变更涉及的环节（需求/设计/代码）                   │
│     - 确定同步范围（哪些文档和代码需要更新）                 │
├─────────────────────────────────────────────────────────────┤
│  2. 执行同步                                                │
│     - 正向变更：按顺序更新需求→设计→代码                     │
│     - 逆向修正：更新设计文档以匹配代码实现                    │
│     - 同步时在变更处标注"【变更】"标记                       │
├─────────────────────────────────────────────────────────────┤
│  3. 验证一致                                                │
│     - [ ] 代码实现的功能点与设计文档一致                     │
│     - [ ] 设计文档的功能点与需求文档一致                     │
│     - [ ] 需求文档准确反映原始需求                           │
├─────────────────────────────────────────────────────────────┤
│  4. 记录变更                                                │
│     - 在变更处的注释中说明变更原因和同步关系                 │
│     - commit 时在 message 中标注涉及的同步变更              │
└─────────────────────────────────────────────────────────────┘
```

### 7.6.7 同步验证检查清单（强制）

每次变更完成后，必须逐项验证：

**正向同步验证**：
- [ ] 需求变更是否已同步到标准需求文档？
- [ ] 标准需求变更是否已同步到设计文档？
- [ ] 设计文档变更是否已同步到代码实现？

**逆向修正验证**：
- [ ] 代码实现与设计文档描述是否一致？
- [ ] 如有不一致，是否已更新设计文档？

**禁止项验证**：
- [ ] 是否有跳级变更（需求→代码，而没有更新设计）？
- [ ] 是否有只改代码而未验证设计文档的情况？
