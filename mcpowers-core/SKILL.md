# mcpowers-core

通用工作流技能，保留完整流程但不绑定特定技术规范。

## 0. 速查表

### 强制执行项
- [ ] **修改前**：必须先分析影响、询问确认
- [ ] **修改时**：必须同步更新所有相关文件
- [ ] **完成时**：必须立即 commit
- [ ] **接口开发**：必须先写文档再写实现
- [ ] **代码注释**：函数/类/复杂逻辑必须有完整注释
- [ ] **临时文件**：必须放在 `temp/` 目录，用完即删

### 禁止项
- ❌ 未经确认直接修改
- ❌ 先代码后文档
- ❌ 多个操作后才 commit
- ❌ 只 commit 代码不 commit 文档
- ❌ 在项目目录创建临时文件

---

## 1. 核心原则

### 红线行为

| 红线 | 说明 | 后果 |
|:-----|:-----|:-----|
| 未经确认直接修改 | 用户未确认前不得执行任何修改 | 用户有权要求回滚 |
| 先代码后文档 | 接口必须先写文档再写实现 | 视为不合格 |
| 多个操作后才 commit | 每个任务完成后必须立即 commit | 视为不规范 |
| 只 commit 代码不 commit 文档 | 代码和文档变更必须同时提交 | 视为不规范 |
| 代码注释不完整 | 函数/类/复杂逻辑必须有完整注释 | 视为不合格 |

### 修改前必须询问

1. **先分析** - 理解需求和影响范围
2. **先确认** - 确认方案是否符合预期
3. **再执行** - 用户确认后才修改

### 变更必须同步

任何代码变更，**必须同步更新所有受影响的文件**。

## 3. 完整项目执行流程

### 阶段0：产品设计

**前置判断：用户是否已有设计？**

- **A. 已有设计** → 直接使用，跳过引导
- **B. 部分设计** → 使用已有部分 + 引导生成缺失部分
- **C. 没有设计** → AI 按流程引导

**执行流程**（用户无设计时）：

1. **确认项目名称**（必须先问）
2. **初始化 Git 仓库**
3. **询问产品类型**（博客/电商/管理后台/其他）
4. **询问目标用户**（普通用户/企业内部/开发者/管理员）
5. **询问使用场景**（Web/移动端/桌面端/多端）
6. **询问功能模块**（用户/内容管理/搜索/消息通知/支付/统计）
7. **询问非功能需求**（性能/安全/兼容性/可靠性）
8. **生成原始需求文档**
9. **确认原型图**（有/无/暂不需要）

**输出文档**：
- 保存位置：`docs/原始需求/`
- 文件命名：`{项目名}_原始需求.md`

---

### 阶段1：需求转换

```
输入：docs/原始需求/
输出：docs/需求文档/

目的：
1. 精确完整提取原始需求信息
2. 明确系统定位和边界
3. 结构化组织，便于后续引用和开发

输出文档应包含：
- 项目概述（名称、背景、目标）
- 系统定位（边界、核心功能、用户角色）
- 功能需求（模块划分、功能点列表）
- 非功能需求（性能、安全等，如有）
- 数据字典（核心数据实体）
- 字段识别结果（基础数据表清单）
```

---

### 阶段2：设计生成

```
输入：docs/需求文档/
输出：docs/设计文档/

目的：
1. 确定技术选型和技术栈
2. 设计系统架构和模块划分

输出文档应包含：
- 系统概述（项目定位、主要功能）
- 技术选型（后端/前端/数据库/缓存等）
- 系统架构（模块划分、目录结构）
- 基础数据模块设计
```

**设计文档命名规范**：
| 技术选型 | 命名规则 |
|:--------|:---------|
| 后端 | `{项目名}_后端设计.md` |
| 前端 | `{项目名}_前端设计.md` |
| 数据库 | `数据库设计.md` |
| 接口 | `{项目名}_接口设计.md` |

---

### 阶段3：代码生成

```
输入：docs/需求文档/ + docs/设计文档/
输出：项目代码

要求：
1. 每个模块/组件先编写文档，再写实现
2. 同步编写配置文件
3. 每完成一个独立功能点，立即 commit

禁止：
- 先代码后文档
- 多个功能点完成后才 commit
- 只 commit 代码不 commit 相关文档
```

**代码质量原则**：
| 原则 | 说明 |
|:-----|:-----|
| SOLID | 单一职责、开闭原则、里氏替换、接口隔离、依赖倒置 |
| KISS | 保持简洁，避免不必要的复杂性 |
| DRY | 拒绝重复代码，相同逻辑只写一次 |
| YAGNI | 只实现当前明确所需的功能 |

---

### 阶段4：细节记录

```
输入：无（持续进行）
输出：docs/细节记录/

记录内容：
- 业务逻辑（复杂规则、判断条件）
- 技术实现（第三方集成、特殊配置）
- 踩坑记录（问题及解决方案）
- 注意事项（后续开发需关注的点）
```

## 4. 三阶段同步机制

需求、设计、代码三者必须保持同步，任何变更都必须向上下游传递。

### 同步方向

| 同步方向 | 触发条件 | 同步内容 |
|:---------|:---------|:---------|
| **正向同步** | 需求变更 | 原始需求 → 标准需求 → 设计文档 → 代码 |
| **逆向修正** | 代码实现与设计不符 | 代码实现 → 更新设计文档 |

### 正向同步规则

| 变更环节 | 必须同步的下游 |
|:---------|:---------------|
| 原始需求变更 | 标准需求 |
| 标准需求变更 | 设计文档 |
| 设计文档变更 | 代码 |

**禁止跳级**：需求变更 → 不允许直接改代码，必须先更新设计文档

## 5. AI 执行流程

### Step 0：项目初始化（仅首次/缺失文件时）

**检查**：项目根目录是否缺少 `.gitignore`、语言特定文件、`CLAUDE.md`、`AGENTS.md`

**跳过条件**：以上文件全部存在 → 直接进入 Step 1

### Step 1：确认流程

**执行内容**：
1. 确认用户需求类型
2. 检查 docs 目录状态
3. 确定进入哪个阶段

**状态判断**：

| 状态 | 条件 | 处理 |
|:-----|:-----|:-----|
| 无原始需求 | `docs/原始需求/` 为空 | 阶段0：产品设计 |
| 有原始需求，无需求文档 | 原始需求存在，需求文档为空 | 阶段1：需求转换 |
| 有需求文档，无设计文档 | 需求文档存在，设计文档为空 | 阶段2：设计生成 |
| 有设计文档 | 设计文档已存在 | 阶段3：代码生成 |

### Step 2：按阶段执行

根据 Step 1 结果进入对应阶段，完成后进入下一阶段。

### Step 3：记录细节（持续）

发现重要细节时立即记录到 `docs/细节记录/`

## 6. Git 规范

### commit 格式

```
<类型>: <简短描述>

<可选详细说明>
```

| 类型 | 说明 |
|:-----|:-----|
| feat | 新功能 |
| fix | 修复 |
| docs | 文档 |
| refactor | 重构 |
| test | 测试 |
| chore | 杂项 |

### 分支管理

| 分支 | 说明 |
|:-----|:-----|
| master | 主分支（生产环境） |
| test | 测试分支 |
| dev | 开发分支 |
| feature/xxx | 功能分支 |
| hotfix/xxx | 热修复分支 |

### 合并规则

```
feature → dev → test → master
```

## 7. 需求变更流程

> ⚠️ **适用场景**：轻量项目的需求变更（通用流程项目用）

**触发条件**：
- 简单需求变更、轻量需求修改
- 加个功能、改个需求（无规范约束项目）

> 💡 完整流程项目（mcpowers-workflow）的需求变更请用对应技能

### 流程

```
1. 评估影响
   └→ 确定变更涉及的环节（需求/设计/代码）

2. 按三阶段同步执行
   └→ 正向同步：原始需求 → 需求文档 → 设计文档 → 代码
   └→ 需求变更必须先更新设计文档

3. 生成变更文档
   └→ 路径：docs/需求文档/需求变更_v{版本号}.md

4. 执行变更
   └→ 按变更文档执行

5. 晋升流程
   └→ dev → test → master
```

## 8. 临时文件管理

- 临时文件放在 `temp/` 目录
- 用完即删，不堆积
- 禁止在项目根目录或代码目录创建临时文件
- 禁止临时文件提交到 git

## 9. 自检清单

每次 commit 前必须检查：

- [ ] 用户已确认修改内容
- [ ] 代码注释完整（函数/类/复杂逻辑）
- [ ] 代码符合 SOLID/KISS/DRY/YAGNI 原则
- [ ] 无临时文件遗留
- [ ] commit 信息规范
- [ ] 代码和文档同步变更
