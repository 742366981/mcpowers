# mcpowers-core

通用工作流技能，保留完整流程但不绑定特定技术规范。

## 核心原则

### 红线（禁止）

| 禁止 | 说明 |
|:-----|:-----|
| 未经确认直接修改 | 用户未确认前不得执行任何修改 |
| 先代码后文档 | 接口必须先写文档再写实现 |
| 多个操作后才 commit | 每个任务完成后必须立即 commit |
| 只 commit 代码不 commit 文档 | 代码和文档必须同时提交 |
| 代码注释不完整 | 函数/类/复杂逻辑必须有完整注释 |
| 临时文件不清理 | 调试文件用完即删 |

### 修改前必须询问

1. **先分析** - 理解需求和影响范围
2. **先确认** - 确认方案是否符合预期
3. **再执行** - 用户确认后才修改

### 变更必须同步

任何代码变更，**必须同步更新所有受影响的文件**。

## 项目文件结构

| 目录 | 含义 |
|:-----|:-----|
| `docs/原始需求/` | 用户提供的原始需求 |
| `docs/需求文档/` | 标准化后的需求文档 |
| `docs/设计文档/` | 项目架构和技术方案 |
| `docs/API文档/` | 接口详细设计 |
| `docs/细节记录/` | 重要细节记录 |

## 流程步骤

### 阶段0：产品设计

**前置确认**：用户是否已有设计？

- **A. 已有设计** → 直接使用，跳过引导
- **B. 部分设计** → 使用已有 + 引导缺失
- **C. 没有设计** → AI 引导生成

**引导流程**（分步询问）：

1. **确认项目名称**（必须先问）
2. **初始化 Git 仓库**
3. **询问产品类型**（博客/电商/管理后台/社区/其他）
4. **询问目标用户**（普通用户/企业内部/开发者/管理员）
5. **询问使用场景**（Web/移动端/桌面端/多端）
6. **询问功能模块**（用户/内容管理/搜索/消息/支付/统计）
7. **询问优先级**（P0核心/P1重要/P2可选）
8. **询问非功能需求**（性能/安全/兼容性/可靠性）
9. **生成原始需求文档**
10. **确认原型图**（有/无/暂不需要）

**输出文档**：`docs/原始需求/{项目名}_原始需求.md`

---

### 阶段1：需求转换

```
输入：docs/原始需求/
输出：docs/需求文档/

输出内容：
- 项目概述（名称、背景、目标）
- 系统定位（边界、核心功能、用户角色）
- 功能需求（模块划分、功能点列表）
- 非功能需求（性能、安全等）
- 数据字典（核心数据实体）
```

---

### 阶段2：设计生成

```
输入：docs/需求文档/
输出：docs/设计文档/

输出内容：
- 系统概述（项目定位、主要功能）
- 技术选型（后端/前端/数据库等）
- 系统架构（模块划分、目录结构）
- 基础数据模块设计
```

**设计文档命名**：
- 后端：`{项目名}_后端设计.md`
- 前端：`{项目名}_前端设计.md`
- 数据库：`数据库设计.md`
- 接口：`{项目名}_接口设计.md`

---

### 阶段3：代码生成

```
输入：docs/需求文档/ + docs/设计文档/
输出：项目代码

要求：
- 先写文档，再写实现
- 每完成一个功能点，立即 commit
- 代码和文档同步变更
```

**代码质量原则**：

| 原则 | 说明 |
|:-----|:-----|
| SOLID | 单一职责、开闭原则、里氏替换、接口隔离、依赖倒置 |
| KISS | 保持简洁，避免不必要的复杂性 |
| DRY | 拒绝重复代码，相同逻辑只写一次 |
| YAGNI | 只实现当前明确所需的功能 |

**代码质量检查**：
- [ ] 函数是否单一职责（不超过50行）？
- [ ] 是否有重复代码需要抽取？
- [ ] 变量/函数命名是否清晰？
- [ ] 是否有不必要的嵌套层级（不超过3层）？

---

### 阶段4：细节记录

持续记录重要细节到 `docs/细节记录/`：

| 类型 | 内容 |
|:-----|:-----|
| 业务逻辑 | 复杂规则、判断条件 |
| 技术实现 | 第三方集成、特殊配置 |
| 踩坑记录 | 问题及解决方案 |
| 注意事项 | 后续开发需关注的点 |

## 三阶段同步

需求、设计、代码三者必须保持同步。

### 同步规则

| 变更 | 必须同步 |
|:-----|:---------|
| 原始需求变更 | 标准需求 |
| 标准需求变更 | 设计文档 |
| 设计文档变更 | 代码 |

**禁止跳级**：需求变更不允许直接改代码，必须先更新设计文档

### 正向同步流程

```
评估影响 → 确定范围 → 同步执行 → 验证一致 → 记录变更
```

## AI 执行流程

### Step 0：项目初始化

**检查**：项目根目录是否缺少 `.gitignore`、语言文件、`CLAUDE.md`、`AGENTS.md`

**跳过条件**：以上文件全部存在 → 直接进入 Step 1

### Step 1：确认流程

**状态判断**：

| 状态 | 条件 | 进入 |
|:-----|:-----|:-----|
| 无原始需求 | `docs/原始需求/` 为空 | 阶段0 |
| 有原始需求，无需求文档 | 原始需求存在，需求文档为空 | 阶段1 |
| 有需求文档，无设计文档 | 需求文档存在，设计文档为空 | 阶段2 |
| 有设计文档 | 设计文档已存在 | 阶段3 |

### Step 2：按阶段执行

按顺序执行：阶段0 → 阶段1 → 阶段2 → 阶段3

### Step 3：记录细节（持续）

发现重要细节时立即记录

## 需求变更流程

**适用场景**：轻量项目的需求变更

### 流程

```
1. 评估影响
   └→ 确定变更涉及的环节（需求/设计/代码）

2. 按三阶段同步执行
   └→ 正向同步：原始需求 → 需求文档 → 设计文档 → 代码

3. 生成变更文档
   └→ docs/需求文档/需求变更_v{版本号}.md

4. 执行变更
   └→ 按变更文档执行

5. 晋升流程
   └→ dev → test → master
```

## Git 规范

### commit 格式

```
<类型>: <简短描述>

<可选详细说明>
```

| 类型 | 说明 |
|:-----|:-----|
| feat | 新功能 |
| fix | 修复 |
| docs | 文档 |
| refactor | 重构 |
| test | 测试 |
| chore | 杂项 |

### 分支管理

| 分支 | 说明 |
|:-----|:-----|
| master | 主分支（生产） |
| test | 测试分支 |
| dev | 开发分支 |
| feature/xxx | 功能分支 |
| hotfix/xxx | 热修复分支 |

### 合并流程

```
feature → dev → test → master
```

### 冲突处理

```
1. 获取最新代码：git fetch origin
2. 切换到目标分支
3. 执行合并：git merge {源分支}
4. 解决冲突
5. 提交：git add . → git commit -m "merge: 解决合并冲突"
```

---

## 临时文件管理

- 临时文件放在 `temp/` 目录
- 用完即删，不堆积
- 禁止在项目根目录或代码目录创建临时文件
- 禁止临时文件提交到 git

## 自检清单

每次 commit 前检查：

- [ ] 用户已确认修改内容
- [ ] 代码注释完整（函数/类/复杂逻辑）
- [ ] 代码符合 SOLID/KISS/DRY/YAGNI 原则
- [ ] 无临时文件遗留
- [ ] commit 信息规范
- [ ] 代码和文档同步变更
