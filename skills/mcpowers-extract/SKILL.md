# mcpowers-extract（模块抽离）

> **核心**：把**已有业务项目**里的**可复用技术能力**，从**一次性业务胶水**里剥出来，沉淀为独立可 `import` 的模块 / 可随时调用的脚本 / 团队公共库。
> **不是**原地重构（结构留原项目），**不是**逆向陌生目标——是"从自己项目提炼可复用资产"。

---

## 核心识别主线：技术能力层 vs 业务逻辑层

抽离的本质 = 把**可复用技术能力**与**一次性业务胶水**分层。

| 场景 | 技术能力层（**抽**） | 业务逻辑层（**不抽**） |
|:-----|:---------------------|:-----------------------|
| **爬虫项目（头号特化）** | **逆向层**：sign/token 算法、加解密、frida hook、补环境、请求签名构造 | 业务层：调度/翻页/入库/清洗/去重（与站点强绑定） |
| 后端项目 | DB/缓存/鉴权/限流/导入导出封装、通用 utils | 具体业务 CRUD / 业务规则 |
| 任意项目 | 纯函数工具、协议/编码处理、通用适配器 | 业务胶水、页面/接口编排 |

**爬虫铁律**：逆向层是**最高抽离优先级**——它与业务无关、同类站点/同厂加密可反复复用；现状痛点是"逆向层与业务焊死 → 下次同类目标又从头逆一遍"。抽离时**必须逆向层与业务层分离剥离**，不可一锅端。

## 编排

本技能按需调用以下方法层技能 + 规范：

| 步骤 | 调用对象 | 类型 | 触发条件 | 失败时 |
|:-----|:---------|:-----|:---------|:-------|
| 1 | `mcpowers-brainstorm` | 方法 | 抽离目标/边界不明确 | 中断并回问用户 |
| 2 | `mcpowers-spec-index` | 规范 | 定位栈规范（爬虫/后端/代码） | 提示加载失败 |
| 3 | `mcpowers-tdd` | 方法 | 抽离的核心逻辑无验证保护 | 补最小 `verify` 脚本 |
| 4 | `mcpowers-code-review` | 方法 | 封装完成 | Critical 必须修复 |
| 5 | `mcpowers-git-commit` | Git | 收尾提交 | — |

**保护路径**（PreToolUse(Write) hook 强制确认）：`skills/mcpowers-shared/`、`skills/mcpowers/`、`hooks/`、`.claude-plugin/` 四目录写操作触发前确认。本技能产物目录在工作区根，不在保护路径内。

**铁律**：
1. **行为不变**——抽离只搬运 + 参数化，禁止顺手改逻辑（改行为是 `refactor`/`bugfix`）。
2. **先分层后抽离**——先分清技术能力层 vs 业务层，爬虫先分逆向层 vs 业务层，再动手。
3. **抽必可独立运行**——产物脱离原项目能 `import` / 跑通，禁止残留对原项目全局/config 的引用。
4. **抽必验证**——每个模块配 `verify.py` + ≥1 组真实调用样本，与原项目结果一致。
5. **YAGNI 优先**——不为一次性/强耦合业务代码造库（见阶段 2 门禁）。

## 触发即执行（6 阶段）

### 1. 识别抽离边界（分层扫描）
- 扫描目标项目，按"技术能力层 vs 业务逻辑层"给候选模块分类。
- 爬虫项目：**先切出逆向层**（sign/加解密/hook/补环境/签名构造），再看其余通用能力。
- 产出：**抽离候选清单**（每项标注：所属层 / 复用潜力 / 对业务的依赖点）+ **依赖图**（模块↔业务上下文的引用关系）。

### 2. 评估抽离价值（YAGNI 硬门禁）
逐项过三道门，任一不达标 → 劝退或降级：

| 维度 | 达标 | 不达标 → |
|:-----|:-----|:---------|
| 复用频率 | 已/将在 ≥2 处或多项目复用 | 一次性代码，不抽 |
| 与业务耦合 | 能参数化解耦为纯能力 | 深度耦合业务字段/规则，不抽或先解耦 |
| 依赖成本 | 依赖可控、可独立安装 | 拖家带口整个框架，评估后再定 |

**禁止**：为"看起来通用"但实际一次性的代码造库。

### 3. 切割依赖
- 去硬编码 config / 全局状态 / 业务字段，改为**参数注入**。
- 斩断对原项目业务上下文的 import；保留纯技术依赖。
- 按 `代码同步修改规范.md` 记录原项目中被抽走代码的引用点（后续可反向依赖新模块）。

### 4. 封装为独立产物（复用 crawler-reverse 阶段 5 骨架）
产物落到工作区根 `extracted-modules/{module}/`：

```
extracted-modules/{module}/
├── __init__.py        # 暴露对外可复用接口
├── functions.py       # 核心函数（可独立 import，docstring 5 字段齐全）
├── constants.py       # 常量（URL/Header/Key 模板等）
├── cli.py             # 可选：脚本随时调用入口（python -m / 直接 run）
├── README.md          # 使用说明：≥2 个 import + CLI 复用示例
└── verify.py          # 复用前快速验证脚本
```
- 命名/分层遵循 `爬虫规范.md`（爬虫类）或 `代码规范.md`（通用类）。
- 逆向层与业务层**分成不同 module**，不混装。

### 5. 可调用性验证
- `import` 用例跑通（脱离原项目上下文）。
- `cli.py` 脚本跑通（"随时调用"诉求的落点）。
- **≥1 组真实调用样本**，输出与原项目一致（逆向类算法 ≥3 组，对齐爬虫分析规范）。

### 6. 落地决策（`AskUserQuestion`）

| 选项 | 走向 |
|:-----|:-----|
| A. 留独立库自管理 | 结束，建议把 `extracted-modules/` 纳入独立 git 仓库/私有包 |
| B. 升级为完整项目骨架 | 跳 `mcpowers-init`，传入 `extracted-modules/{module}/` |
| C. 基于抽离产物继续开发 | 跳 `mcpowers-feat` |

## 反模式（禁止）

- ❌ 抽一次性/强耦合业务代码造库（违反 YAGNI，阶段 2 门禁拦截）
- ❌ 抽完不切依赖（模块仍引用原项目全局/config，无法独立 import）
- ❌ 只抽不验证（无 `verify.py` + 无真实调用样本）
- ❌ 抽离时改行为（那是 `refactor`/`bugfix`，本技能行为不变）
- ❌ **爬虫项目把逆向层和业务层一锅端**（必须分层剥离）
- ❌ 逆向类算法只验 1 组样本就声称抽离成功（需 ≥3 组）
- ❌ 产物散落工作区不按 `extracted-modules/{module}/` 归档

## 关联技能

- **上游**：`mcpowers-brainstorm`（边界不清时澄清）
- **下游**：`mcpowers-init`（选项 B 落地骨架）/ `mcpowers-feat`（选项 C 二次开发）/ `mcpowers-code-review`（封装自审）/ `mcpowers-git-commit`（提交）
- **同级（易混淆）**：
  - `mcpowers-refactor` —— 原地改结构、产物留原项目、行为不变；本技能产出**跨项目独立复用资产**
  - `mcpowers-crawler-reverse` —— 起点是**陌生目标 + 逆向**；本技能起点是**自己已有项目**（可衔接：逆向产出的 `04-modules/` 后续用本技能提炼为团队公共库）
  - `mcpowers-init` —— 从零搭骨架；本技能从已有代码提炼
