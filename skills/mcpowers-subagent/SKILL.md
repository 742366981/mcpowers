# mcpowers-subagent（子代理并行执行）

> 借鉴自 superpowers `subagent-driven-development` + `dispatching-parallel-agents`。
> **核心**：任务**相互独立**才并行；不独立 → 串行。

---

## 触发即执行

### 1. 判断是否适用
适合子代理并行：
- ✅ 任务**相互独立**（无强依赖）
- ✅ 任务**边界清晰**（输入输出明确）
- ✅ 任务**可独立验证**
- ✅ 任务规模较大（否则调度成本 > 收益）

不适合：
- ❌ 任务间有强依赖（A 必须在 B 之后）
- ❌ 任务边界模糊（要协商）
- ❌ 任务很小（改个变量名）

### 2. 拆解任务
对每个并行任务写明：
- **目标**：做什么
- **输入**：拿什么开始
- **输出**：产出什么
- **约束**：不能改什么
- **验证**：怎么确认完成

### 3. 加载规范
- Read `mcpowers-shared/mcpowers-spec-index/SKILL.md`
- 加载：
  - 对应栈规范
  - `mcpowers-shared/docs/技术规范/代码规范.md`

### 4. 启动子代理
对每个独立任务，启动一个子代理（使用 Agent 工具）：
- 任务说明完整（让子代理无需追问）
- 提供规范文件路径（让子代理按需 Read）
- 给出明确的输出格式

### 5. 汇总与验证
- 收集所有子代理输出
- 验证任务间一致性（命名、接口、依赖）
- 跑全量测试
- 跑全量 lint / type check

### 6. 整合 commit
- 子代理各自 commit 不合适
- 主代理整合后**整体** commit

## 子代理提示词模板

```markdown
你的任务：{任务描述}

输入：
- {文件路径或数据}
- {规范文件路径：mcpowers-shared/docs/技术规范/xxx}

输出：
- 修改/新建的文件列表
- 验证结果（测试输出）

约束：
- 严格遵守 {规范名}
- 不要修改 {其他文件}
- 不要做 {禁止的操作}

完成后报告：
- 改了什么
- 测试是否通过
- 是否有未解决的问题
```

---

## 反模式（禁止）

- ❌ 强依赖任务并行（A 还没好 B 就开始）
- ❌ 子代理间共享状态（会产生竞态）
- ❌ 子代理任务描述不清（要追问）
- ❌ 子代理间命名/接口不一致
- ❌ 子代理各自 commit（应主代理整合后统一 commit）

---

## 何时使用 vs 串行执行

| 情况 | 选择 |
|:-----|:-----|
| 3 个独立模块改动 | **并行**（节省时间） |
| 改 A 必须先改 B | **串行** |
| 任务量小（< 30 分钟） | **串行**（调度成本不划算） |
| 任务量大（> 2 小时）且独立 | **并行** |
| 需要频繁协商（接口/命名） | **串行**（先定接口再并行） |
