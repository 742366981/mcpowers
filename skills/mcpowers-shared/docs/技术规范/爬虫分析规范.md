# 爬虫分析规范

本文档定义爬虫目标的**分析方法论**，是《爬虫规范》（项目骨架）的配套文档。

> **适用范围**：本文档覆盖两件事——**接口分析**（抓包侦察、接口定位、请求/响应结构、反爬强度评估）与**逆向攻坚**（加密/签名参数还原）。项目工程骨架（目录结构、任务调度、部署等）不在此列，见《爬虫规范》。
>
> **文档定位**：`爬虫规范`（骨架/工程）→ 本文档`爬虫分析规范`（分析 + 逆向）。分析是入口，逆向是「分析发现参数被加密」后的延伸，故合并为一册、内部分层。

> **状态**：v2.7.0 已填实 §2-§11 方法论（抓包/自动化/过滤/风控/Web JS 逆向/APP 逆向/工具清单）；v2.12.0 新增 §1.1 交付形态与 RPC 逆向方式分离、§9.4 真实可用性验收；附录 B 术语表 / 附录 C 案例库仍为 TODO，待实战沉淀。

# 第一部分 · 接口分析（侦察）

> 目标：在**不做逆向**的前提下，摸清目标数据从哪个接口来、请求怎么构造、反爬有多强。绝大多数爬虫止步于此即可开工。

### 1.1 最终交付形态与逆向实现方式分离（**v2.12.0 新增**）

逆向前必须先确认最终交付形态，避免分析完成后才发现产物方向不对：

| 最终交付形态 | 运行边界 | 验收目标 |
|:-------------|:---------|:---------|
| **纯协议** | 最终脱离浏览器/App/RPC，协议客户端独立生成参数并请求 | 关闭运行时后仍能完成核心业务 |
| **半自动化** | 自动化或 RPC 处理登录、验证码、challenge、sign/token 等难点，协议层完成核心请求 | 运行态状态可刷新、隔离、过期恢复 |
| **纯自动化** | 浏览器/App 自动完成完整业务动作与数据提取 | 页面/App 业务链路端到端成功 |

**RPC 是逆向实现方式，不是第四种交付形态**。阶段 4 可按难度选择：Python 纯复现 → Node/JS 补环境 → RPC 调用目标运行时。若使用 RPC：

- Web 可在目标页面注入 WebSocket 客户端，由本地服务按 `group` / `name` 隔离运行时，注册受控 action 或执行受限 JS，返回 sign/token/响应；
- APP 可使用 Frida `rpc.exports` 调用 Java/native 运行时函数；
- 必须记录调用端、运行时标识、action、参数/返回 schema、健康检查、超时、断线重连和并发隔离；
- RPC endpoint 仅绑定本机或受控内网，禁止公网暴露、任意代码默认执行、跨账号/session 串用或静默复用旧参数；
- 纯协议目标最终不得依赖 RPC；无法剥离时必须重新确认改为半自动化。

**JsRpc 参考**：[`jxhczhl/JsRpc`](https://github.com/jxhczhl/JsRpc) 展示了本地服务 + 浏览器注入 WebSocket、`group/name` 连接隔离、注册 action、`/go` 调用和 `/execjs` 执行模式。这里只借鉴驻留运行时与显式 action 的方法，不把该项目、默认端口或接口变成本规范硬依赖。

运行态 token/Cookie/challenge 必须与抓包样本、稳定常量分离，记录生成时间、TTL、账号/session/设备绑定并原子刷新；日志只保留脱敏标识。

## 2. 抓包与工具


### 2.1 Web 抓包（3 类工具按场景选择）

| 工具 | 优势 | 适用场景 |
|:-----|:-----|:---------|
| **浏览器 DevTools** | 零成本、XHR/Fetch 筛选、Initiator 调用栈 | **入门首选**，单接口断点调试 |
| **mitmproxy** | Python 脚本化、可改写请求/响应、可批量过滤 | **自动化分析首选** |
| Charles | GUI 友好、Throttle 模拟弱网、支持重发 | 人工巡检、复现问题 |
| Fiddler | Windows 友好 | Windows 环境 |

**mitmproxy 核心用法**（**必学**）：

```python
# 脚本保存为 mitm_script.py，mitmdump -s mitm_script.py
# 1. 只保留业务接口，过滤 CDN/上报
def request(flow):
    url = flow.request.pretty_url
    if any(skip in url for skip in ['.png', '.woff', 'analytics.', 'log.', 'beacon.']):
        flow.kill()  # 阻断，不传给上游
    elif any(api in url for api in ['/api/', '/graphql', 'gateway']):
        save_core_request(flow)
```

### 2.2 APP 抓包（3 层递进）

| 层级 | 场景 | 工具 |
|:-----|:-----|:-----|
| **L1 明文 HTTP** | APP 用 HTTP | mitmproxy + 用户证书（Android 7+ 需 root / iOS 需描述文件） |
| **L2 HTTPS** | APP 用 HTTPS | 同上，但需用户证书被 APP 信任 |
| **L3 SSL Pinning** | 装了证书但抓不到 | **必须绕过**（见 §10） |

**⚠️ 关键提示**：抓包结果常含大量冗余（图片/字体/CDN/上报），**必须按请求类型过滤**才能定位核心业务接口（详见 §3）。

### 2.3 自动化分析（**必备，可大幅提升效率**）

> **核心思想**：人工巡检只适合看 1-2 个接口，**真正业务接口往往需要触发特定交互**（登录态、滑动验证、下拉刷新）才会出现。**必须用自动化工具模拟用户行为**。
>
> **v2.9.3 强化**：默认 **Playwright-Python**（不要用 Node 版本），默认开启 **`playwright-stealth`** 绕过 `navigator.webdriver` / WebGL / canvas 指纹；协议层（不走浏览器的 API 直连）默认用 **`curl_cffi.requests`** 替代裸 `requests`（详见 §2.6）。

**自动化浏览器**（Web 抓动态接口）：

| 工具 | 优势 | 适用场景 |
|:-----|:-----|:---------|
| **Playwright-Python** + `playwright-stealth` | Python 生态、跨浏览器、内置指纹伪装 | **分析阶段首选**（v2.9.3 强制） |
| **DrissionPage** | 国产、**内置接管浏览器 + 内置反检测**、对国内站点适配好 | **封装阶段备选**（v2.9.4）：国内项目（小红书/抖音/淘宝/1688） |
| **seleniumbase** | UC Mode（undetected-chromedriver）成熟、国外生态 | **封装阶段备选**（v2.9.4）：需要 Selenium 兼容 + UC 反检测的海外项目 |
| Playwright-Node | Node.js 生态 | 仅当 Python 复现失败时作 §8 路径 B 使用 |
| Puppeteer | Node.js 生态、轻量 | 简单 Chromium 场景 |
| Selenium | 多语言、老牌 | 跨语言兼容需求 |

**Playwright 抓全量接口示例**（**v2.9.3 默认 `connect_over_cdp` 模式**，**禁止**新开窗口，详见 §2.5）：

```python
from playwright.sync_api import sync_playwright
from playwright_stealth import stealth_sync   # 指纹伪装

with sync_playwright() as p:
    # 接入用户本机 Chrome（先按 §2.5 启动 chrome --remote-debugging-port=9222）
    browser = p.chromium.connect_over_cdp("http://localhost:9222")
    context = browser.contexts[0] or browser.new_context()
    page = context.new_page() if not context.pages else context.pages[0]

    # 指纹伪装（推荐同步执行）
    stealth_sync(page)

    # 拦截所有请求/响应
    page.on("request", lambda req: save_req(req))
    page.on("response", lambda res: save_res(res))

    # 模拟用户行为
    page.goto(url)
    page.fill('input[name=username]', 'xxx')
    page.click('button[type=submit]')
    page.wait_for_load_state('networkidle')
```

> ⚠️ **反例**（v2.9.3 禁止）：`p.chromium.launch(headless=False)` 新开窗口会丢失用户登录态/扩展，并触发 `navigator.webdriver` 风控。**生产代码必须用 `connect_over_cdp`**（见 §2.5）。

**APP 自动化**（如需触发特定交互）：

| 工具 | 用途 |
|:-----|:-----|
| **Appium** | 跨平台 UI 自动化（iOS/Android） |
| **uiautomator2**（Android） | Python API 简单 |

### 2.4 设备与运行时框架（**APP 逆向环境基石**）

**调试设备选择**：

| 设备类型 | 优势 | 适用场景 |
|:---------|:-----|:---------|
| **本机安卓模拟器**（MuMu / 雷电 / 夜神 / Android Studio 官方模拟器） | 免真机、root 简单、可快照回滚 | **首选**（初版逆向调试） |
| **真机调试**（USB 连接 + root + frida-server 推送） | 真实环境（部分 APP 检测模拟器）、性能稳定 | 模拟器被反调试识别 / 关键业务场景复现 |
| **云真机**（各厂商云测平台） | 覆盖多机型多系统版本 | 兼容性测试、非 root 设备场景 |

**Xposed 框架选型**（**按 Android 版本**）：

| Android 版本 | 推荐框架 | 说明 |
|:-------------|:---------|:-----|
| **Android < 7（API < 24）** | **Xposed**（原版） | 老方案，部分定制 ROM 仍可用 |
| **Android 7-10（API 24-29）** | **EdXposed** | 原 Xposed 停更后社区继任者 |
| **Android 11+（API 30+）** | **LSPosed**（**现代首选**） | 基于 Magisk，Hook 稳定性最好，需 root + Magisk 环境 |

**配套模块**：
- **justtrustme**：Xposed/LSPosed 模块，**一键绕过 SSL Pinning**（配合 LSPosed 使用）
- **TrustUserCerts**：LSPosed 模块，让 APP 信任用户证书（解决 Android 7+ APP 不信任用户证书问题）

**完整调试链路**（**真机/模拟器 + LSPosed + frida + justtrustme**）：

```
设备（root + Magisk + LSPosed + frida-server）
    ↓
安装 justtrustme / TrustUserCerts（解决证书信任）
    ↓
PC 端 mitmproxy 代理（设代理指向 PC IP:8080）
    ↓
APP 启动 → frida attach → Hook 加密函数
    ↓
mitmproxy 抓包 + frida 看入参/出参 → 还原算法
```

### 2.5 浏览器复用策略（**v2.9.3 新增**）

> **核心原则**：**默认复用用户本机 Chrome，不开新窗口**。每次新开 Playwright 窗口会丢失用户登录态/扩展/书签，且 `navigator.webdriver` 指纹暴露给风控。

**方式 1：CDP attach（首选）**

用户先在终端启动 Chrome（**带远程调试端口**）：

```bash
# macOS
/Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome \
  --remote-debugging-port=9222 \
  --remote-allow-origins=*

# Windows
"C:\Program Files\Google\Chrome\Application\chrome.exe" ^
  --remote-debugging-port=9222 ^
  --remote-allow-origins=*
```

Python 端 `connect_over_cdp` 接入：

```python
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    # 接入用户本机 Chrome，复用所有 cookie/扩展/登录态
    browser = p.chromium.connect_over_cdp("http://localhost:9222")
    context = browser.contexts[0]  # 用用户已有 context，不新建
    page = context.pages[0]        # 用用户已有标签页，或 new_page() 新开标签
    # ... 抓包 / 自动化
```

**方式 2：`launch_persistent_context` 复用 user-data-dir（备选，仅当用户明确要"独立环境"时）**

```python
context = p.chromium.launch_persistent_context(
    user_data_dir="/Users/xxx/Library/Application Support/Google/Chrome",
    headless=False,
)
```

**禁止**：

- ❌ 每次 `p.chromium.launch(headless=False)` 新开窗口（丢失登录态 + 触发风控）
- ❌ 用 `launch(headless=True)` headless 模式抓需要登录态的接口（必然失败）
- 唯一例外：用户明确说"无 GUI 自动化"或"协议直连（不经过浏览器）"

#### §2.5.1 接管前置预检（**v2.9.5 新增**）

> **核心原则**：AI 接到任务后的第一个动作是检测 Chrome 远程调试端口。**检测到接管比假设接管更可靠**。

**检测脚本**（AI 第一个动作）：

```python
import urllib.request, json

def probe_chrome_cdp(port: int = 9222, timeout: float = 2.0) -> dict:
    """探测 Chrome 远程调试，返回 {available, version, tabs}"""
    result = {"available": False, "version": None, "tabs": []}
    try:
        with urllib.request.urlopen(f"http://localhost:{port}/json/version", timeout=timeout) as r:
            ver = json.loads(r.read())
            result["available"] = True
            result["version"] = ver.get("Browser", "unknown")
    except Exception:
        return result
    try:
        with urllib.request.urlopen(f"http://localhost:{port}/json", timeout=timeout) as r:
            result["tabs"] = json.loads(r.read())
    except Exception:
        pass
    return result

# 用法
info = probe_chrome_cdp()
if info["available"]:
    print(f"✓ Chrome {info['version']} 远程调试可用，{len(info['tabs'])} 个标签页")
    for i, t in enumerate(info["tabs"]):
        print(f"  [{i}] {t['type']:8s} | {t['title'][:40]:40s} | {t['url'][:60]}")
else:
    # → 给出 AskUserQuestion 引导用户启动 Chrome 调试模式（见 §2.5.4）
    print("✗ 未检测到 Chrome 远程调试")
```

**预检后行为**：

| 预检结果 | AI 行为 |
|:---------|:--------|
| **可用 + 含目标域 tab** | 主动提示用户接管现有 tab（§2.5.3） |
| **可用 + 无目标域** | 在用户 context 内新开 tab（§2.5.2 L3） |
| **不可用** | AskUserQuestion 4 选 1 引导启动（§2.5.4） |

#### §2.5.2 接管粒度分级（**v2.9.5 新增**）

> **核心原则**：接管粒度按"用户已登录态范围"分级，**从粗到细递进**。

| 级别 | 适用场景 | 代码 | 风险 |
|:-----|:---------|:-----|:-----|
| **L1 接管整个浏览器** | 用户已登录目标站，要复用所有登录态 | `browser = p.chromium.connect_over_cdp(...)`<br>`context = browser.contexts[0]` | 无 |
| **L2 接管特定标签页** | 用户已在某 tab 打开目标页 | `context.pages[i]` 直操作 | 低 |
| **L3 新开标签页（保留 cookie）** | 用户浏览器有 cookie 但没打开目标页 | `context.new_page()` 在用户 context 内新开 | 低 |

**禁止**：

- ❌ `p.chromium.launch(headless=False)`（v2.9.3 已禁；v2.9.5 强化）
- ❌ `browser.new_context()`（新建独立 context，不在用户 context 内）
- ❌ `context.clear_cookies()`（清空用户登录态）

#### §2.5.3 早检测：用户已在浏览器中打开目标页面（**v2.9.5 新增**）

> **核心原则**：如果预检时发现用户已经在某个 tab 中打开了目标域，**必须主动提示**，不要重新打开丢失登录态。

**检测逻辑**：

```python
def find_target_tab(tabs: list, target_domain: str) -> int | None:
    """在 tabs 中查找目标域名，返回 tab 索引或 None"""
    for i, t in enumerate(tabs):
        url = t.get("url", "")
        if target_domain in url and t.get("type") == "page":
            return i
    return None

# 用法
target_idx = find_target_tab(info["tabs"], "github.com")
if target_idx is not None:
    print(f"✓ 检测到您已在 Chrome 中打开 github.com 的标签页（tab #{target_idx}）")
    # → 给出 AskUserQuestion 3 选 1
```

**提示话术**（AI 自动生成）：

> "检测到您已在 Chrome 中打开 `github.com` 的标签页（tab #3，标题：`<title>`）。
> - A. 直接接管这个标签页（推荐，已登录态保留）
> - B. 在新标签页打开（保留 cookie 池）
> - C. 让我重新开一个浏览器（不推荐，会丢失登录态）"

#### §2.5.4 未检测到 Chrome 时的引导（**v2.9.5 新增**）

> **核心原则**：用户没启动 Chrome 调试模式时，**不要自作主张开新窗口**，而是给出明确指引让用户选择。

**AskUserQuestion 4 选 1**：

```
> 未检测到 Chrome 远程调试模式（端口 9222）。请选择：
> - A. 启动 Chrome 调试模式（推荐，可接管当前页面）
>   Windows: "C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222 --remote-allow-origins=*
>   macOS: /Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome --remote-debugging-port=9222 --remote-allow-origins=*
>   Linux: google-chrome --remote-debugging-port=9222 --remote-allow-origins=*
> - B. 让 AI 开新浏览器窗口（无登录态，仅适合简单静态页）
> - C. 协议直连（curl_cffi，无 GUI）
> - D. 取消本次任务
```

#### §2.5.5.0 bb-browser 安装与 MCP 配置（**v2.11.1 新增**）

bb-browser 安装与 MCP 接入是 v2.10.0 缺失的实操环节，本节补全。

**前置要求**：

- **Node.js ≥ 18**（bb-browser 是 ESM 模块，Issue #10 报告 < 18 时 daemon 启动失败）
- 网络可访问 `registry.npmjs.org`（postinstall 拉原生二进制需要）

**安装方式（双轨 fallback）**：

| 方式 | 命令 | 适用场景 |
|:-----|:-----|:---------|
| **A. 全局安装（推荐）** | `npm install -g bb-browser` | 网络通畅，默认首选 |

#### §2.5.5 bb-browser 集成策略（**v2.10.0 新增**）

> **核心原则**：bb-browser（[epiral/bb-browser](https://github.com/epiral/bb-browser)）是**可选增强依赖**，不是本规范的硬依赖。bb-browser 通过 CDP 接管用户已运行的真实 Chrome，提供 CLI / MCP server / 35+ 平台 site adapters。未安装、daemon 未运行、目标站点未适配或版本不兼容时，**必须完整回退 v2.9.5 的 Chrome CDP + Playwright + popup-handler.py 链路**。

**安装**：

```bash
npm install bb-browser
```

**接管预检阶段先运行**（§2.5.1 的第一个动作）：

```bash
bb-browser status
```

命令可用且 daemon 正常时，**优先使用 adapter**；需要 MCP 时按 bb-browser CLI 帮助启动：

```bash
bb-browser daemon --mcp
```

**已知 adapter 覆盖**：GitHub、Twitter/X、Reddit、V2EX，以及其他 35+ 平台；**实际可用列表必须以当前安装版本输出为准**。**国内站点或未覆盖项目需自写 adapter**，不得假设所有站点均受支持。

**与 §2.5.1 接管预检协作**：

- 先检查 `bb-browser status`，再检查 `localhost:9222`（§2.5.1）和目标 tab（§2.5.3）
- bb-browser 与 Playwright **应连接同一用户 Chrome / CDP 会话**
- 与 §2.5.2 接管粒度一致，**优先 L2 已打开目标 tab**，其次 L3 在用户 context 新开 tab，**禁止新建独立 context**

**与 §2.7 弹窗协同**：

- adapter 通常可处理登录前导航或公开入口，**但不替代 `popup-handler.py`**
- 仍须先清理 D.1-D.5 弹窗；D.6-D.8 **必须截图并询问用户**

**置信度联动**：

- adapter 命中后，**接口线索还要由 Playwright / `curl_cffi` 实测并保存响应**
- 验证通过后置信度自动升为 `[🎯]`（详见 §3.4.5）
- adapter 命中但未实测 → 只能标 `[⚠️]`，**不得直接升 `[🎯]`**

**职责边界**（与原链路不重叠）：

- **adapter**：站点级导航 / 内容入口 / 结构化操作
- **Playwright**：CDP 会话内的网络实测 / DevTools 抓包 / 浏览器自动化
- **`popup-handler.py`**：通用 DOM 弹窗 / 浏览器原生权限 / 合规询问

#### §2.5.5.1 bb-browser + Playwright 共享 Chrome CDP 实操（**v2.11.1 新增**）

bb-browser daemon 与 Playwright `connect_over_cdp` 共享同一用户 Chrome 是 v2.10.0 缺失的实操细节。

**启动顺序（严格，不可乱序）**：

1. 用户先启动 Chrome 调试模式（铁律 #8 前置，`chrome --remote-debugging-port=9222`）
2. 启动 bb-browser daemon（占用 9001 端口）
3. Playwright `connect_over_cdp("http://localhost:9222")`（9222 端口）
4. 复用 `browser.contexts[0]`（铁律 #8）

**端口分配（互不冲突）**：

| 端口 | 占用方 | 作用 |
|:-----|:-------|:-----|
| `9222` | 用户 Chrome | CDP endpoint（Playwright `connect_over_cdp` 目标） |
| `9001` | bb-browser daemon | MCP endpoint + adapter 调用入口 |
| 其他（9002+） | bb-browser adapter | 多 adapter 并行时占用 |

**daemon 异常接管顺序**：

1. `curl http://localhost:9001/health` 检测 → 5xx/无响应视为异常
2. `bb-browser daemon stop && bb-browser daemon --mcp &` 重启
3. 重启失败 → 完全回退 v2.9.5，bb-browser 标记 unavailable

**共享 Chrome CDP 验证（4 步全过）**：

```bash
# 1. Chrome 9222 端口存活
curl http://localhost:9222/json/version | grep webSocketDebuggerUrl

# 2. bb-browser 9001 端口存活
curl http://localhost:9001/health

# 3. 两者能看到同一 tabs 列表
curl http://localhost:9222/json | jq '.[].url'
curl http://localhost:9001/tabs | jq '.[].url'

# 4. Playwright attach 复用用户 context
python -c "
from playwright.sync_api import sync_playwright
with sync_playwright() as p:
    b = p.chromium.connect_over_cdp('http://localhost:9222')
    print('contexts:', len(b.contexts), 'pages:', sum(len(c.pages) for c in b.contexts))
"
```

**4 步任一失败** → 未真正共享 Chrome，**禁止**进入 §3.0 模式 A 的 bb-browser 增强流程，强制回退纯 Playwright 链路。

**反模式**：

- ❌ daemon 未启动就调用 adapter 命令（必须先 `bb-browser status`）
- ❌ Playwright `browser.new_context()` 新建独立 context（违反铁律 #8）
- ❌ daemon 异常反复重启超过 3 次（第 4 次直接回退）
- ❌ 共享验证 4 步未全部通过就启用 adapter

### 2.6 协议层请求框架（**v2.9.3 新增**）

> **核心原则**：**禁止裸用 `requests` 直连 API**。裸 `requests` 的 TLS 指纹（JA3/JA4）一秒被风控识别为 Python 客户端。

**首选：`curl_cffi`**（**TLS 指纹伪装 + 0 配置**）

```python
from curl_cffi import requests

# 模拟 Chrome 120 浏览器 TLS 指纹 + UA
resp = requests.get(
    "https://api.example.com/v1/users",
    impersonate="chrome120",   # 关键：伪装成 Chrome TLS 指纹
    headers={"User-Agent": "Mozilla/5.0 ... Chrome/120.0 ...",  # UA 配套
             "Referer": "https://example.com/"},
    cookies={"session": "xxx"},
)
print(resp.json())
```

**关键要点**：
- `impersonate="chrome120"` → 模拟 Chrome 120 的 TLS 握手指纹
- **UA ↔ TLS 指纹必须配套**（Chrome UA 不能配 Python 默认 TLS 指纹）
- 支持 `chrome` / `chrome99` / `chrome120` / `edge` / `safari` / `firefox` 等版本

**备选**：`httpx` + `tls-client`（需要更细控制时）

**禁止**：

- ❌ 裸 `requests.get(...)` 直连目标站 API（TLS 指纹一秒被识别）
- ❌ UA 写 Chrome 但 `impersonate` 用默认（指纹不配套，必触发风控）

### 2.7 弹窗检测与处理（**v2.9.5 新增**）

> **核心原则**：进入页面后的第一件事是清理弹窗。**抓到弹窗内接口 ≠ 抓到核心业务接口**。v2.9.4 缺失这一步，导致 Cookie 弹窗、App 下载引导、登录墙遮挡真实业务内容，抓包结果严重失真。

#### §2.7.1 8 类弹窗字典与分级策略（v2.9.5 新增）

| 类型 | 典型场景 | 分级策略 | 处理方式 |
|:-----|:---------|:---------|:---------|
| **D.1 Cookie 同意** | GDPR / 国内站首次访问 | **自动拒绝** | 优先点 "Reject All" / "拒绝可选" / "仅必需" |
| **D.2 Notification 询问** | 浏览器原生 Notification 权限 | **自动拒绝** | `context.clear_permissions()` |
| **D.3 Newsletter 订阅** | 弹窗式邮件订阅 | **自动关闭** | 点 "X / 关闭 / 不再提醒" |
| **D.4 App 下载引导** | 小红书/抖音/淘宝打开网页版 | **自动关闭** | 点 "继续访问网页版 / X" |
| **D.5 地理位置请求** | 浏览器原生 Geolocation | **自动拒绝** | `context.clear_permissions()` |
| **D.6 登录墙** | 未登录挡核心内容 | **暂停并询问用户** | 截图 + AskUserQuestion |
| **D.7 年龄验证** | 18+ / 21+ 内容站 | **暂停并询问用户** | 截图 + AskUserQuestion（合规风险） |
| **D.8 合规同意** | 隐私政策 / 用户协议 | **暂停并询问用户** | 截图 + AskUserQuestion |

> **关键设计**：「自动」类（D.1-D.5）AI 直接处理；「询问」类（D.6-D.8）AI 截图后暂停，**绝不自动点**，避免合规风险和误登录。

## 3. 接口定位与筛选

### 3.1 过滤冗余请求（**必做第一步**）

**冗余请求类型清单**（**先排除这些**）：
- 静态资源：`.png` / `.jpg` / `.css` / `.js` / `.woff` / `.ttf` / `.svg`
- 上报埋点：`/log`、`/beacon`、`/track`、`/analytics`、`/collect`、`/monitor`
- 健康检查：`/health`、`/ping`、`/actuator`、`/favicon.ico`
- CDN 域名：常见 CDN 厂商域名段
- 心跳保活：`/heartbeat`、`/keepalive`（长连接场景）

### 3.2 核心业务接口特征（**重点关注**）

- URL 含 `/api/`、`/gateway/`、`/graphql`、`/v1/`、`/v2/`
- Content-Type 是 `application/json` 或 `application/x-www-form-urlencoded`
- 有非空 Request Body
- 响应含 `data` / `list` / `result` / `records` 字段
- 通常每次操作只发 1-3 次（不是高频上报）

### 3.3 静态页 vs 动态接口

| 特征 | 静态页（HTML 渲染） | 动态接口（API 渲染） |
|:-----|:-------------------|:-------------------|
| 抓包主体 | Network → Doc | Network → XHR/Fetch |
| 数据位置 | HTML DOM 节点 | JSON 响应体 |
| 适用工具 | BeautifulSoup / lxml | requests / aiohttp |
| 抓取难度 | 低（无反爬） | 中-高（常含加密） |

### 3.0 接口分析协作模式（**v2.9.5 新增**）

> **核心原则**：AI 抓不到时**主动切换模式**，**不把"找不到"等同于"不存在"**。v2.9.4 缺失这一步，导致复杂场景（登录态接口、懒加载接口）漏抓关键接口。

#### §3.0.1 4 种协作模式

| 模式 | 适用场景 | 操作流程 | AI 行为 |
|:-----|:---------|:---------|:--------|
| **A. AI 全自动**（默认） | 抓包 + 自动化分析无障碍 | 自动化抓包 + 过滤 + 置信度标记 | 跑 Playwright 模拟 + DevTools 抓包 |
| **B. 用户操作 + AI 抓包** | 关键操作只能在登录态触发（支付、评论、关注等） | "请你在浏览器里操作 X → A → B，我监控网络请求" | 用户操作时开启 DevTools Network 录制 |
| **C. 用户告知接口** | 用户已知目标接口（曾用过接口/查过文档/有现成 HAR） | "请直接告诉我 URL / 参数 / 业务含义" | 直接录入用户给的接口 |
| **D. AI 引导用户到指定页面** | 用户不清楚目标页位置（"我要爬 X 但不知道从哪里开始"） | "请告诉我要爬的具体页 URL → 我接管你的标签页" | 用户到指定页后切换 A 模式接管 |

#### §3.0.2 模式选择 AskUserQuestion（v2.9.5 必走）

> **核心原则**：阶段 2 开头**必问**，让用户一开始就有掌控感。

```
> 请问使用哪种协作模式分析接口？
> - A. AI 全自动抓包（默认，AI 跑 Playwright 模拟触发）
> - B. 用户操作 + AI 抓包（适合登录态场景：你操作我看）
> - C. 用户告知接口（如果你已知目标 URL / 参数）
> - D. AI 引导用户到指定页面（适合不清楚目标位置的场景）
```

#### §3.0.3 模式切换触发条件（v2.9.5 新增）

| 触发条件 | 切换动作 |
|:---------|:---------|
| A 模式下，连续 3 次自动化抓包未识别出核心接口 | **暂停**，主动切换到 B / C / D |
| 用户主动说"我直接告诉你" | 切到 C |
| 用户主动说"我帮你打开" | 切到 D |
| 用户主动说"我自己操作" | 切到 B |
| 阶段 2 自检发现 [❓] 过多（>3 条） | 暂停，切到 B 让用户操作触发遗漏接口 |

#### §3.0.4 模式协同工作流

```
[问 1] 协作模式 4 选 1（§3.0.2）
  │
  ├─ A 模式 ─── 自动化抓包 → 漏抓 → [问 3] 切换到 B/C/D
  │
  ├─ B 模式 ─── 用户操作时 AI 监控 → 每个操作触发的接口都收下
  │              → 用户操作完 → 转 A 模式做置信度收敛
  │
  ├─ C 模式 ─── 用户告知接口 → AI 直接录入 + 实测验证（转 A 的实测阶段）
  │
  └─ D 模式 ─── 用户到指定页面 → AI 接管 → 自动转 A 模式
```

#### §3.0.5 bb-browser adapter 失败判定与结果合并（**v2.11.1 新增**）

模式 A 中 bb-browser adapter 调用是"结构化线索"，但 v2.10.0 未明确**失败如何判定、结果如何与 Playwright 实测合并**。本节补全。

**adapter 调用失败判定（4 类）**：

| 失败类型 | 判定标准 | 处理 |
|:---------|:---------|:-----|
| **超时** | 单次 `bb-browser site <site> <action>` > **30s** 未返回 | 标记 `[adapter-timeout]`，回退 Playwright |
| **命令不存在** | `bb-browser status` 显示 daemon running，但 site 命令报 `command not found` | 标记 `[adapter-not-covered]`，目标站点无 adapter |
| **返回空结构** | adapter 返回 JSON 解析后 `data == None` 或 `len(data) == 0` | 标记 `[adapter-empty]`，回退 Playwright |
| **结构不匹配** | adapter 返回字段缺 `url` / `method` / `params` 任一关键字段 | 标记 `[adapter-malformed]`，记录原始响应，回退 Playwright |

**调用日志格式（必落）**：

每次 adapter 调用必须记录到 `01-target-profile/bb-browser-calls.log`：

```log
[2026-07-24T10:23:45+08:00] adapter=twitter/search action="AI agent" status=success duration=2.3s urls=3
[2026-07-24T10:24:12+08:00] adapter=twitter/user-detail action="@openai" status=timeout duration=30.0s urls=0
```

**结果合并规则（adapter ↔ Playwright 实测冲突时）**：

| 维度 | 优先级 | 理由 |
|:-----|:-------|:-----|
| URL 路径 / Method | **Playwright 实测优先** | 实测拿到真实响应样本 |
| 加密参数位置 | **adapter 优先** | adapter 知道站点逻辑 |
| selector / XPath | **adapter 优先** | adapter 返回站点维护者认可的稳定 selector |
| 业务语义标注 | **adapter 优先** | adapter 自带站点业务模型 |

**api-inventory.md 加「来源」列（v2.11.1 新增）**：

| # | URL | Method | 置信度 | 来源 | 加密参数 | 业务含义 |
|:--|:----|:-------|:-------|:-----|:---------|:---------|
| 1 | /api/v1/user/profile | GET | [🎯] | Playwright | 无 | 用户资料 |
| 2 | /api/v1/feed | GET | [⚠️] | adapter | sign | 信息流 |
| 3 | /api/v1/tweet/post | POST | [⚠️] | adapter+Playwright | sign+token | 发推 |

**来源取值**：`adapter` / `Playwright` / `curl_cffi` / `adapter+Playwright`

**反模式**：

- ❌ adapter 调用无日志（必须落 `bb-browser-calls.log`）
- ❌ adapter URL 与 Playwright 实测 URL 冲突时直接信 adapter（实测优先）
- ❌ adapter 失败 4 类判定任一未检查就继续
- ❌ api-inventory.md 无「来源」列

### 3.4 接口功能实测验证原则（**v2.9.3 铁律** + **v2.9.5 置信度增强**）

> **核心原则**：在 `api-inventory.md` 写「这个 URL 是干嘛的 / 这个参数是加密的 / 这个响应字段是用户数据」等结论前，**必须实测一次**。**禁止凭接口名/参数名/字段名凭空判断**。

**实测流程**（**必走**）：

1. **标定核心接口**：在抓包结果中识别出"看起来像核心业务接口"的 URL（命中 §3.2 特征）
2. **发起实测请求**：用 §2.6 的 `curl_cffi` 或 §2.5 的 `playwright` 发起一次**带真实 header/cookie/参数**的请求
3. **保存响应样本**：把响应原文（**脱敏后**）落到 `02-interfaces/responses/{slug}.json`
4. **在 `api-inventory.md` 写结论**：基于实测响应**确认**接口功能（不是猜）

**示例（反例 → 正例）**：

```markdown
# ❌ 反例（凭空判断）
- `GET /api/v1/user/profile` → 拿用户信息（凭路径名猜的）
- 参数 `sign` → 加密签名（凭参数名猜的）

# ✅ 正例（基于实测）
- `GET /api/v1/user/profile` → 拿用户信息
  - 实测响应样本：`02-interfaces/responses/user-profile.json`
  - 响应字段：`{code: 0, data: {uid, nickname, avatar, ...}}`
  - 结论：返回登录态用户的基础资料
- 参数 `sign` → HMAC-SHA256 加密签名
  - 实测：在 `algo-restore.md` §3.1 已用 3 组样本验证还原成功
```

**唯一例外**：用户已明确告知所有核心内容（URL + 参数 + 响应字段 + 业务含义），可跳过本节的接口语义确认；但仍不得跳过 §9.4 的模块真实可用性验收。

> **v2.12.0 证据边界**：本节的一次实测只证明“接口语义已确认”。HTTP 200、响应样本存在或置信度为 `[🎯]`，都不能证明模块可重复调用、动态报文可持续生成、跨 session 可用或并发稳定；交付结论必须按 §9.4 验收。

## 4. 请求结构分析

### 4.1 URL 与 Query 参数

- 路径参数 vs Query 参数 vs Body 参数的区别
- 必填 vs 选填（看哪些参数每次都发、哪些偶尔发）
- 命名规律（`id`、`pid`、`uid`、`biz_id`、`trace_id` 等）

### 4.2 Header / Cookie / Token

- **必看 Header**：`User-Agent`、`Referer`、`Origin`、`Cookie`、`Authorization`、`X-*` 自定义头
- **Token 来源**：
  - 登录接口返回 → 缓存复用
  - 每次请求动态生成 → 看是否参与签名（多数情况是）
  - 第三方 OAuth → 看是否有 refresh 机制

### 4.3 Body 形式

- `application/x-www-form-urlencoded`：表单提交（key=value&...）
- `application/json`：JSON 体（最常见）
- `multipart/form-data`：文件上传
- 二进制：protobuf / MessagePack（**高难度**，需逆向 IDL）

### 4.4 分页机制

| 形式 | 参数 | 特点 |
|:-----|:-----|:-----|
| 偏移分页 | `page`、`page_size` | 简单 |
| 游标分页 | `cursor`、`last_id` | 性能好、爬取全量需记录 cursor |
| 时间分页 | `since`、`until` | 增量同步 |
| 加密游标 | `cursor=xxx`（密文） | **需逆向** |

### 4.5 鉴权方式

| 方式 | 特征 | 应对 |
|:-----|:-----|:-----|
| **Cookie** | `Cookie: session=xxx` | 复用浏览器 Cookie |
| **Bearer Token** | `Authorization: Bearer xxx` | 看 token 有效期 |
| **签名头** | `X-Sign: xxx` | **需逆向**（见 §7） |
| **双因素** | Cookie + 签名头 | 两个都要解决 |

### 4.6 加密参数的初步识别（**核心**）

**风控参数常见 5 类**（**必查**）：

| 参数名（模糊匹配） | 含义 | 应对难度 |
|:-----------------|:-----|:---------|
| `sign` / `signature` / `sig` | 请求签名（核心反爬） | **高** |
| `token` / `access_token` / `auth` | 鉴权令牌（可绕过/可复用） | 中 |
| `_ts` / `timestamp` / `t` | 时间戳（防重放） | 低（跟随即可） |
| `nonce` / `uuid` / `rid` | 一次性随机串（防重放） | 低（跟随即可） |
| `device_id` / `fp` / `fingerprint` / `umid` | **设备指纹** | **高** |
| `x-ticket` / `x-token` / `x-sign` | 自定义头签名 | **高** |

**判定原则**：参数值是 32/64 位十六进制、Base64 字符串、时间戳+nonce 组合 → 大概率是加密/签名 → 进入 §7 加密参数定位。

## 5. 响应结构分析

### 5.1 数据字段提取路径

- 响应通常是 JSON：`{ "code": 0, "msg": "ok", "data": { ... } }`
- 重点看 `code` 字段（业务状态码 ≠ HTTP 状态码）
- 列表接口：`data.list` 或 `data.records` 或 `data.items`

### 5.2 响应加密/压缩识别

| 现象 | 识别 | 应对 |
|:-----|:-----|:-----|
| 响应是乱码字符串 | Base64 / 加密 | 看响应头 `Content-Encoding` |
| 响应体很短（< 50B）但页面有数据 | 加密 + 客户端解密 | 需逆向客户端解密逻辑 |
| 响应是二进制 | protobuf / MessagePack | 需逆向 IDL |

### 5.3 空响应与风控响应

- HTTP 200 + 空 body → 可能是被风控拦截
- HTTP 403 / 429 / 503 → 限频或被封
- 业务 `code: 401` / `code: 403` → Token 过期或权限不足
- 业务 `code: -1` + `msg: "风控拦截"` → 需绕风控

**应对**：记录典型风控响应特征，作为自动检测脚本的判定依据。

## 6. 反爬强度评估

### 6.1 L1-L5 难度分级（**v2.7.0 新增**）

| 难度 | 特征 | 首选方案 |
|:-----|:-----|:---------|
| **L1 明文** | GET/POST 无加密 | 直接采 |
| **L2 简单编码** | Base64 / URL 编码 / 固定密钥 AES | 一次性还原 |
| **L3 动态签名** | HMAC、时间戳参与 | Web JS 逆向（见 §8） |
| **L4 设备指纹 + 行为** | Canvas / WebGL / 鼠标轨迹 | 逆向 + 浏览器环境模拟（**Playwright stealth**） |
| **L5 风控引擎** | 服务端实时风控决策 | **降级**（降频/人工/官方 API） |

### 6.2 反爬维度清单（评估项）

| 维度 | 评估内容 | 应对 |
|:-----|:---------|:-----|
| **限频规则** | 多少请求/秒触发限制？429 状态码？ | 加 `time.sleep` / 代理池 |
| **UA / 指纹校验** | 校验 User-Agent？校验 TLS 指纹（JA3）？ | 随机 UA / `curl_cffi` 模拟 TLS |
| **Cookie 时效** | Cookie 多久过期？是否含登录态？ | 自动登录 / Cookie 池 |
| **验证码触发条件** | 多少次请求后触发？哪种类型？ | 人工打码 / OCR / 打码平台 |
| **风控信号** | 服务端实时风控？是否有 device_id 校验？ | 逆向算法 + 模拟设备指纹 |

### 6.3 评估输出

写到 `02-interfaces/anti-crawl-eval.md`，结论包括：
- 综合难度等级（L1-L5）
- 主要反爬维度（限频 / UA / Cookie / 验证码 / 风控）
- 应对策略：是直接采（用《爬虫规范》骨架）还是进入第二部分逆向

## 7. 加密参数定位

> **目标**：找到目标加密参数（如 `sign`）到底由哪个 JS 函数生成。

### 7.1 关键字搜索（**第一手**）

在 JS 源码（Sources 面板 / 静态资源 / 反混淆后代码）中搜索：
- `sign`、`signature`、`encrypt`、`encryptData`、`aes`、`md5`、`rsa`、`hmac`、`sha`、`base64`
- 自定义头名：`x-sign`、`x-token`、`x-ticket`

**技巧**：
- 用正则：`(sign|signature|encrypt).{0,20}=`
- 全局搜索（Ctrl+Shift+F）
- 同时搜索 Network 里的请求体

### 7.2 XHR/Fetch 断点

1. Sources 面板 → 目标接口 URL 行打断点
2. 触发请求 → 浏览器自动停在断点
3. 看右侧 Call Stack，从断点往上跟栈 → 找到计算 sign 的函数

### 7.3 调用栈回溯

从请求触发点反向追溯：
- Network → Initiator 列（看是哪个 JS 触发的）
- Sources → Call Stack（多层调用）
- 在每层打 console.log，看 sign 值何时被计算

### 7.4 Hook 定位（**对混淆代码最有效**）

```javascript
// 注入到目标页面，Hook 常见加密函数
// 保存到 03-reverse/hooks/web-hook.js
const oldAES = window.CryptoJS.AES.encrypt;
window.CryptoJS.AES.encrypt = function(...args) {
    console.log('[HOOK AES]', JSON.stringify(args));
    debugger;  // 自动断点
    return oldAES.apply(this, args);
};
```

**注入方式**：
- Charles/Fiddler 替换响应（Map Local / Map Remote）
- mitmproxy response injector（`response.replace(...)`）
- Chrome Snippets（仅临时调试）

## 8. Web JS 逆向

### 8.1 混淆类型识别与还原

| 混淆类型 | 特征 | 应对 |
|:---------|:-----|:-----|
| **变量混淆** | `var _0x123abc = ...` | 重命名（VSCode + babel 插件） |
| **控制流平坦化** | switch-case 循环 | AST 反混淆（`babel/parser` + `traverse` + `generator`） |
| **字符串加密** | `"\\x65\\x6e\\x63"` | Hook `String.fromCharCode` / console.log 输出 |
| **死代码注入** | 大段永不执行的代码 | AST 静态分析剔除 |
| **自定义 VM** | 自解释字节码 | 极难，需 1-2 周分析 |

### 8.2 AST 反混淆思路

工具链（**首选**）：
```bash
npm install @babel/parser @babel/traverse @babel/generator @babel/types
```

基本流程：
1. `parser.parse(code)` → AST
2. `traverse(ast, visitor)` → 遍历节点（重命名变量、删除死代码）
3. `generator.generate(ast)` → 新代码

**现成工具**：
- `obfuscator-io-deobfuscator`（通用 obfuscator.io 反混淆）
- `js-deobfuscator`（基础还原）

### 8.3 补环境（**Node.js 执行原始 JS 时的常见障碍**）

> **核心问题**：原始 JS 在浏览器里有 `window` / `document` / `navigator`，Node 里没有 → 需补全。

**工具栈**：

| 工具 | 用途 |
|:-----|:-----|
| **vm2** | Node.js 沙箱（**首选**，安全 + 兼容） |
| **jsdom** | DOM 模拟（处理 window/document） |
| **canvas**（Node 包） | 模拟 Canvas API（Canvas 指纹场景） |
| 自写 stub | 兜底方案，按报错信息补全缺失对象 |

**常用补全对象**：`window`、`document`、`navigator`、`location`、`localStorage`、`canvas`、`WebGL`、`AudioContext`、`screen`

**技巧**：先用浏览器跑一次，把所有用到的浏览器 API 输出到文件，再在 Node 里 stub。

### 8.4 算法还原与复现

**路径 A：Python 纯复现**（**推荐**，性能好、不依赖 Node）：

| 算法 | Python 库 |
|:-----|:---------|
| AES / DES / RSA | `pycryptodome` |
| 哈希 MD5/SHA | `hashlib` |
| HMAC | `hmac` 模块 |
| 国密 SM2/SM3/SM4 | `gmssl` |

**路径 B：Node/execjs 直接调用原始 JS**（最快但有运行时依赖）：
- `pip install PyExecJS2` 或 `subprocess` 调 `node script.js`
- 缺点：性能差、部署需 Node 环境

### 8.5 正确性校验（**铁律**）

- 取浏览器实际请求的 **≥ 3 个不同 sign 值**
- 用复现算法生成同样 sign，与抓包结果对比
- **必须 ≥ 3 组样本通过**，否则算法还原错误
- 详见 `mcpowers-crawler-reverse/SKILL.md` 阶段 4 自检清单

## 9. 参数还原与复现

> §8.4 已详述 Python/Node 双路径。本节强调**正确性校验流程**与**工程化产出**。

### 9.1 还原结果校验流程（**强制**）

```
抓包拿 5 组不同入参的 sign 值（标记 sign_real_1 ~ 5）
        ↓
用复现算法生成 sign_repro_1 ~ 5
        ↓
对比：sign_real_X == sign_repro_X ?
        ↓
  全等 → 还原成功（标记 ≥ 3 组）
  任意不等 → 算法还原错误，重新分析
```

### 9.2 工程化产出

- **代码位置**：`{slug}-crawler-reverse/04-modules/{module}/functions.py`
- **接口形式**：纯函数（输入参数 → 返回 sign 值），无副作用
- **依赖管理**：`requirements.txt` 列出加密库（`pycryptodome`、`gmssl` 等）

### 9.3 边界情况

| 情况 | 表现 | 应对 |
|:-----|:-----|:-----|
| **时间戳依赖** | sign 与请求时间相关 | 算法接受 `_ts` 参数，复现时传当前时间 |
| **nonce 依赖** | sign 含一次性随机串 | 算法接受 `nonce` 参数，复现时生成新 nonce |
| **加密 Body** | 整个请求体是密文 | 复现加密逻辑（更复杂，需看 §8 算法） |
| **多 sign** | 一个请求有多个 sign 参数 | 逐一还原，每个独立验证 |

### 9.4 模块真实可用性验收（**v2.12.0 新增**）

> **目标**：把“算法正确”推进到“用户要求的业务功能真的可用”。本节是 `mcpowers-crawler-reverse` 阶段 5.5 的方法论依据；只有验收 `PASS` 才能沉淀案例或创建完整骨架。

#### 9.4.1 四层证据不可混用

| 证据层 | 证明内容 | 不能外推为 |
|:-------|:---------|:-----------|
| **算法正确性** | ≥ 3 组还原值与真实值一致 | 服务端会接受请求 |
| **协议有效性** | 一次真实请求被接受 | 业务功能完整、可重复使用 |
| **业务完整性** | 用户要求的字段/副作用正确 | 跨会话、TTL、并发稳定 |
| **运行稳定性** | 重复、生命周期和目标并发实测通过 | 未测试环境下永久有效 |

验收前必须写清输入、模块公开入口、核心业务动作、业务成功断言、运行前提和目标并发。业务成功必须校验响应业务码、关键字段、数据数量或实际副作用，禁止只检查 HTTP 200。

#### 9.4.2 串行重复与冷启动

从模块公开入口执行，而不是复用分析临时代码：

1. 至少 2 组业务输入，合计连续调用 ≥ 5 次，小样本门禁要求全部满足业务断言
2. 至少覆盖 2 个独立 session 或冷启动环境，排除 DevTools 上下文、进程全局变量和残留 token 依赖
3. 记录时间、脱敏输入摘要、HTTP/业务状态、关键字段、耗时和失败原因
4. 任一核心业务动作未完成，回到接口分析、算法还原或模块实现，不能留给项目骨架补救

#### 9.4.3 报文生命周期矩阵

§4.2 的 Cookie/Token、§4.6 的 timestamp/nonce 和 §9.3 的动态参数必须通过以下最小矩阵确认：

| 测试 | 操作 | 识别目标 |
|:-----|:-----|:---------|
| **原报文重放** | 完全相同报文额外发送 1 次 | 是否单次消费或防重放 |
| **动态参数重生成** | 业务输入不变，重新生成动态参数 | 是否能持续构造有效新报文 |
| **跨 session 重放** | 新 session 先用旧状态，再用新状态对照 | 是否绑定 Cookie、账号、设备或会话 |
| **延时 / TTL** | 根据过期字段、已知 TTL 或合理短间隔复测 | 是否受时间窗口约束 |

关键状态统一分类：

- `reusable`：仅在已验证范围内可重复使用，不得表述为永久有效
- `per-request`：每次请求重新生成
- `single-use-token`：服务端消费一次即失效，每次调用前重新获取
- `session-bound`：按 Cookie / 账号 / 设备 / session 隔离
- `time-bound`：记录 TTL 并在过期前刷新
- `challenge-bound`：封装完整“获取 challenge → 生成参数 → 请求”链路
- `unknown`：证据不足；禁止写成可复用，影响验收契约时不能 PASS

原报文重放失败不等于逆向失败。只要模块能按已确认生命周期持续生成有效新报文，并满足业务契约，即可继续验收。

#### 9.4.4 有界并发稳定性

并发验证只用于发现共享状态污染，**不是压力测试**：

1. 按并发 2 → 5 递增，每级使用最小批量
2. 分别使用相同输入和不同输入，检查 nonce/token 重用、session 线程安全、参数串值和结果交叉污染
3. 记录总数、业务成功数、401/403/429/5xx、验证码次数、P50/P95、session 策略和失败原因
4. 出现 429、验证码增加、账号安全提示、目标异常、robots/服务条款/授权不允许时立即停止
5. 用户要求的目标并发未通过或未能证明时，不能 PASS

完整项目的线程池、Session 池、代理池、Redis 锁等工程设施仍按《爬虫规范》实施；轻量模块只保留完成真实调用所需的最小状态生命周期，优先使用实例/调用级状态，禁止模块级可变全局状态。

#### 9.4.5 判定与报告

| 状态 | 条件 | 行为 |
|:-----|:-----|:-----|
| **PASS** | 当前验收契约的业务、重复、生命周期、跨会话/时效和目标并发均有实测证据 | 可进入案例沉淀和落地决策 |
| **CONDITIONAL** | 存在未被契约接受的限制，或关键生命周期仍为 `unknown` | 不得落地；调整契约后补测，满足后才能改为 PASS |
| **FAIL** | 核心业务失败、无法持续生成有效报文、状态污染或目标并发失败 | 返回对应分析/还原/封装步骤 |

统一报告到 `04-modules/{module}/verification-report.md`：测试环境、验收契约、串行结果、生命周期矩阵、并发结果、停止原因、已知限制、最终状态和证据路径。`verify.py` 未实际执行、报告缺证据或只检查 HTTP 200，均视为 FAIL。

## 10. APP 逆向（进阶）

> **核心思路**（**比 Web 难 2-5 倍**）：从「抓不到包」到「能跑通」需 4 步 —— **脱壳 → 静态分析 → SSL Pinning 绕过 → frida Hook**。

### 10.1 脱壳（**加固 APP 的第一道坎**）

**判断是否加固**：解压 APK 看 `lib/` 目录有无 `libexec.so`、`libjiagu.so`、`libDexHelper.so` 等。

**脱壳工具**（按强度选择）：

| 工具 | 用途 |
|:-----|:-----|
| **FRIDA-DEXDump**（**通用首选**） | 基于 frida 运行时 dump dex |
| **FART**（**ART 主动调用 + 脱壳**） | 处理 ART 优化后的 dex（**加固方案较优时用**） |
| BlackDex | 360 加固专用 |
| DexHunter / drizzledumper | 老版本方案 |

**脱壳产物**：纯 dex 文件 → 用 jadx 反编译看源码。

### 10.2 SSL Pinning 绕过（**抓到包的关键**）

**症状**：APP 装了证书，但抓包工具全是 `Tunnel to ...` 或 `SSL handshake failed`。

**绕过方案**（**按优先级选**）：

| 优先级 | 方案 | 适用 |
|:-------|:-----|:-----|
| 1 | **frida + objection**（**推荐首选**，免改包） | 大多数 APP |
| 2 | frida 自写脚本（更灵活） | objection 不支持时 |
| 3 | **justtrustme**（Xposed/LSPosed 模块） | 需 root + Xposed/LSPosed 环境 |
| 4 | 重新打包（终极方案） | 所有方案都失效时 |

**objection 一键绕过**：

```bash
objection -g com.target.app explore
# 在 objection REPL 里执行：
android sslpinning disable
```

**frida 自写 SSL Bypass**：

```javascript
// 保存到 03-reverse/hooks/ssl-bypass.js
Java.perform(function() {
    var TrustManagerImpl = Java.use('com.android.org.conscrypt.TrustManagerImpl');
    TrustManagerImpl.verifyChain.implementation = function() { return []; };
});
```

**iOS SSL Pinning 绕过**：用 `frida-ios-dump` + SSL Bypass 脚本，流程类似但工具不同。

### 10.3 静态分析（看代码，不运行）

| 工具 | 用途 |
|:-----|:-----|
| **jadx / jadx-gui**（**首选**） | dex 反编译，可读性最好 |
| apktool | APK 解包，看资源、清单、smali |
| dex2jar + jd-gui | jadx 不支持时备选 |
| Android Studio | 官方 IDE，自带 APK Analyzer |

**关键搜索**：与 Web 逆向类似（`sign`、`encrypt`、`aes`、`token`、`x-sign`、`x-ticket`、`hmac`）

**关键关注类**：
- 加密类：`javax.crypto.*`、自定义 `XxxUtil`、`CryptoUtils`
- 网络类：`OkHttpClient`、`Retrofit`、`Interceptor`、`Request.Builder`
- 风控类：`DeviceFingerprint`、`RiskControl`、`FingerprintCollector`

### 10.4 动态分析（frida Hook）—— **最有效手段**

**安装 frida-server**：root 设备 + 推送 frida-server + 启动

**Hook 加密函数**（**核心**，直接拿到入参/出参）：

```javascript
// 保存到 03-reverse/hooks/app-sign-hook.js
Java.perform(function() {
    var EncryptUtil = Java.use('com.target.app.utils.EncryptUtil');
    EncryptUtil.sign.implementation = function(input) {
        var result = this.sign(input);  // 原始调用
        console.log('[HOOK sign] input=' + input + ' output=' + result);
        return result;
    };
});
```

**执行**：`frida -U -f com.target.app -l app-sign-hook.js --no-pause`

**Hook 网络请求**：Hook OkHttp 的 `Interceptor`/`RealInterceptorChain`，**直接拿到最终请求体**（无需反编译 sign 生成逻辑）

**Hook native 层**：so 文件里的 `JNI_OnLoad`、加密函数，需 IDA/Ghidra 配合

**脱壳后 Hook**：用 FRIDA-DEXDump 脱壳后，Hook 完整源码里看到的加密函数

### 10.5 so 层分析（**极难**，仅当 Java 层没找到时）

| 工具 | 用途 |
|:-----|:-----|
| **Ghidra** | NSA 开源，**首选** |
| IDA Pro | 商业级，业界权威 |
| `strings` / `objdump` | so 文件初步探查 |
| `nm` / `readelf` | 导出符号表 |

**基本流程**：`strings` 搜索 → `objdump` 看导出函数 → IDA/Ghidra 静态分析 → frida Hook native 验证

**替代方案**：直接 frida Hook JNI 入口，把入参/出参 dump 出来，**算法分析工作量大幅降低**

## 11. 验证码与风控应对

### 11.1 验证码类型与应对

> **v2.9.3 铁律**：遇到任何类型验证码，**AI 必须主动解决**，**不得以"难以绕过"为由建议人工**。行为验证码的"通常降级"已改为"先穷尽自研手段再降级"。

| 类型 | 特征 | 应对方案（**v2.9.3 主动解决**） |
|:-----|:-----|:---------|
| **图形验证码**（简单） | 4-6 位数字字母 | **主动解决**：Tesseract / PaddleOCR / 打码平台（主动调用，**不推人工**） |
| **滑动验证码** | 拼图 + 滑动轨迹 | **主动解决**：轨迹模拟（贝塞尔曲线 + 随机扰动）+ OpenCV 缺口识别 + 行为轨迹拟合（**不推人工**） |
| **点选验证码** | 按顺序点击文字 | **主动解决**：OCR（点选文字识别）+ 行为轨迹拟合 + 必要时打码平台（**不推人工**） |
| **行为验证码**（极验/腾讯） | 拖动 + 行为评分 | **先穷尽自研**：1) 行为轨迹深度拟合（贝塞尔 + 加速度曲线 + 鼠标抖动）2) JS 逆向获取 gt/challenge 3) 真实浏览器 CDP 接管（详见 §2.5）。**仅当以上全部失败才降级** |
| **短信验证码** | 短信下行 | 接码平台（合规敏感，需用户明确授权） |

### 11.2 风控参数生成还原

**设备指纹**（常见 5 类）：

| 维度 | 生成方式 | 模拟难度 |
|:-----|:---------|:---------|
| **浏览器指纹**（Web） | UA + Canvas + WebGL + 字体列表 | 中（Playwright stealth） |
| **设备指纹**（APP） | `IMEI` + `MAC` + `Android ID` + `OAID` | 高（需 root 改值） |
| **行为轨迹** | 鼠标轨迹 + 滑动速度 + 点击间隔 | 高（行为评分模型） |
| **IP 风险** | IP 信誉库 + ASN + 地理位置 | 中（高质量代理池） |
| **账号风险** | 登录设备数 + 登录频率 + 异地登录 | 高（养号） |

**应对决策树**（**v2.9.3 强化：先防御再主动解决再降级**）：

1. **第 1 步：指纹防御（默认已开）** —— `playwright-stealth` + UA/视口/时区合理随机 + 行为模式伪装 + Cookie 持久化
2. **第 2 步：仅 L4 设备指纹** —— 逆向生成算法 + Playwright/真实设备模拟
3. **第 3 步：含 L5 风控引擎** —— 优先**主动解决**（行为轨迹深度拟合 + JS 逆向 + 真实浏览器 CDP 接管，详见 §2.5），仅当全部失败才**降级**（降频 / 购买数据 / 走官方 API / 人工打码）
4. **风控决策误判可申诉**：少数场景支持人工申诉

### 11.3 风控对抗速查

| 难度 | 特征 | 首选方案 |
|:-----|:-----|:---------|
| L1 明文 | GET/POST 无加密 | 直接采 |
| L2 简单编码 | Base64/URL编码/固定密钥 | 一次性还原 |
| L3 动态签名 | HMAC、时间戳参与 | Web JS 逆向（§8） |
| L4 设备指纹 + 行为 | Canvas/WebGL/鼠标轨迹 | 逆向 + 浏览器环境模拟 |
| L5 风控引擎 | 服务端实时决策 | **先主动解决**（行为轨迹深度拟合 + JS 逆向 + 真实浏览器 CDP 接管，§2.5），**仅当全部失败才降级**（降频/购买数据/官方 API/人工打码） |
